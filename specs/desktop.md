# Native desktop

## Architecture decision

Use an Electrobun Bun host and a bundled Solid/Vite frontend with TanStack Router and Query. The host owns the native window, resource validation, typed RPC and backend lifecycle. The existing native Protocol, backend and `@ycoding-ai/client` remain TypeScript/Bun. The desktop has no relay, cloud account, device enrollment or separate backend API.

The bundled Bun worker owns endpoint capabilities, credentials, SDK subscriptions and connection-scoped operations. The native WebView has no Node runtime; restrict its local main-window capabilities to preferences, state, connect, disconnect, the native Session workspace operations below and event listen/unlisten. The renderer receives validated SDK results, connection status and native events, never an authorization header, arbitrary HTTP/command bridge or backend credential.

The host forwards typed connection state, replies and native events. An event larger than 16,384 UTF-8 bytes is replaced by a resync signal; the renderer then reads its Session data again. The host creates a blank window, installs a deny-all rule followed by an allow rule for `views://mainview/*`, then loads the local view. Native navigation enforcement requires packaged-window verification.

The rule syntax is sourced from Electrobun `v1.18.1` [`nativeWrapper.mm`](https://raw.githubusercontent.com/blackboardsh/electrobun/v1.18.1/package/src/native/macos/nativeWrapper.mm), SHA-256 `2f9b1b804f92f903012eb525d74e9dc77dffad06334a1353640c47b1b6706aca`: lines 1408–1451 define rule evaluation, 2132–2147 handle WKWebView navigation, 4993–5016 handle CEF navigation, and 7127–7131 expose `setWebviewNavigationRules`. The installed `package/dist/api/bun/proc/native.ts` omits `navigationRules` when calling `initWebview`; the host explicitly installs the rules on a blank view before loading its URL. Native enforcement remains unverified.

Bundle the CLI executable and native helpers in Electrobun's runtime resources. The bundle manifest lists every regular file under `backend/` with its SHA-256 digest. The controller verifies the complete tree before each backend spawn: an extra, missing, changed or non-regular entry, a non-executable main binary or a runtime version mismatch refuses the launch. A file replaced between verification and spawn remains a residual risk. The CLI host/control command executes the existing Effect/Bun lifecycle. Its private stdio endpoint reply remains inside the Bun host and control process and is never sent to the WebView.

## Backend ownership

- Own mode starts the bundled CLI with the existing `Standalone.owned` lifecycle and an explicit `[bundledExecutable, "serve"]` command with `detached: false`. Preserve random private authentication, appended `--stdio --port 0`, stdout readiness plus continuous drain and stdin EOF ownership. The direct child retains its control process's group; Core uses the retained Node child handle and exit signal for TERM/three-second grace/KILL confirmation without process enumeration. Other Standalone and Shell defaults and grouped descendant cleanup remain unchanged. Direct-child termination does not claim containing-tree supervision. Never derive this command from the desktop executable or PATH.
- Shared URL mode uses `ServerConnection.resolve` and the real native health endpoint. Shared managed-local mode discovers a compatible service and starts one using the bundled executable when absent. An incompatible managed service is left running and connection is refused. Reconnect follows the same policy.
- An explicit shared URL authenticates like `ycoding --server`, with `YCODING_PASSWORD` or `YCODING_SERVER_PASSWORD` from the app process environment. Managed discovery uses the service registration credential. The desktop accepts no password input and persists no credential.
- A connection becomes ready only after successful native health and the first actual event `server.connected`. Health alone is insufficient. Own and shared modes use the same generated client/event adapter, abortable requests and ownership-fenced reconnect. Each connected state, including after a reconnect, carries the version and PID from the latest successful health check of the current connection.
- Switching, retry and window close retire the previous client/event owner. Closing an own-mode control lease stops only its private backend. Closing a shared-mode control lease never stops its endpoint. Stale completion cannot select a backend or report readiness for a newer operation.
- Observe an own-mode control from startup, including while native health or the allowed asynchronous first-event handler is pending. A valid retirement record, invalid lease or control closure invalidates that attempt before connected publication, including same-turn native resolution. Suppress readiness, event and status callbacks from an invalidated or cancelled attempt. Join native acquisition, close any late handle exactly once and wait for successful control close before confirming retirement or admitting an explicit replacement; preserve native-close failures as unconfirmed ownership. A retirement record does not prove transport or native closure. Shared native lifetime does not end merely because its control closes.
- Private readiness carries the original Standalone PID and must match native health. `desktop-host` owns a separate private connection scope and writes exactly one internal `desktop.retired` record only after `Scope.close` succeeds. Before readiness `{type:"desktop.retired"}` confirms that every acquired private resource was finalized, including cancellation before any child was acquired. A positive safe `pid` is optional before readiness and mandatory after readiness, where it must match the original Standalone PID and its actual exit observation. Retirement never establishes readiness; an endpoint after retirement, stale PID, duplicate, malformed, partial or absent observation cannot confirm ownership. Scope-finalization failure emits no retirement record and remains a failure. Preserve the original operation result when finalization succeeds. This channel remains inside the host/control pair and is not a public Protocol or renderer operation.
- Concurrent retirement shares one finalization outcome. Failed, nonzero or signalled control closure and failed native closure remain errors, and repeated disconnect preserves that failure. Successful cancellation before readiness permits switching or an explicit later connection only after scoped retirement, complete control closure and successful native close. Unconfirmed ownership blocks respawn. Version or resource failures before a control exists remain recoverable. No automatic retry, instance replacement or empty identity map establishes cleanup.
- Remember the validated mode and a separate credential-free shared endpoint. At startup connect to the saved mode or shared managed service by default; invalid preferences prevent automatic connection. Show pending/error/retry and keep switching available without dropping an unsent draft silently.
- Preserve terminal `--standalone`, `--server`, default managed-service behavior, mini, noninteractive execution and update-version meanings. Add no renderer/release selector or redundant version flag.

## Chat workspace

Own and shared describe only the backend process lifecycle. Both use the same native Session operations through the generated client.

- The rail reads Sessions from `session.list`, 40 at a time, with the backend's default handling of background Sessions. A search is at most 256 UTF-8 bytes as sent and is trimmed; an empty search reads the newest Sessions. The next page uses only the backend's `cursor.next` together with the connection revision of the page that returned it. The worker remembers every `cursor.next` returned under the current connection revision, from any page or search, without duplicates and at most the 64 most recently returned; a cursor returned again counts as newest. Another first-page read or search adds to that list and never clears it. Only a new connection revision, a disconnect or an error clears it, and a page that settles after the revision changed adds nothing. The worker refuses a cursor from an earlier revision, a cursor not returned under the current revision, and a cursor over 4096 bytes, all before any request. Each item carries only its ID, parent ID, title, directory, updated, active, archived and pinned times, agent, model ID and provider, token counts and cost. Every field is type-checked; a malformed item is dropped whole, and a malformed list or cursor fails the read.
- One Session is read with `session.get` for its Session ID and projected like a rail item, so a Session opened from a search or a later page still has its title, model and usage. A record with a different ID or a malformed field fails the read, and so does a read that settles after a connection change.
- Pinning or unpinning names the Session ID, the connection revision and the pinned state, and sends one `session.pin` or `session.unpin` request. A revision from an earlier connection is refused before the request. A failure, or a result that settles after a connection change, is reported as not confirmed and never retried.
- Selecting a Session reads its transcript with `message.list`. Native events carrying that Session ID, and Session events for the list, mark the reads stale; a resync signal marks every read stale.
- `fileChanges` validates the Session ID and returns captured file changes from `session["file-change"].list`, the Session ID and connection revision. A malformed result is refused.
- `activity` reads the Session and up to 10 direct subagents, returning their `total`, `activeTotal` and optional `subagentNext`. For a non-standalone Session with a directory, it reads that repository's shells. It includes only shells whose `metadata.sessionID` matches the selected Session or a child in the returned subagent page, with `ownerSessionID` identifying the owner. Shells without a nonempty string owner contribute to `unattributedShellCount`; shells attributed to other Sessions are excluded. A different Session, unrelated child or mismatched shell location is refused. Standalone Sessions and Sessions without a directory return no shells. A remaining `subagentNext` means children and their shells may be absent from this bounded result.
- `projects` returns coordination settings, each listed coordination group's details and up to 50 repository inventory entries. `PageInput` accepts `cursor`, `revision` and `search`. Search is trimmed and limited to 256 UTF-8 bytes; an empty search is omitted. Search without a cursor reads the first matching inventory page while retaining settings and groups. An optional `repositoriesNext` identifies a remaining inventory page.
- `usage` returns the retained usage summary and a cost-descending model report limited to 25 rows. `hasMoreModels` indicates the report's `nextOffset`; the report also retains its aggregate total and `rowCount`.
- New chat with a directory places a bound Session in an available directory from `project.inventory`, checked again before `session.create`. An omitted or empty directory delegates location resolution to the server and requires a non-standalone Session response.
- New chat creates the Session with a client `ses_<uuid>` ID and sends the first message with a client `msg_<uuid>` ID; continuation uses a new `msg_<uuid>` per draft. The window keeps both IDs and the text locked until the backend confirms them. Retry is an explicit action that resends the same IDs; the backend returns the existing Session or admission instead of a duplicate. The worker rejects a returned Session whose ID, directory or bound scope differs, and an admission whose message or Session ID differs.
- The renderer stops, lists and answers for the Session it has selected. Native code receives only a Session ID, checks its shape and does not know or enforce which Session the window shows.
- Stop sends `session.interrupt` for the given Session ID. A stop that fails or settles after a connection change says it was not confirmed.
- Pending requests for a Session ID come from `permission.list` and `form.list`, returned with the connection revision they were read under. The worker assigns revisions from one counter that increases on every connected or reconnected state, across all backend connections, and never reuses one. An answer names its kind (`permission`, `form` or `form-cancel`), the Session ID, that revision and the request or form ID; a form answer keeps every field key exactly, including `__proto__`. The worker refuses the answer before any request if the connection revision changed, saying it was not sent. It then reads that Session's pending requests again and refuses one that is no longer listed. It answers with the listed request's own Session and ID through `permission.reply`, `form.reply` or `form.cancel`. A permission decision passes through exactly as `once`, `always` or `reject` with an optional message; the desktop never picks one, saves a rule or changes autonomy on its own. An answer that fails, or settles after a connection change, says it was not confirmed and asks for a refresh, because the backend may have applied it.
- The model list for a Session comes from `model.list` and `model.default` at the location in the backend's own `session.get` record for that Session ID. For New chat it uses a directory only if `project.inventory`, searched for that exact directory, lists it as available. The worker refuses models that the backend reports for any other location. Every model field is type-checked before it crosses to the window. A model is listed only if its ID, provider, name, status, enabled flag, context and output limits, variant IDs and profiles are all well formed. IDs, provider IDs, names and variant IDs are at most 1024 UTF-8 bytes, and profile names at most 256 bytes. Directory, shared-endpoint, form-answer and model limits count UTF-8 bytes. Any other model entry is dropped whole, never truncated, and provider headers, body, settings, costs and capabilities never cross. A Session's list also carries its current model, the default model and whether it is running, read from `session.active`.
- A profile is a saved credential's label. The window may show it and send it back only as an explicit choice from the list; the desktop never picks, inherits, saves or logs one.
- Switching a model names the Session ID, the connection revision the list was read under and the chosen model. Before anything changes, the worker refuses it if the revision changed, reads the Session, its running state and that location's models again, and refuses a choice that is no longer listed exactly. A disabled model can be chosen only through a listed profile, and a variant must be listed for the model or that profile. The backend interrupts a running turn when the model switches, so the worker refuses to switch while the Session is running and asks to stop the chat first. It reads the running state once more immediately before `session.switchModel`. A switch that fails, or settles after a connection change, is reported as not confirmed. A turn that starts in the moment between that last check and the switch can still be interrupted by the backend.
- Pending requests also include optional `guardrails` and `reviews` arrays when those reads return items. Empty or unavailable supplemental sections are omitted, preserving the permission/form envelope. Guardrail metadata is excluded; review display payloads recursively exclude credential and configuration fields. A `guardrail` reply carries `requestID` and `once`, `always` or `reject`. A `review` reply carries `itemID` and the native typed decision. Both require the connection revision, re-read the pending list, target the listed item's owning Session, and refuse settled items or stale connections before sending a decision. Backend hard-review and family ownership rules remain authoritative. No decision is automatic and no uncertain mutation is replayed.
- Every workspace read and send is fenced by the connection generation and revision. A result that settles after a reconnect or switch is rejected instead of being shown for the new connection.
- Known limitations: New chat reads at most 50 opened repositories, with no paging. The worker forwards the backend's global event stream; the renderer filters it by Session ID instead of subscribing per Session.
- Routing follows only the worker's published connection state. When the renderer loads or reloads, it shows the worker's current state unless a newer state event has already arrived.

## Local folders and host actions

`browseDirectory({ directory?, showHidden? })` works without a backend connection. Its default is the controller working directory or the user's home directory. Paths must be absolute, at most 4096 UTF-8 bytes and existing directories. The result contains `directory`, nullable `parent`, `home`, `entries` and `truncated`. Entries carry only `name`, `path` and `kind` (`directory` or `file`). Dotfiles are hidden unless explicitly requested. Valid symlinks are classified by their targets; broken symlinks and special files are omitted. Directories sort before files, with locale ordering within each kind. At most 500 entries are returned. Browsing reads metadata only, never file contents.

`openDirectory({ directory })` validates the folder on disk and registers it through `location.get`. `createDirectory({ parentDirectory, name })` validates the existing parent and creates one child non-recursively, then registers it. A trimmed name must contain 1–255 UTF-8 bytes, no separators or control characters, and cannot be `.` or `..`. Existing targets and denied filesystem access produce actionable errors. Successful registration returns `OpenedDirectory` with `revision`, `directory` and `projectID`. If creation succeeds but registration fails, the error directs the user to browse and open the existing folder rather than create a duplicate. Neither method changes the inventory admission checks for New chat or models.

`pickDirectory({ startingFolder? })` invokes the host's single-directory dialog. Cancellation, an empty array or a whitespace-only selection returns `{ directory: null }`. A selected absolute directory is also registered when the controller is connected; registration failure does not discard the selection. The headless worker refuses `pick-directory` and `pickDirectory` with an instruction to use Browse folders. `openExternalUrl({ url })` invokes the host only for a valid HTTPS URL without embedded credentials. Other schemes are refused. The headless worker cannot launch an external browser.

`changeProject` accepts `create-in-directory` with a connection revision, Project name, existing absolute directory, optional Master title and member Session IDs. It registers the folder, creates one bound Master Session, then creates the coordination group and refreshes Projects. The Master title is the trimmed explicit title or Project name. If coordination fails after Session creation, the error identifies the existing Master Session and directs the user to reuse it through Existing Session. Project updates accept `delegatedDecisions` alongside concurrency while preserving unspecified group settings.

## Native management contracts

All connected reads and mutations use the existing native client. Mutations require a connection revision, reject stale revisions before sending anything, report unconfirmed outcomes after connection replacement and never retry automatically. A source is a Session ID or an optional absolute directory; Session-scoped reads resolve location from the backend's own Session record.

- `integrations(source?)` returns `IntegrationsSnapshot` with `revision`, `source` and `items`. Items retain integration IDs, names, method descriptors and credential/environment connection summaries. Command arguments, raw credentials and backend configuration are excluded. `manageIntegration` accepts `connect-key`, `oauth-start`, `oauth-status`, `oauth-complete`, `oauth-cancel`, `command-start`, `command-status`, `command-cancel`, `wellknown-add`, `credential-activate`, `credential-rename` and `credential-remove`. Keys and completion codes are sent only to the native integration operation, never echoed. OAuth and command results project attempt ID, kind, status, timestamps and applicable URL, instructions, mode, manual-code flag or status message. The native OAuth attempt exposes `mode` and `manualCode`, not a generated device-code field. Wellknown discovery requires HTTPS.
- `mcpServers(source?)` returns `McpSnapshot` with projected server names, status strings, optional errors, resources and resource templates. A resource-catalog failure preserves server status and adds `resourcesNotice`. The `needs_auth` status is a string value, not a credential field. `manageMcp` accepts `connect`, `disconnect`, `remove` and runtime `add`. Add accepts a local command with optional absolute working directory or an HTTPS remote URL, plus an optional disabled flag. Secret headers, environment variables and OAuth client secrets are not accepted or returned.
- `manageSession` accepts `rename`, `fork`, `archive`, `unarchive`, `delete`, `move`, `daybreak`, `background`, `cancel-subagent`, `kill-shell` and `resolve-skill-conflict`. Rename trims a nonempty title. Fork accepts an optional message boundary and returns a projected `SessionItem`. Move requires an existing absolute directory. Daybreak accepts `daybreak_blue`, `daybreak_red` or null. Subagent cancellation names a direct child; native ownership checks remain in force. Shell removal resolves the Session location and verifies the shell's recorded owner before terminating it. Skill-conflict resolution names winner and loser IDs.
- `vcsDiff({ source?, mode })` returns `VcsDiffSnapshot` containing branch names, file status and patch-based diffs. Desktop mode `git` requests native mode `working`; `branch` requests the default-branch merge-base diff. Session captured changes remain available through `fileChanges`.
- `systemSnapshot({ sessionID?, directory? })` returns connection status and sanitized skills, Project artifact summaries, plugin IDs, remote state, Dots access/configuration/connection state and credential-free server URLs. With a Session ID it also reads Session skill state, paired-browser status/tabs and isolated-browser status/tabs. An unavailable section is omitted with a named notice; it is not represented as a successful empty result. Browser pairing credentials are returned only by an explicit `browser-start` mutation and are not persisted in snapshots.
- `manageSystem` accepts `browser-start`, `browser-forget`, `isolated-browser-start`, `isolated-browser-stop`, `artifact-enable`, `artifact-disable` and `remote-set`, then refreshes status. Browser operations require a Session ID. Artifact changes require the native scope, kind, ID, expected revision, version ID and digest. `plugin-activate`, `plugin-deactivate` and `plugin-add` are recognized but refused with configuration guidance: the native Protocol currently exposes plugin discovery only. No arbitrary config-write or command bridge is provided.

The typed RPC, injected bridge and line worker expose the same management methods. The line worker accepts camelCase names and hyphenated names for the new methods. Every new result is explicitly projected; nested display objects strip keys named `auth`, `password` or `authorization` case-insensitively, along with credential and configuration branches. Server basic-auth secrets and API keys never cross into the renderer.

## Selected acceptance basis

Use synthetic owned backend/database/config/registration state; never inspect or mutate a real user database, credentials or installed daemon. Positive native-client cases use an actual YCoding server, not a fabricated health/device response. Negative wire tests may use a deliberately invalid HTTP/event peer and remain distinct from native acceptance. Keep run results in task evidence.
