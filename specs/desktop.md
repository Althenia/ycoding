# Native desktop

## Architecture decision

Use a Tauri 2 Rust shell and a bundled Solid/Vite frontend with TanStack Router and Query. Rust owns only the native window, bundled resource validation, restricted invokes/events and Bun worker lifetime. The existing native Protocol, backend and `@ycoding-ai/client` remain TypeScript/Bun. The desktop has no relay, cloud account, device enrollment or separate backend API.

The bundled Bun worker owns endpoint capabilities, credentials, SDK subscriptions and connection-scoped operations. The native WebView has no Node runtime; restrict its local main-window capabilities to preferences, state, connect, disconnect, the native Session workspace operations below and event listen/unlisten. The renderer receives validated SDK results, connection status and native events, never an authorization header, arbitrary HTTP/command bridge or backend credential.

Rust forwards only typed worker messages: connection state with known fields, replies carrying data or an error bounded to 512 characters, and native events. An event larger than 1 MiB is replaced by an explicit resync signal; the renderer then reads its Session data again. Worker state and reply errors carry only fixed desktop messages; other failures become a generic message.

Bundle the CLI executable and native helpers through the owning Tauri resource map. The bundle manifest lists every regular file under `backend/` with its SHA-256 digest. Rust verifies the complete tree before it spawns the worker, and the worker verifies it again before each backend spawn: an extra, missing, changed or non-regular entry, a non-executable main binary or a runtime version mismatch refuses the launch. A file replaced between verification and spawn remains a residual risk. The CLI host/control command executes the existing Effect/Bun lifecycle. Its private stdio endpoint reply remains inside the Bun native client/control processes and is never logged or sent to Rust or the WebView.

## Backend ownership

- Own mode starts the bundled CLI with the existing `Standalone.start` lifecycle and an explicit `[bundledExecutable, "serve"]` command. Preserve random private authentication, appended `--stdio --port 0`, stdout readiness plus continuous drain, stdin EOF ownership and scoped SIGTERM/three-second fallback cleanup. Never derive this command from the desktop executable or PATH.
- Shared URL mode uses `ServerConnection.resolve` and the real native health endpoint. Shared managed-local mode performs read-only compatible service discovery. Missing, failed or incompatible managed services are visible errors, never permission to ensure/start/stop/replace a service or migrate its registration. Reconnect has the same read-only policy.
- An explicit shared URL authenticates like `ycoding --server`, with `YCODING_PASSWORD` or `YCODING_SERVER_PASSWORD` from the app process environment. Managed discovery uses the service registration credential. The desktop accepts no password input and persists no credential.
- A connection becomes ready only after successful native health and the first actual event `server.connected`. Health alone is insufficient. Own and shared modes use the same generated client/event adapter, abortable requests and ownership-fenced reconnect. Each connected state, including after a reconnect, carries the version and PID from the latest successful health check of the current connection.
- Switching, retry and window close retire the previous client/event owner. Closing an own-mode control lease stops only its private backend. Closing a shared-mode control lease never stops its endpoint. Stale completion cannot select a backend or report readiness for a newer operation.
- Show Start my own backend and Connect to a shared backend at startup. Remember the validated mode and a separate credential-free shared endpoint; show the endpoint field only in shared mode. Preference hydration never starts or attaches. Require an explicit Start/Connect action, show pending/error/retry, and keep switching available without dropping an unsent draft silently.
- Preserve terminal `--standalone`, `--server`, default managed-service behavior, mini, noninteractive execution and update-version meanings. Add no renderer/release selector or redundant version flag.

## Chat workspace

Own and shared describe only the backend process lifecycle. Both use the same native Session operations through the generated client.

- The rail reads Sessions from `session.list`, 40 at a time, with the backend's default handling of background Sessions. A search is at most 256 UTF-8 bytes as sent and is trimmed; an empty search reads the newest Sessions. The next page uses only the backend's `cursor.next` together with the connection revision of the page that returned it. The worker remembers every `cursor.next` returned under the current connection revision, from any page or search, without duplicates and at most the 64 most recently returned; a cursor returned again counts as newest. Another first-page read or search adds to that list and never clears it. Only a new connection revision, a disconnect or an error clears it, and a page that settles after the revision changed adds nothing. The worker refuses a cursor from an earlier revision, a cursor not returned under the current revision, and a cursor over 4096 bytes, all before any request. Each item carries only its ID, parent ID, title, directory, updated, active, archived and pinned times, agent, model ID and provider, token counts and cost. Every field is type-checked; a malformed item is dropped whole, and a malformed list or cursor fails the read.
- One Session is read with `session.get` for its Session ID and projected like a rail item, so a Session opened from a search or a later page still has its title, model and usage. A record with a different ID or a malformed field fails the read, and so does a read that settles after a connection change.
- Pinning or unpinning names the Session ID, the connection revision and the pinned state, and sends one `session.pin` or `session.unpin` request. A revision from an earlier connection is refused before the request. A failure, or a result that settles after a connection change, is reported as not confirmed and never retried.
- Selecting a Session reads its transcript with `message.list`. Native events carrying that Session ID, and Session events for the list, mark the reads stale; a resync signal marks every read stale.
- New chat places a bound Session in a directory from `project.inventory` that is marked available. The worker searches the inventory for that exact directory again immediately before `session.create`. Standalone creation stays unavailable.
- New chat creates the Session with a client `ses_<uuid>` ID and sends the first message with a client `msg_<uuid>` ID; continuation uses a new `msg_<uuid>` per draft. The window keeps both IDs and the text locked until the backend confirms them. Retry is an explicit action that resends the same IDs; the backend returns the existing Session or admission instead of a duplicate. The worker rejects a returned Session whose ID, directory or bound scope differs, and an admission whose message or Session ID differs.
- The renderer stops, lists and answers for the Session it has selected. Native code receives only a Session ID, checks its shape and does not know or enforce which Session the window shows.
- Stop sends `session.interrupt` for the given Session ID. A stop that fails or settles after a connection change says it was not confirmed.
- Pending requests for a Session ID come from `permission.list` and `form.list`, returned with the connection revision they were read under. The worker assigns revisions from one counter that increases on every connected or reconnected state, across all backend connections, and never reuses one. An answer names its kind (`permission`, `form` or `form-cancel`), the Session ID, that revision and the request or form ID; a form answer keeps every field key exactly, including `__proto__`. The worker refuses the answer before any request if the connection revision changed, saying it was not sent. It then reads that Session's pending requests again and refuses one that is no longer listed. It answers with the listed request's own Session and ID through `permission.reply`, `form.reply` or `form.cancel`. A permission decision passes through exactly as `once`, `always` or `reject` with an optional message; the desktop never picks one, saves a rule or changes autonomy on its own. An answer that fails, or settles after a connection change, says it was not confirmed and asks for a refresh, because the backend may have applied it.
- The model list for a Session comes from `model.list` and `model.default` at the location in the backend's own `session.get` record for that Session ID. For New chat it uses a directory only if `project.inventory`, searched for that exact directory, lists it as available. The worker refuses models that the backend reports for any other location. Every model field is type-checked before it crosses to the window. A model is listed only if its ID, provider, name, status, enabled flag, context and output limits, variant IDs and profiles are all well formed. IDs, provider IDs, names and variant IDs are at most 1024 UTF-8 bytes, and profile names at most 256 bytes. Directory, shared-endpoint, form-answer and model limits count UTF-8 bytes, as the Rust host does, so the worker never accepts a value the host refuses. The 200,000-character message limit always fits the host's 600,000-byte limit. Any other model entry is dropped whole, never truncated, and provider headers, body, settings, costs and capabilities never cross. A Session's list also carries its current model, the default model and whether it is running, read from `session.active`.
- A profile is a saved credential's label. The window may show it and send it back only as an explicit choice from the list; the desktop never picks, inherits, saves or logs one.
- Switching a model names the Session ID, the connection revision the list was read under and the chosen model. Before anything changes, the worker refuses it if the revision changed, reads the Session, its running state and that location's models again, and refuses a choice that is no longer listed exactly. A disabled model can be chosen only through a listed profile, and a variant must be listed for the model or that profile. The backend interrupts a running turn when the model switches, so the worker refuses to switch while the Session is running and asks to stop the chat first. It reads the running state once more immediately before `session.switchModel`. A switch that fails, or settles after a connection change, is reported as not confirmed. A turn that starts in the moment between that last check and the switch can still be interrupted by the backend.
- Guardrail decisions are not exposed. The TUI decides them through its review flow, which has no desktop contract yet.
- Every workspace read and send is fenced by the connection generation and revision. A result that settles after a reconnect or switch is rejected instead of being shown for the new connection.
- Known limitations: New chat reads at most 50 opened repositories, with no paging. The worker forwards the backend's global event stream; the renderer filters it by Session ID instead of subscribing per Session.
- Routing follows only the worker's published connection state. When the renderer loads or reloads, it shows the worker's current state unless a newer state event has already arrived.

## Selected acceptance basis

Use synthetic owned backend/database/config/registration state; never inspect or mutate a real user database, credentials or installed daemon. Positive native-client cases use an actual YCoding server, not a fabricated health/device response. Negative wire tests may use a deliberately invalid HTTP/event peer and remain distinct from native acceptance. Keep run results in task evidence.

| D02 | Shared discovery with incompatible registration/version | Visible compatibility error; registration and endpoint survive unchanged. |

## Native test isolation

Native backend cases and any native-window smoke must keep real credential and configuration stores, real provider endpoints and every message outside the test. Stripping the environment or adding a provider-less config is not isolation. A provider-less config is also inert, because the configuration key is `providers`, not `provider`.

`packages/desktop/test/isolation.ts` defines two trust zones.
- The test process is the trusted harness. It runs the fake provider and SDK clients and connects to backend loopback ports. It starts from the README command with no inherited credential-named variable and refuses to run otherwise. It never starts a backend-side process directly.
- The harness replaces `globalThis.fetch` for its lifetime. The generated client reads `globalThis.fetch` when it is made unless `ClientOptions.fetch` is given, and it has no default base URL, so the replacement covers the controller's native client. `@ycoding-ai/client/service` calls the global `fetch` when it runs, so it is covered too; the harness imports only its `headers` helper. The harness's own SDK clients also receive the same wrapper explicitly through `ClientOptions.fetch`. Every request is sent with `redirect: "error"`. A request is refused unless its origin is `http://127.0.0.1:<port>` and the port is either a live endpoint grant or a TCP listener that `lsof` reports as running the canonical bundled executable. Own-mode private endpoints, reported by a confined `desktop-host`, pass only through that check, cached while the verified PID is alive.
- Every backend-side process (`--version`, `desktop-host`, `serve`, `desktop-client`) starts through `/usr/bin/sandbox-exec -p <profile>`. The controller does this through its `launch` option. Confinement is inherited by every descendant, including the private backend and any tool process.
- Confined launches accept only opaque grants that the isolation module issued, never caller paths or ports:
  - An owned-root grant comes only from the module's own `mkdtemp` under its run directory. It is checked again as a non-symlink directory at each launch and revoked on release.
  - An endpoint grant comes only from a loopback listener that the module itself created (the fake provider or a harness peer). The other source is a confined `serve` started on a port the module chose. Before granting, the module verifies that the readiness line names exactly that port. The authenticated health request uses `redirect: "error"`, must return 200, and must carry the confined process's PID. Stopping the listener or backend, or the backend exiting on its own, revokes the grant, and a port holds at most one live grant.
  - A `--server` origin in a launched command must be `http://127.0.0.1:<port>/` for a live endpoint grant. Loopback syntax alone grants nothing.

Each confined launch gets a deny-by-default profile generated from validated canonical paths and exact ports. Paths must be absolute, normalized, symlink-resolved, and free of quotes, backslashes and control characters. The profile allows only:
- process fork; exec of the digest-verified bundled executable only; signals and process info within the same sandbox; sysctl reads; JIT code generation;
- metadata reads of the literal ancestors of granted paths only; never directory contents;
- reads and executable mappings of `/usr/lib`, `/System/Library` and the OS cryptex paths, plus reads of `/dev/null`, `/dev/random` and `/dev/urandom`, and writes to `/dev/null`;
- reads of the bundle's `backend/` directory and `backend.json`. Resources must canonicalize to a real directory that does not contain HOME; `backend/` must be canonical, and the manifest walk refuses symlinks and other non-regular entries;
- reads of one empty harness working directory, which every confined process inherits as its working directory;
- reads and writes of one owned fixture root. It is a fresh `mkdtemp` directory with mode 0700, owned by the current user, outside HOME and not containing HOME, under one run directory outside HOME;
- loopback bind and inbound connections on any port;
- outbound connections only to the ports of the endpoint grants passed to that launch: the fake provider, plus the granted `--server` endpoint when the command names one.

The profile grants nothing else. That covers other files under or outside HOME, the user temp directory, `/private/etc`, other loopback ports, remote addresses, Unix sockets including sockets inside the owned root, Mach services (Keychain, window server, accessibility and directory services), and exec of anything else, including `/usr/bin/security`, `git` and shells. Only the probed operations below are observed as denied.

Each fixture environment holds only HOME (the user's own, never repurposed), USER, LOGNAME and LANG when set, `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, plus owned synthetic state under the fixture root:
- `TMPDIR`, so the backend's `os.tmpdir()/ycoding` stays owned rather than shared user temp state;
- `YCODING_TEST_HOME`, the four XDG directories and `YCODING_DB`;
- `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1`;
- disabled models fetch, autoupdate and project config;
- an inline config with sharing off that pins `model` to the loopback fake provider.

Before the fake provider starts and before the first bundled-backend execution, the harness probes the boundary with harness-side oracles. The probe profile is identical to the backend profile except that it may also exec `/bin/bash`, `/bin/cat`, `/bin/ls` and `/usr/bin/nc`. Each step fails fast: the first unexpected result throws, and no later step runs. In order:
1. The probe profile reads an owned synthetic file.
2. It is refused reading a synthetic file in a sibling directory outside the owned root.
3. The same read from a descendant shell is refused.
4. Writing a synthetic file outside the owned root is refused, and the file must not appear.
5. The backend profile refuses to exec the harmless surrogate `/usr/bin/true` and `/bin/cat`. No credential utility is ever invoked; `/usr/bin/security` is denied by the same exec rule.
6. The following are refused:
   - reads of `/private/etc/hosts`, of a nonexistent path under HOME, and of the existing desktop `package.json` (under HOME in the current worktree layout);
   - a listing of HOME, which must also print nothing;
   - a no-clobber write of a new uniquely named file into HOME. If that write ever succeeds, the harness removes the file it just created and stops.
7. The following are checked against harness listeners:
   - the exact allowed loopback listener is reachable and records one connection;
   - TCP to another IPv4 loopback listener and to an IPv6 `::1` listener is refused, and neither records a connection;
   - a UDP datagram to a harness UDP listener on another loopback port is refused and none arrives;
   - a Unix socket inside the owned root is refused and records no connection.
8. Only then is a connect to the non-routable documentation address 192.0.2.1 attempted, which must be refused.
9. Last, the confined bundled backend must print its exact version.

Startup must send nothing. Connecting, reading and disconnecting must leave the fake provider's request log unchanged and create no Session; only an explicit prompt may reach the fake provider. The chat case waits for a completed assistant message with finish `stop`, disconnects, and stops its shared backend before it reads the request log. No turn from that case can reach the fake provider during a later case.

Limits:
- The profile cannot name "a port bound inside this sandbox". A confined client of a private backend chosen with `--port 0` would need every loopback port, so the worker case runs in shared mode against a confined shared backend on a known port. The worker's own-mode lifecycle is not exercised; the controller own-mode cases cover the same controller code with a trusted client.
- Loopback bind and inbound connections are allowed on any port.
- An SBPL `ip` network filter names `localhost:<port>`. It covers TCP and UDP, and both IPv4 and IPv6 loopback, on that port, so a grant for `127.0.0.1:P` also allows `[::1]:P`. Probes cover TCP to IPv4 and IPv6 loopback, UDP to IPv4 loopback, and Unix sockets. UDP over IPv6, raw sockets and ICMP are not probed.
- The HOME probes run only after every synthetic denial has passed. They would read the package manifest and a HOME listing into harness memory, without printing it, only if confinement failed after those controls; the write probe could then create, and immediately remove, one uniquely named file in HOME.
- An owned-root grant names a path, not an inode. The harness checks it again as a non-symlink directory at each launch. The parent run directory is never granted, so a confined process cannot move the root elsewhere. It can delete and recreate the root, or put a symlink at its path. The launch-time check refuses a symlink but does not detect a recreated directory.
- The production controller accepts any credential-free HTTP(S) origin from the lease reply. In tests only the harness `fetch` wrapper stops a non-loopback or unverified origin; the controller itself does not.
- Each real launch gets its own generated profile with that fixture's owned root, ports and paths. The probe runs against probe-only roots and listeners, so it does not exercise the exact per-launch profiles. The reviewer must approve the canonical values: resources, backend directory, run directory and HOME.
- Mach lookups, IPC, signals to processes outside the sandbox, and the sysctl and process-info allowances are not probed. Their denial or scope rests on the profile text alone.
- The harness's own-mode check trusts `lsof` and the first `txt` entry it reports as the listener's executable. Any process that runs the same canonical bundled executable passes it, confined or not.
- Nothing here proves zero egress. A passing probe shows only the listed refusals and the reachable allowed listener. Endpoint grants prove the port belonged to a harness listener or confined backend when granted. Revocation affects only later launches: a running confined process keeps its profile. A different local process that takes over the port after its owner stops therefore stays reachable to processes launched while the grant was live.
- A confined shared backend's port is reserved by binding and releasing it. Another process can take it before `serve` binds, in which case readiness or the PID-matched health check fails and no grant is issued. That check sends one authenticated synthetic-password health request to the chosen port.
- Grants are enforced inside the test module only. Test code that calls `Bun.spawn` or `sandbox-exec` directly bypasses them, so review must confirm that every backend-side spawn goes through `confine`, `launch` or `shared`.
- `dynamic-code-generation`, `file-map-executable` and `process-info*` with `same-sandbox` are assumed valid on the installed macOS. An unsupported operation fails profile compilation, and the first probe step stops the run.
- The deny-by-default profile has never been run. Startup may need allowances it lacks, such as Mach services, `/private/etc` reads, git or other executables, or error handling for `EPERM` from code that calls `os.homedir()`. Each failure stops the run, and each added allowance needs the same review.
- `sandbox-exec` is deprecated by Apple.

Before any native test or smoke launch, a reviewer independent of the source owner must approve:
- the generated profile and the canonical values for the run;
- the environment and synthetic config;
- that the in-boundary probe precedes the fake provider and every backend spawn;
- the exact command.

Until then these checks remain unrun. A passing run proves the probed denials, the inherited confinement and the fake-provider request log. It does not prove that unprobed operations, such as Mach lookups, were denied.

Use selected CLI resolver cases, desktop preference/resource/client/controller cases, the Rust host tests and the app's synthetic packaged smoke. Do not run full workspace/package suites or regenerate clients: this design changes no Protocol/Schema contract. Keep source checks, Rust/CLI compilation, app packaging and genuine native-window evidence distinct. Use the existing Bun workspace and configured Rust toolchain, Tauri 2, Solid 1.9.10, Vite 7.1.4, TanStack Router 1.170.36 and Query 5.104.0. Keep the configured package release-age policy and normal Cargo target/cache/config locations.
