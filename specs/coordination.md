# Projects and coordination

## Ownership and membership

A local Project contains exactly one Master Session and a roster of member root Sessions. It is distinct from repository-derived `Project.ID` and retains a `cgrp_` identifier. Each Session belongs to at most one Project as Master or member. Membership preserves Session IDs, histories, Locations, parentage, agents, models, permissions, and goals. Unknown, archived, and non-root Sessions cannot join. A Project has at most 64 members; its Master is separate from that list. A Session that joins as a member, through `coordination.create`, a `coordination.update` that adds it, or the Master tool's `create`, takes the Master's effective permissions, guardrails, and answers modes at join time as its own stored modes. Later changes to the Master's modes, including replacing the Master, leave existing members' modes unchanged; a Session that newly joins takes the current Master's modes, including a former Master re-added as a member. A later explicit change on the member persists. Goal and sleep state are not copied. The member's subagents inherit the member's modes through the ordinary subagent rules: permissions and answers through the managed-task chain, and guardrails from the member as the root of its Session family.

A member's family is the member and its unarchived descendant Sessions reached through `parent_id`. Every question/form, permission ask, and guardrail review raised in that family is the member's request for notifications, `list`, `inspect`, `answer`, and `escalate`. A request raised by a descendant carries the optional `requestSessionID` naming the requesting Session; the member's own requests omit it.

Schema owns the wire shapes and durable events. Core owns Project storage, membership validation, activation, message admission, notifications, and native delegated decisions. Protocol and Server expose owner-authenticated operations. Session Locations are resolved by the backend, not supplied by Project operations.

## Human operations

| Operation | Method and path | Request | Response |
| --- | --- | --- | --- |
| `coordination.settings` | `GET /api/coordination/settings` | — | Resolved user-level delegated-decision policy |
| `coordination.list` | `GET /api/coordination` | — | Project summaries |
| `coordination.create` | `POST /api/coordination` | `name`, `masterSessionID`, `memberSessionIDs` | Project detail |
| `coordination.get` | `GET /api/coordination/:groupID` | — | Project detail |
| `coordination.update` | `PATCH /api/coordination/:groupID` | `revision`, optional `name`, `masterSessionID`, `memberSessionIDs`, `settings` | Project detail |
| `coordination.delete` | `DELETE /api/coordination/:groupID` | — | 204 No Content |

Data responses use `{ data }`. Revision conflicts and invalid membership are explicit failures. Omitted update fields retain their values. Supplied member lists and settings replace their previous values. Settings contain `concurrency` (positive integer or null) and optional `delegatedDecisions` narrowing. New Projects default to null concurrency and inherited decision policy.

Creating a Session for a Project composes the existing Session create operation with `coordination.update`, or with `coordination.create` for a new Master. Removing a member from a Project uses `coordination.update` and leaves it running with its history intact. Deleting a member Session uses the existing Session delete and removes its membership. Deleting the Master Session deletes its Project. Deleting only the Project preserves all Sessions and their histories.

The TUI resolves a new Master's chosen directory through the repository Project's canonical directory before Session creation and prompt admission. Explicit member-directory choices remain unchanged. A failed lookup makes no creation write and keeps correction available. Project deletion is directly visible in keyboard hints and requires confirmation: cancellation changes nothing; confirmation removes only selected Project metadata and leaves Sessions, histories and files intact, including for an active Project. Empty and New project rows have no deletion target. The waiting-state `?` glyph is not a help control.

The CLI operation set is `ycoding coordination list|get|create|update|delete`. Browser relay operations use the same coordination-prefixed names, validation, ownership, and backend-resolved Locations. Uncertain mutation outcomes require reconciliation, not an automatic retry with a new identity.

## Activation

A human user message in the Master chat activates the Project. Interrupting the Master, including while idle, pauses it. That pause persists across backend restarts as `pausedReason` `interrupted`; every other Project is active after a restart. Activation clears `pausedReason`. Newly created inactive Projects omit it.

While inactive, `send` fails with `Project is inactive; send a message in the master chat to resume`; `answer`, `escalate`, and `interrupt` remain available. Routine notifications remain pending in the recorded owner's chat without starting an execution; failures, decision requests, and escalations still wake their receiver under the owner wake conditions in Member notifications. There are no separate arm, stop, complete, lease, or dispatch-queue controls.

## Master tool: `project`

The persisted Master and Sessions recorded as owners of at least one member receive the `project` tool. Every Session in a Master's family, found by walking ancestors to a Project Master, is a Project coordinator: it does not see `edit`, `write`, or `patch`, and permission evaluation denies its `edit` requests and every `shell` command the read-only shell recognizer rejects, ahead of agent allows, saved and Session approvals, permission modes, goals, and coordinator answers. Read-only shell, read, search, `project`, subagent, decision, todo, memory, worktree, MCP, and plugin tools keep their normal rules; MCP and plugin tools have no mutation classification, so only the controller instructions keep coordinators from changing the Project through them. Member Sessions and their descendants keep their normal rules and make every Project change. Executor children inherit no controller authority. A Master-family Session without the Master or supervisor role receives the Master's-subagent role text: it makes no Project changes, does read-only research, review, and evidence verification for its parent, and reports results and blockers with evidence and a recommendation. Member Sessions and their descendants receive the executor role text. `Coordination.accessOf` supplies the role and ownership scope used by tool availability, native authorization, recipient routing, and generated role instructions. Sessions outside a Project retain their configured behavior and tools.

Each member has an optional `owner_session_id` referencing a Session with `ON DELETE SET NULL`. Existing members retain null ownership; no historical owner is inferred. A null owner holds routine events and sends material items to the Master only as escalations. The Master explicitly owns members directly by default and may launch a supervisor subagent only for more than three long-running parallel members. Only the Master creates members through `create` and assigns or transfers ownership to itself or a live owner subagent; `assign` refuses a stale owner. Only the Master releases it with reason `completed` or `released`; owner self-release is refused. Member idling, failure, interruption, and execution settlement do not release ownership.

A live owner is the Master or an unarchived managed subagent the current Master launched whose task is not `cancelling`, `cancelled`, `failed`, or `lost`; any other recorded owner is stale. `create`, `assign`, notification routing, and ownership-change handoff apply this check. Ownership ends only on member removal, member archive/delete, owner cancellation/failure/loss or deletion, Master transfer, Master-only release, or Master replacement. Member idle, execution settlement and work-completion reports retain ownership. Historical `completed` release reasons remain decodable; supervisors cannot release themselves. Stale-owner releases leave members unowned, hold routine state and escalate material requests once to the Master. Existing members remain unowned without inferred backfill. Ownership changes, native controls and delivery retain their process-local fence; former owners cannot replay admissions after transfer.

| Action | Input | Output |
| --- | --- | --- |
| `create` | Either `projectID` or `name` with optional `repository`; optional `ownerSessionID`, `title`, `prompt`, `model` | `{ action: "create", sessionID, location, directory, enrollment: { groupID, member, error? }, model, branch?, owner?, prompt? }`; Master-only |
| `model` | Read: `sessionID`; replace: `sessionID`, `model`, `expectedModel` (Ref or null) | Actual member Location, state, owner and saved model; Master or recorded owner only |
| `list` | — | Project identity, active state, optional pause reason, concurrency, and members |
| `inspect` | `sessionID`, `requestID` | Current pending request identity, `requestSessionID` for a descendant's request, bounded redacted action/resources or question fields, review rules and flags, escalation reasons, and `delegation`: `routine`, `decline-only`, or `explicit-decision:<reason>`; metadata and tool descriptions are excluded |
| `send` | `sessionID`, `text`, optional `delivery`, `messageID`, `model` | Admitted message ID, member state, and whether an existing admission reconciled |
| `answer` | `sessionID`, `requestID`, `kind`, `fingerprint`, `rationale`, optional native `answer` and `confidence`, optional `decision` (`approve` default, or `decline`) | Native settlement result or visible escalation reason |
| `escalate` | `sessionID`, `requestID`, `kind`, `fingerprint`, `reason` (1–500 characters) | `delivered`, optional notice `messageID`, `requestSessionID` for a descendant's request, and `decision` (`outcome`, optional `to: master \| client`, `coordinationEscalation`, `reason`, `reviewItemID`), plus `guidance` when `decision.to` is `client`: the request stays open as the member's prompt, the user answers it in the named member Session, or in the requesting Session for a descendant's request, and messages or Master-relayed answers cannot settle it |
| `interrupt` | `sessionID` | Interrupt result and member state |
| `assign` | `sessionID`, `ownerSessionID` | Recorded owner; Master-only assignment or transfer |
| `release` | `sessionID`, `reason: completed \| released` | Cleared ownership; Master only |
| `remove` | `sessionID` | `{ action: "remove", sessionID, removed: true }`; Master only |

`remove` ends one current member's Project membership. Only the Project's Master may call it; owners, supervisors and executors are refused with "Only the Project's Master removes member Sessions". The target must be a current member of the caller's Project, so the Master itself and Sessions outside the roster are refused. Removal is for settled, verified-complete members whose delivery is integrated or finished; `release` only parks ownership and leaves the Session in the Project, while `remove` takes it off the roster and records the end of its ownership. The call is refused with "Session <sessionID> has active work or pending requests; wait for it to settle or interrupt it before removing it from the Project" while the member is running, has queued pending input, or has background work, and while the member or any of its descendant Sessions has a pending question/form, permission request or guardrail review. Descendants include every unarchived Session at any depth below the member through `parent_id`. The result is `{ action: "remove", sessionID, removed: true }`.

The runtime holds the Project's native control fence across the whole operation: it rechecks the caller, current membership and every refusal condition, then removes the member, then detaches the member's ownership and completes supervisors that no longer own any member (`completeUnownedSupervisors`). A control admitted before the removal finishes under its original ownership, and later controls recheck current membership. The service's `removeMember` runs under the Project's ownership fence and storage lock, so a call nested inside the runtime's fenced operation on the same fiber does not deadlock while other fibers still wait their turn. It rechecks current membership, advances the Project revision and time, and publishes `Changed` events. Removal deletes no Session and changes no Session, message or history record and no Session's modes; Session and Project history are preserved, and the removed Session keeps its Location, goals, agent, model and permissions. Events from before removal and while outside the Project are excluded from any later membership interval.

`list` returns member titles, recorded Locations, `lastActivity`, live state (`idle`, `running`, `waiting`, `failed`), and pending native request summaries of the member's family with IDs, fingerprints, and `requestSessionID` for descendant requests. `waiting` indicates the member's own question/form, permission request, or review; a descendant's request alone does not make the member `waiting`. Optional `drivenBy: { sessionID, title }` identifies the Master subagent that last sent to that member while the subagent is still running.

`create` authorizes the Master and validates a supplied live owner, model and optional prompt's active-Project requirement before creation. Canonical placement accepts an existing repository `projectID`, reads its canonical directory, and refuses unknown or unavailable placement without creating a directory, branch or worktree. It cannot be combined with `name` or `repository`. Worktree placement accepts `name` and optional absolute `repository` inside a Git repository; omitted repository uses the Master's Location. Only that route requires the worktree capability and follows its permission, guardrail, branch and existing-name rules.

Both routes create a standalone root Session, not a child of the Master. Its ceiling contains the Master's full ceiling plus effective agent denies: retain a deny unless a later non-deny rule covers the exact action or `*` and exact resource or `*`; other wildcard patterns do not loosen it. `title` is non-blank and at most 120 characters, defaulting to repository Project name or canonical basename, or worktree `name`. Enrollment records the owner and copies effective autonomy modes. Omitted owner leaves routine state held and material items routed as Master escalations.

Creation identity is derived from native caller, message and call IDs. A durable receipt binds its input digest, directory and optional branch; local duplicate creation serializes by identity. Retry reads that receipt and any existing Session before repeating worktree or Session creation. Changed input, changed canonical directory, foreign parentage/workspace or conflicting placement refuses adoption. The result returns actual Session ID, Location, directory, saved model or null, and `enrollment: { groupID, member, error? }`. Branch is present only for worktrees. Failed enrollment preserves the created Session and explicitly returns `member: false` with its error. The optional first prompt uses a stable message identity through `send`; its receipt is `{ sessionID, messageID, state, reconciled }` or `{ refused: <reason> }`, leaving the member intact. No failure deletes a Session, worktree or history.

`send` defaults to `delivery: queue`; `steer` admits input for an active turn. It returns without awaiting member completion. An optional model reference is `{ providerID, id, variant?, profile? }` and applies to the turn the message starts, without changing the member's configured agent or model. Invalid model choices are refused at the target Location.

`model` reads the actual saved full reference or null, never a substituted default. A write requires both replacement `model` and `expectedModel`; null compares against an unset selection. Comparison includes provider, model ID, profile and variant with exact optional-field presence. Replacement clears omitted optional fields. Native target resolution and profile binding occur at the member's Location. Selection waits for an active Step's safe boundary without interrupting or waking execution, then revalidates ownership, archive state, placement, private binding and expected selection before committing. Conflicting input model overrides and stale selections are refused. A conflict requires a fresh read; it never authorizes blind replay. Public Session model-switch controls retain their own execution guards.

`send` to a member with its own pending question/form, permission request, or review is refused for both `steer` and `queue`, because the member cannot take input until the request settles. A request pending only in a descendant Session does not refuse `send`. The refusal names each pending request by kind and request ID and directs the caller to settle it with `answer`, hand it up with `escalate`, or `interrupt` the member to withdraw it; nothing is admitted and no execution is woken. The check follows reconciliation of an existing admission and the membership and inactive-Project checks, and precedes the concurrency limit.

A supplied `messageID` makes send retries idempotent. The same ID and text reconcile the existing admission; a different text, target, or incompatible existing identity fails. Reconciliation requires current authority: a former owner cannot reuse an admitted identity after transfer. At a configured concurrency limit, sending to an idle member fails with `Project concurrency limit <n> reached`. Active member execution and admitted pending work count toward admission; work is refused, not placed in a Project dispatch queue.

Transfers, membership changes, member controls, and event delivery serialize through one process-local Project ownership fence. Controls admitted before transfer complete under their original ownership; later controls recheck the recorded owner. Delivered history remains immutable. Pending requests retain native identities and are handed to the current owner with deterministic notice identities. Late events route to the owner current at delivery, and stale owner-change notifications cannot redirect them. Restart retains ownership while leaving the Project inactive. Role instruction updates revoke controller guidance when ownership ends.

## Provenance and transcript presentation

Member messages are the owner's first-person instruction channel: an outcome, direct actions and checks, exclusions, and a stop/report condition. The `ycoding/coordination-voice` instruction source guides the Master and its subagents. The member transcript renders these as ordinary user messages under TUI rule T55, without a separate sender persona or delegation label.

The backend admits `inputOrigin: coordination` with Project, Master, sender Session, and message identities as audit metadata. Message text cannot become a native control reply or expand authority. Decision statements must be grounded in recorded human instructions or current delegated authority.

## Member notifications

Member lifecycle events and requests raised in the member's family produce notifications only for the recorded owner. Lifecycle events of descendant Sessions produce none. Completion requires no unfinished child task (including supervising ownership), no undelivered task notice, no outstanding or running job and no member pending input of any kind. Token deltas and tool progress do not notify. Deterministic admission identities prevent duplicate delivery.

Project notifications appear only in a member's live recorded owner Session. The Master receives them only for members it explicitly owns; siblings, unrelated Sessions and other Projects receive none. `started` and `progress` never wake their receiver. Completion and interruption wake only while the Project is active; urgent items retain their inactive-Project wake behavior. Waiting or starting owners retain inputs until they run; supervising owners return to running on an eligible wake, subject to open-review and revert gates. Cancelled, cancelling, failed, lost or archived owners never resume from member notices.

Unowned or stale-owner routine events (`started`, `progress`, `completed`, `interrupted`) write nothing to any transcript and wake nobody. Retained member history in the current membership interval holds their state. Attachment or transfer delivers the held state once as one compact latest lifecycle notice with a retained-event count, plus still-pending native requests; deterministic admission receipts prevent duplication after transfer or restart. A paused Project permits only urgent handoff wakes, never member replay or an automatic restart of a stopped owner.

Material items without a live owner—member failures, questions/forms, permissions, guardrail reviews and managed-child questions—reach the Project's Master as `Project escalation:` inputs with metadata `source: project_escalation`, an ownership reason (`unowned` or `owner-failed`) and request/event identities, not routine `Project notification:` rows. Explicit owner `escalate` calls use the same class and carry the supplied reason. Request handoffs deduplicate by request ID and fingerprint; child questions carry child Session ID, question ID and task revision and disappear from handoff after native answer or withdrawal. These observations grant no authority and settle nothing. Only the existing native answer path with its own ownership and approval checks can settle a child question.

Notification text starts with `Project notification:` and carries JSON metadata:

```text
{ source: "project_notification", groupID, memberSessionID, title,
  event: "started" | "progress" | "completed" | "failed" | "interrupted" | "question" | "permission" | "review" | "escalated",
  requestID?, requestSessionID?, excerpt?, memberSequence?, held?: { count } }
```

`requestSessionID` names the requesting Session when a descendant of the member raised the request, on notifications, handoffs, and escalations. The excerpt is at most 500 characters. An explicit escalation carries `source: project_escalation`, the request `kind` and `fingerprint`, the escalating subagent as `escalatedBy`, and its supplied `reason`. Notifications contain observations, not authority. The receiver rereads current member state and pending native requests before acting.

Startup recovers retained member state only from the current membership interval. It uses current ownership and deterministic receipts without waking Sessions or replaying work. Stale ownership is released, routine state remains held and pending material items escalate once. Events before joining or while outside the Project are excluded.

An owner task whose execution settles while it owns attached members is `supervising`: non-terminal, outstanding ownership, neither active model execution nor waiting for a user. It produces no parent completion notice. Waking member notices transition it to `running`; last ownership loss while idle completes it once with one parent notice. Attaching a completed eligible owner also puts it in `supervising` without execution or wake. Restart preserves supervising tasks without replay or loss.

## Delegated routine decisions

User-level `coordination.delegated_decisions` enables routine delegation by default. It is centrally configurable and revocable. Project `settings.delegatedDecisions` may only narrow inherited categories, actions, resources, and expiry; it cannot restore globally disabled authority. Every attempt binds the calling Master or subagent, current Project membership and policy, live request identity and fingerprint, and native settlement.

Default routine classes are member questions/forms and permission asks for reads, local edits, and shell commands that match no explicit-decision class. Native policy verifies these facts before settlement. In every answers and permissions mode, including Manual, a coordinator's explicit answer settles a question after validation, its approval allows a still-asking routine permission once, and `decision: decline` rejects a permission. Without an explicit coordinator answer, native question reconsideration keeps the effective mode: Manual escalates with `explicit-decision:manual-answers`, Auto settles only a valid explicit default or exactly one Recommended option, and YOLO uses the answers evaluator.

Hard and custom-rule review approvals, requests marked `requireExplicitDecision`, and mandatory human safety/platform decisions remain human-owned. Invalid guardrail configuration cannot be approved. Safe native declines remain available; ordinary outside-repository reviews are not categorically human-only. Heuristic delegation classes describe risk and cannot grant authority or replace a native gate. Uncertain/refused settlement escalates without replay. Denies and permission ceilings remain enforced. Delegation reaches requests raised in the member's family but grants no Project-edit authority to the Master's family.

Revalidate global policy, Project narrowing, membership, expiry, request state, queues, and deny/ceiling rules immediately before settlement. A coordinator names the member's `sessionID`; native settlement applies to the request's own Session, and a request from a Session outside the member's family is `stale`. Project active state gates only `send`; `answer` (approve or decline), `escalate`, and `interrupt` work while the Project is inactive. Use native decision and validation paths and record the rationale and originating Session in their audit records. Every coordinated permission settlement publishes `permission.replied` with its reply, so clients remove the pending prompt. Native audit fields retain the `coordinator` actor name. Delegation does not change any category's autonomy mode or create another evaluator.

`decision: decline` applies to permission asks and reviews, not questions (`invalid-decision`). It retains policy, ownership, membership, live-identity and settlement-time checks. A permitted decline can reject a hard/custom review or explicit-human permission without granting approval. Native rejection records `session.permission.assessed` with outcome `deny`, via `coordination`, reply `reject`, and coordinator fields, and publishes `permission.replied` with reply `reject`; reviews record `guardrail.replied` with reply `reject` and `session.guardrail.decided` with reply `reject` and coordinator fields. The member receives the rationale as feedback.

Exact repeated decisions reconcile existing settlement; conflicting or stale requests fail. Denies remain denied. Hard reviews and human-only review-box items remain human-owned. Invalid policy, unavailable evaluators, uncertain results, unsupported requests, and new approval boundaries produce a visible escalation reason rather than automatic approval.

## Escalation chain

`escalate` passes a pending member request up one hop with a reason. It requires current Project membership and the live request identity and fingerprint, and it is never blocked by inactive state, delegation policy, or human-only classification. From a Master subagent it goes to the Master as an `escalated` Project escalation that wakes the Master even while the Project is inactive, without activating outbound sends; a repeated escalation of the same request by the same caller reuses the notice. From the Master it hands the request to the human: the pending native prompt (permission, review, or question/form) stays open for the human, and a permission handoff also records `session.permission.assessed` with outcome `escalate`, via `coordination`, reason `escalated`, and the Master's reason as rationale. Review and question handoffs record no model-incident or guardrail-escalation event. The Master's `escalate` result states that the request stays open as the member's prompt, that the human answers it in that member Session (identified by Session ID and title), and that messages or answers relayed through the Master cannot settle it. For a descendant's request it states that the request stays open as the prompt of the requesting Session, named by its Session ID, which the human answers there.

Each hop appends `{ sessionID, reason }` to the request's optional `coordinationEscalation.reasons`, in order, at most four; an identical reason from the same Session reconciles, and a fifth reason returns `escalation-chain-full` without changing the chain, a `to` hop, a notice, or a handoff audit. The field appears on `Permission.Request`, `Guardrail.Request`, and `Form.Info`, does not change the request fingerprint, and is published to clients by the ephemeral `coordination.request.escalated` event `{ sessionID, rootSessionID?, kind, requestID, coordinationEscalation }`. Entering sleep defers the pending request to the review box with the chain on its `permission`, `guardrail`, or `form` payload, with reasons redacted like other payload text. When the request was already deferred to the review box, `escalate` appends nothing and returns `outcome: escalated`, reason `deferred-to-review-box`, the open item's `reviewItemID`, and the chain recorded on its payload, without a `to` hop or notice; the human decides that item through `session.review.decide`, and no coordination path settles it. A stale identity returns `stale` and appends nothing.

## Notification filtering

Filters are client preferences, not Project settings: TUI configuration, web per-browser preferences, and phone push subscription preferences. The phone column remains `coordination_filter`. Persisted `coordinator` terminology in filter values denotes Masters.

Default all-source behavior preserves existing focus, root, category, and permission rules. Optional Master-only or selected-Master filtering applies at external notification/sound delivery. Selection uses durable Master identities, not names. Categories are questions/forms, permissions, reviews, failures, and completion.

Filtering hides no in-app history, pending controls, or human review-box entries and settles no requests. Quota and machine-level notifications retain their separate policy. Unknown source state never replaces an explicit selection with all sources. Existing delivery identities remain responsible for deduplication.

TUI, web-system notifications, and phone Web Push use the same Master selection and category meanings. Phone delivery evaluates persisted subscription filters against Master identities supplied by the authenticated backend. A browser-supplied filter cannot make an unverified Session a Master. Restricted scopes require the source itself to be a verified Master; membership and saved selection IDs do not confer that identity. An unreadable Master list withholds restricted delivery without changing the saved filter.
