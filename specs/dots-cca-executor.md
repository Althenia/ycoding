# Dots CCA executor

## Boundary

The CCA executor serves the Codex exec-server process/filesystem protocol to a remote harness. It is a separate surface from the [NativeDots Session-prompt connector](./dots-native-connector.md): NativeDots admits prompts and decisions into YCoding Sessions, while CCA executes bounded process and filesystem operations against one Location. The two surfaces share no transport, session identity, or authority.

YCoding owns every part of CCA execution. The bundled Codex binary never runs as an exec-server and its sandbox helpers are never invoked. Wire shapes follow the published exec-server protocol at `openai/codex@939f5decb26456169c42bec12aac88dcdedc4b9a`, principally `codex-rs/exec-server-protocol/src/protocol.rs`; behavior, policy, and limits are those defined here, not upstream defaults.

## Identity chain

Flora device enrollment is separate from registry transport registration. A completed Flora enrollment is stored locally and its `executor_id` is reused by every later attempt; one host run keeps one Noise identity and one registry registration across its attempts. The service host (see Service lifecycle) starts attempts automatically while Dots access is On and enrolls only when no reusable, uncertain, or unreadable enrollment is stored.

1. `POST https://chatgpt.com/backend-api/flora/cca/executor` with the selected OpenAI OAuth credential and a display name (default: hostname, bounded to 100 characters) returns an `executor_id` of prefix class `ccarenv_b64_` and surfaces the executor in the account's device list. This stage (local enrollment and device-list visibility) is live-proven.
2. `POST {registry}/cloud/environment/{id}/register` with `Authorization: Bearer …`, `chatgpt-account-id`, and a JSON body `{ security_profile: "noise_hybrid_ik_v1", executor_public_key }` returns `{ environment_id, security_profile, executor_registration_id, url }`. The returned environment ID must exactly equal the requested ID, the profile must echo `noise_hybrid_ik_v1`, and `url` must be a trusted `wss:` endpoint. Any mismatch aborts before a socket opens.
3. `executor_id` is used as the registry `{id}` (`environment_id`). For this implementation, that mapping and the registry transport registration built on it are live-proven: live `/register` has succeeded with it and the resulting `wss` socket has opened. Live Noise handshake, channel establishment, and RPC request/response exchange with a real harness are established. Locally authorized command output and clean end-to-end completion are live-proven: on 2026-10-29 at 08:42:46Z a cloud task ran `/bin/zsh -c "printf 'cca-proof-ok\n'"` through the YCoding executor, which reported exit 0 with 13 bytes of stdout and 0 bytes of stderr, inside the executor Session titled "Dots task" created at 08:42:38Z. A Permission or Guardrail escalation has not been exercised live.

The `executor_public_key` is `{ suite, x25519_public_key, mlkem768_public_key }` for suite `Noise_hybridIK_X25519+MLKEM768_AESGCM_SHA256`, generated locally once per host run (one enabled configuration) and reused across reconnects, as upstream keeps one Noise identity per exec-server process. Private keys, access tokens, the signed `wss` URL, and `executor_registration_id` are secrets (see Security invariants).

## Service lifecycle

The YCoding service hosts the executor. `startNativeRemoteControl` starts `createCcaExecutorHost` beside the remote-control host and stops both on service shutdown. The host runs while `NativeDots.Host.configuration()` reports Dots access enabled with a ready pinned credential. It re-reads configuration on every configuration notification, restarts when the pinned profile, credential, account, account generation, or access revision changes, and stops when access turns Off or readiness is lost.

Enrollment state lives in `cca-executor.json` in the YCoding state directory, in the same format the register proof writes, at mode `0600`:

| Stored state | Host action |
| --- | --- |
| Absent | Enroll once with display name = hostname bounded to 100 characters and the remote-control `installation_id`; persist the outcome |
| `completed` for the current account | Reuse `executor_id`; no Flora request |
| `failed` (definitive 4xx) | Stop until the next configuration change; then remove the file and enroll once |
| `pending` or `uncertain` | Never enroll; stop with `enrollment-uncertain` until the file is replaced or removed |
| `completed` for another account | Never enroll; stop with `enrollment-account-mismatch` |
| Unparseable or missing `executor_id` | Never enroll; stop with `enrollment-unreadable` |

Reuse requires only `status` `completed`, a matching `accountHash`, and a nonempty `executor_id`. The stored `installationID` is not compared: `installation_id` is sent only in the Flora enrollment body, never by `/register`, `/validate`, the socket upgrade, Noise, or RPC. A completed state file written by the register proof and placed at this path is reused as is. A Flora request already in flight when the host stops runs to completion, bounded by its 15 s timeout, so its outcome is recorded.

Each attempt resolves the pinned credential and requires its account, credential, and account generation to match configuration. Registry requests carry the standalone exec-server identity, the codex default originator without ChatGPT's `CODEX_INTERNAL_ORIGINATOR_OVERRIDE` (`originator: codex_cli_rs`, `User-Agent: codex_cli_rs/0.165.0-alpha.1.2 (<os> <version>; <arch>) unknown`); Flora enrollment and Dot attachment keep the `Codex Desktop` identity, have a 10 s deadline, and retry once after a 401 with a refreshed credential. The host registers with `/register` once per run and reuses the registration and signed URL across reconnects; `503 registration_conflict` and `502 authentication_service_unavailable` are retried after 0.5 s doubling to 5 s plus jitter, and only a 4xx on the socket upgrade registers again. It opens the signed `wss` socket within 10 s, sends a ping every 30 s while no pong is outstanding, and drops the connection when a pong is 60 s late or a write takes longer than 60 s. The executor then acts as Noise responder with `/validate` acceptance. A socket close ends the attempt.

Each `initialize` without `resumeSessionId` opens one exec-server session with its own executor; it creates no YCoding Session. `environment/info` reports the home directory as `cwd` and `userHomeDir`. When a channel ends, its exec-server session detaches for 30 s; an `initialize` with that `resumeSessionId` on any channel reattaches it, with its thread binding, and receives its process notifications, a still-attached session answers `-32010`, and an unknown or expired one answers `-32600 unknown session id <id>`. On expiry or host stop the executor closes, killing its processes and draining grants.

### Thread Sessions

The Core executor resolves the YCoding Session for every operation with `scopeFor(attribution, { sessionId, cwd })`, where `attribution` is the request's `metadata` (`threadId`, `toolCallId`) and `cwd` is the operation's native cwd (the process cwd for `process/start`). The host answers an operation with a `threadId` with `NativeDots.Host.threadScope({ environmentID: <executor_id>, threadID, cwd })` and any other with `NativeDots.Host.unattributedScope({ environmentID: <executor_id> })`. The thread ID only routes; it grants nothing (see Local security invariants).

- **Thread Session.** One per cloud thread; an unknown thread gets a new Session. Its directory is, in order of preference, the worktree of the project assigned to the thread, the root `taskWorkspace/prepare` returned, the project root of the first command's cwd, that cwd, or home. An assignment moves an existing Session only while it has no messages. It is titled `Dots · <project or folder name>`, with ` · <first 60 characters of the first command>` appended once; a user rename is never overwritten. Its roots are `[Session directory, home]` plus the sandbox's temporary roots.
- **Unattributed Session.** One per environment, titled `Dots · unattributed`, with directory home and roots `[home]`. It receives calls that cannot be tied to one thread: filesystem calls before the exec-server session has seen a `threadId`, and calls on an exec-server session that has seen two threads. An exec-server session that has seen exactly one thread sends its unattributed calls to that thread's Session.
- **Lifetime.** Core caches, counts, and closes Session scopes; the host never closes one. A scope that fails to open reports `CCA executor scope-unavailable` and fails only that operation; the connection and other threads continue.

### Session recording

Core records each thread Session's operations in one ordered queue:

| Operation | Record |
| --- | --- |
| `process/start` | A Shell message, Started when the process starts and Ended when it closes, with the exit code and `sandboxDenied`. Output is capped at 1 MiB and stored in a file under the shell data directory. Metadata `{dots: {threadId, toolCallId, processId, cwd}}` |
| Filesystem writes and patches | One Synthetic summary per write with the path and byte counts; a FileChange record when the path is inside the Session directory |
| File-content reads | A Synthetic record in a thread Session; none in the unattributed Session |
| `fs/getMetadata`, `fs/canonicalize`, directory listings | Only when denied |
| `http/request` | Method, origin and path, status, and byte size |
| Denials | The decision trace: for each entry its kind (`permission` or `guardrail`), reply, and decider (`rule`, `user`, `auto`, `yolo`, or `expired`) |

Never recorded: environment values, `envPolicy` values, header values (including `httpHeaderEnvVars` headers), query strings, request and response bodies, and file contents. A recording failure is logged and never fails the operation.

Retryable failures are a socket drop, a credential lookup error, an enrollment file I/O failure before any Flora request, a registry network error, a registry 5xx, 408, or 429 response, and a socket open failure. After one, the host waits a jittered delay between half and all of the current backoff, which starts at 1 s and doubles to 30 s; a connection that stayed up at least 120 s resets it. A registry 4xx other than 408 or 429, a Flora rejection, and a missing or mismatched pinned credential stop retries until the next configuration change.

Stop is idempotent and awaits teardown: it cancels any backoff delay, aborts registration and socket opening, closes the transport, and waits until every exec-server session's executor has closed.

The host reports only through the service diagnostic sink, as `CCA executor <category>` with category one of `credential-unavailable`, `enrollment-failed`, `enrollment-rejected`, `enrollment-uncertain`, `enrollment-unreadable`, `enrollment-account-mismatch`, `registration-rejected`, `connected` (each time the rendezvous socket opens after `/register`), `connection-failed`, `connection-dropped`, `scope-unavailable`, `channel-opened` (each time a channel starts, before any RPC), `channel-failed`, `registration-executor-changed`, `registration-update-failed`, or `cleanup-failed`. When a channel's RPC bridge ends, the host also reports exactly one `CCA executor channel-summary end=<channel|connection|failed> rpc=<entries>` line: `end` is `connection` when the connection or host stopped, `failed` when the bridge failed, and otherwise `channel` (the stream itself closed). Entries are comma-separated in observation order: `>method` for a received request or notification (`>initialize(resume)` when a resume session was requested), `<method=outcome` for a delivered or failed response, and `~method` or `~method=outcome` for a sent or failed notification. Methods and outcomes come only from the closed diagnostic sets; any other method is `other`. At most 64 entries are listed, followed by `omitted=<count>` when more occurred, and `rpc=-` when none did. The line never contains request or process IDs, session IDs, arguments, environment, output, paths, or error text. The `/api/dots` status contract is unchanged.

## Upstream task attachment (external prerequisite)

Executor enrollment, registry registration, and device presence do not attach this computer to a Dot for task use. Attachment is a separate upstream user grant, distinct from local YCoding operation authorization: the local grants in Local security invariants decide what an inbound operation may do on this host, while attachment decides whether the upstream service routes a Dot's tasks to this computer at all. Neither substitutes for the other.

In the native client, the grant flow resolves the active Dot for a thread with `GET https://chatgpt.com/backend-api/tbo/by-thread/{thread_id}`, requiring `status` active and `active_root_thread_id` null or equal to the expected thread. It then reads `GET /tbo/{tbo_id}/computers?expected_thread_id={thread_id}` and accepts the list only when the response `thread_id` matches. The raw list carries `local_computer_access_disabled_by_admin` and one row per computer with `kind`, `environment_id`, `is_attached`, `status`, `can_connect`, and `can_disconnect`; the target computer is selected by `environment_id`, never by display name. The grant itself is `POST /tbo/{tbo_id}/computers/{environment_id}/connect` or `.../connect-and-replace` with the `expected_thread_id` query, no request body, and no retries. Which of the two the client uses follows its own rollout capability; replacement detaches the user's other desktops (the cloud computer stays attached), is confirmed in an explicit consent dialog, and takes effect wherever the user messages that Dot. Revocation is `POST` to the same path with `/disconnect`.

Server state governs: `can_connect` and administrator policy must be respected, the client invalidates and re-reads the computers list after a change, and optimistic UI success is not proof of attachment. An error can leave the change unconfirmed, so the list must be observed again before any retry. The upstream "Other devices" surface intentionally offers no Allow action for detached devices (it may offer Revoke for attached ones), so a missing button is not evidence that the API refused a grant. Equivalence between a reported `is_authorized_for_tasks` field and the source-backed `is_attached` state above is not established; the names differ and no semantic equivalence is verified.

ChatGPT's own UI offers the grant only for the computer it runs on, so YCoding performs it for its executor. `packages/cli/src/remote-control/cca-computer.ts` serves `transport.computer()` and `transport.attachComputer()` (see the [native connector status contract](./dots-native-connector.md)) with the pinned credential and the CCA headers, against `https://chatgpt.com/backend-api`:

1. Require Dots access On, the pinned credential matching configuration, and a `completed` enrollment for the current account in `cca-executor.json`; otherwise no request is sent.
2. `GET /tbo?limit=25&include_room_preview=false`, following `cursor`, keeps items with `status` `active`. One active Dot is used; several resolve through `GET /tbo/primary` `profile.id`, which must be one of them; otherwise `dot-unavailable`.
3. `GET /tbo/{tbo_id}/root-thread` must return a nonnull `root_thread_id`.
4. `GET /tbo/{tbo_id}/computers?expected_thread_id={thread}` must echo that `thread_id`. The executor row is the one whose `environment_id` equals the stored `executor_id`: `is_attached` true is `attached`; otherwise `local_computer_access_disabled_by_admin` true is `detached` with `admin-disabled`, `can_connect` not true is `detached` with `not-connectable`, and the rest is `detached`. No row is `unavailable` with `not-listed`.
5. Attach repeats steps 1–4 without the cache and posts only for a plain `detached` row: `POST /tbo/{tbo_id}/computers/{environment_id}/connect-and-replace?expected_thread_id={thread}` with no body, exactly once, never retried. It then reads steps 1–4 again and returns that observation; a still-`detached` row is reported with `rejected` after a definitive 4xx refusal and `unconfirmed` otherwise.

Status is cached per key (configuration plus the stored `executor_id`). Only the first read for a key waits for steps 1–4; later reads return the cached value at once, and a value 15 s or older starts one background refresh that concurrent reads share. A refresh that fails with `connection` keeps the last value, reports `CCA computer refresh-failed problem=connection` through the service diagnostic sink, and retries after another 15 s. A key change drops the cached value and waits for a fresh read. An attach replaces the cache with its re-read, and a read that started before the attach cannot overwrite it. Concurrent attach calls share one attempt. 401 and 403 reads are `authentication`; network failures, other non-2xx responses, and malformed payloads are `connection`. Results carry only these categories, never identifiers, tokens, or response text. `ycoding dots attach` shows the current state, warns that attaching detaches the user's other computers, asks for confirmation unless `--yes` is given, calls `dots.attach`, and prints the re-read state; it exits nonzero unless the computer ends attached.

The connect-proof and task-proof drivers do not perform this attachment. Attachment binds at task routing: a task routed through a Dot requires this computer to be attached to that Dot, independently of executor enrollment, transport registration, and any transport-only connection proof.

## Transport

The WebSocket upgrade sends exactly one header, `x-request-id`. It sends no bearer token, cookie, or account header; authorization rides on the signed URL and the Noise handshake. Redirects are errors at every HTTP step.

Each WebSocket binary message is one protobuf `RelayMessageFrame`, version `1`:

| Tag | Field | Tag | Field |
| --- | --- | --- | --- |
| 1 | `version` (uint32) | 7 | `resume { 1: next_seq }` |
| 2 | `stream_id` (string) | 8 | `reset { 1: reason }` |
| 3 | `ack` (uint32) | 9 | `heartbeat` (empty) |
| 4 | `ack_bits` (uint32) | 10 | `handshake { 1: payload }` |
| 5 | `data { 1: seq, 2: segment_index, 3: segment_count, 4: payload }` | 11 | `traceparent` (string) |
| 6 | `ack` body (empty) | 12 | `tracestate` (string) |

The harness is the Noise initiator and the executor is the responder. The handshake prologue is four parts — the domain string `codex-exec-server-relay-noise/v1`, `environmentID`, `registrationID`, `streamID` — each encoded as a `u64BE` byte length followed by the UTF-8 bytes. Before emitting any handshake response, the executor validates the initiator's static key with `POST {registry}/cloud/environment/{id}/validate`; validation failure, timeout (10 s), or an unparseable reply drops the stream silently. Handshake authorizations are bounded to 4096 bytes, pending validations to 32 concurrent, and repeated failures to 8 per 10 s cooldown.

Ciphertext data frames are consumed in strict sequence order. Reordering is tolerated only inside the fixed window below; out-of-window, duplicate, or undecryptable frames reset the stream with reason `noise_relay_protocol_error`. Decrypted records carry application messages framed as a `u32BE` length prefix plus one JSON-RPC message whose `"jsonrpc"` member is omitted. Channel dispatch runs two lanes: ordinary methods and a control lane (`process/signal`, `process/terminate`, `environment/info`, `environment/status`) that is not blocked behind ordinary work. In-flight requests are capped at 64 ordinary plus 64 control; outbound sends on the channel are serialized.

Keepalive is a transport ping every 10 s; a missing pong within 10 s closes the socket. Socket close aborts the connection's dispatch queue and every process it started. Transport `close()` clears keepalive immediately and returns one shared Promise that settles successfully only after actual socket closure, including closure that preceded the call. Closing preserves the WebSocket's existing grace period and socket-destroy fallback. An error event or a returned socket `close()` call does not establish closure. A socket without an observable close event must already be CLOSED; otherwise cleanup fails with the fixed sanitized message `CCA executor transport cleanup failed`. A thrown socket-close request produces the same failure. Removable transport listeners are detached after actual closure.

Upstream limit constants, mirrored locally:

| Constant | Value |
| --- | --- |
| Active Noise relay streams | 128 |
| WebSocket message size | 256 KiB |
| Noise ciphertext record | 65 535 bytes |
| Noise max send plaintext | 65 519 bytes |
| Carrier send chunk (plaintext per record) | 60 KiB |
| Framed JSON-RPC message (relay and RPC-session frontier) | 64 MiB |
| Default per-stream queued bytes | 4 MiB |
| Default aggregate carrier inbound bytes | 32 MiB |
| Base64 body decoded cap (RPC params) | 16 MiB |
| Reorder distance | 64 frames |
| Pending (out-of-order) bytes | 1 MiB |

The 64 MiB message size is an outer frontier checked at the relay and RPC-session layers, not a guarantee of acceptance: the lower default per-stream and aggregate carrier caps bound what is actually buffered, and oversized input resets or rejects at the first cap it crosses.

## RPC surface

JSON-RPC errors use exactly these classes: `-32600` invalid request or framing (oversize, non-UTF-8, non-JSON, non-object, invalid request ID or method name, lifecycle violations), `-32602` invalid params, `-32601` any method outside the supported set, `-32001` local authorization denial, `-32004` not found, and `-32603` internal failure. Operation errors use the classes the upstream 0.165 exec-server returns for the same condition (`exec-server/src/server/file_system_handler.rs:360-367`, verified against the shipped `codex exec-server` over loopback):

- `fs/readFile`, `fs/getMetadata`, `fs/readDirectory`, and `fs/canonicalize` on a path that does not exist answer `-32004` "No such file or directory (os error 2)", and on a path below a regular file `-32603` "Not a directory (os error 20)", inside or outside the Location roots, exactly as the official executor reports the operating-system error. A path that exists outside every root is still refused with `-32600` "Operation not permitted (os error 1)", the answer every outside-roots refusal in the executor and the extended filesystem methods gives. The upstream client turns only `-32004` into a not-found I/O error (`exec-server/src/remote_file_system.rs:54`, `:556-557`).
- `fs/readFile` on a path that is not a regular file answers `-32600` "Path is not a file". A filesystem permission error from the operating system answers `-32600` "Permission denied", and an invalid-argument error `-32600` "Invalid path"; `-32001` stays reserved for local authorization denial. A directory listing of a regular file answers `-32603` "Not a directory (os error 20)"; any other filesystem failure, including a target that is a directory where a file is needed, answers `-32603` "Filesystem error". The extended filesystem methods report operating-system errors as `<strerror> (os error <n>)`, as upstream does.
- `process/read` for an unknown process id and `process/start` with a process id that is still live answer `-32600` ("unknown process id <id>", "process <id> already exists"). A `process/start` whose cwd is missing inside the roots, is not a directory, or whose program cannot be spawned answers `-32603` "Failed to start process"; a cwd outside every root answers `-32600` "Operation not permitted (os error 1)" whether or not it exists, unless the request's sandbox context admits it (see Task workspaces); a sandboxed start with such a cwd gets the sandbox denial instead.

Error codes are limited to the classes above; any other thrown failure answers `-32603` "Internal error". The message of an allowed class is the handler's own text, unbounded and unfiltered, so upstream messages, including the paths they name, reach the wire as the official executor sends them; `data` is never sent.

Lifecycle is connection-scoped. `initialize` may be sent once; it requires `clientName`. `resumeSessionId` absent or JSON `null` is no resume request — the pinned upstream field is `Option<String>` with `#[serde(default)]` and no custom deserializer, so both decode to `None` — and proceeds as fresh initialization. A string `resumeSessionId` reattaches the detached session with that id (see Service lifecycle); a session still attached elsewhere answers `-32010`, and an unknown or expired one `-32600` "unknown session id <id>". A non-string, non-null value is rejected with `-32602`. A failed resume leaves the connection free to `initialize` again. The `initialized` notification completes the gate. Every supported method other than `initialize` requires the completed lifecycle and fails with `-32600` before `initialize` or before `initialized`; unsupported methods fail with `-32601` at every lifecycle state, including before `initialize`. Notifications other than `initialized` have no effect.

Supported methods, exhaustive:

| Family | Methods |
| --- | --- |
| Environment | `environment/info`, `environment/status` |
| Process | `process/start`, `process/read`, `process/write`, `process/signal`, `process/terminate` |
| Filesystem | `fs/readFile`, `fs/writeFile`, `fs/getMetadata`, `fs/readDirectory`, `fs/canonicalize`, `fs/createDirectory`, `fs/open`, `fs/readBlock`, `fs/writeBlock`, `fs/close`, `fs/walk`, `fs/remove`, `fs/copy` |
| HTTP | `http/request` |
| Configuration | `environmentConfig/read` |
| Capability discovery | `capabilityRoots/discoverV1`, `capabilities/discoverV2` |

Explicitly unsupported, and rejected with `-32601` like every other upstream method: `fs/watchMissing` and `network/policyRequest` as an inbound method.

The extended filesystem methods (`packages/core/src/cca/fs-extended.ts`, decoded and encoded by `cca-executor-fs-wire.ts`) and `http/request` (`packages/core/src/cca/http.ts`, through `cca-executor-http-wire.ts`) belong to the connection, not the session: each initialized connection gets its own file-handle table and HTTP client, created when `initialize` or a resume succeeds and shut down when the connection ends, so open handles and in-flight requests never survive a detach. A filesystem call with a sandbox context uses the same per-call task-workspace roots and `external_directory` approval as the core filesystem methods; file handles stay with the root set that opened them. A streamed `http/request` answers its JSON-RPC response first and only then starts the body stream, whose chunks arrive as `http/request/bodyDelta` notifications; when the response cannot be sent, the stream is cancelled.

The executor sends JSON-RPC requests to the cloud on the connection (`CcaRpcSession.call`) in its own id space: integer ids from 1, as the official executor numbers them. A matching response resolves the call, an error response rejects it with that code and message, and the call rejects after its timeout (30 s by default), when its abort signal fires, or when the connection closes. A response for an id with no pending call is dropped. Each session's `initialize` context carries a session-level `call` that reaches whichever connection the session is attached to and rejects while the session is detached; the only caller is `network/policyRequest` (see Network proxy).

`environment/info` and the `initialize` result carry the official executor's fields in its order: `shell`, `executorVersion` `0.165.0-alpha.1.2` (`ccaCompatibleExecServerVersion`), `providerId` `sha256:6c00ea8010dd56f75443a655293fd43e86b65f038786b1a257324d4a6028d4cf` (`ccaExecServerProviderId`, the bundled 0.165.0-alpha.1.2 build identity), `cwd`, `userHomeDir`, `platformOs`, `prependPathDirs` (ChatGPT's `codex-cli/codex-path` directory, `ccaExecServerPrependPathDir`, present only when that directory exists), `temporaryDirectories`, `tempDir`, and `capabilities`. Other callers of the Core builder keep its `0.0.0` version and omit `providerId` unless they pass them. `temporaryDirectories` lists the executor's own temporary directories the way the upstream executor does: on POSIX hosts the `TMPDIR` value when it is set and nonempty (resolved against the executor cwd when relative), on Windows `TEMP` then `TMP` when absolute, deduplicated, and an empty list when none apply. Capabilities advertise only what the executor implements, in the official key order. `networkProxyLaunch`, `networkProxyReviewDomains`, `credentialMasking`, `credentialMaskingCustomProviders`, and `shellSnapshotV2` come from `ccaNetworkProxyCapabilities` for the reported shell: launch and review domains are always `true`, masking is `true` only for bash or zsh on macOS or Linux and only when the executor has a proxy CA directory, and `shellSnapshotV2` is `true` off Windows. A masking or review key that is not `true` is omitted, as the official executor omits it. `capabilityDiscoverySandbox`, `capabilityDiscoveryV2`, `environmentConfigRead`, `httpHeaderEnvVars`, `sandboxedFileStreaming`, and `fileWriteStreaming` are `true`; `windowsMxc` is `false`; the Linux root-write flags are omitted. `environment/status` returns `ready` once the lifecycle gate passes. `process/start` responses report `sandboxType: "none"`; that value states the absence of a platform sandbox and nothing else. Where the official executor applies its managed sandbox and answers `macosSeatbelt`, YCoding enforces the request through Location roots, Permission, and Guardrail instead.

### Task workspaces

The cloud runs tasks in a workspace it chooses, such as `/tmp/codex-task.<id>`, and describes it in the request's sandbox context. For a `process/start` or `fs/*` call that carries a sandbox context, the context's `cwd` and `workspaceRoots`, plus `/tmp` and the temporary directories when the profile grants `slash_tmp` or `tmpdir` read or write access, join the Location roots for that one call only. A resolved path that lies outside the Location roots first needs the `external_directory` permission on `<directory>/*` (its canonical directory, with `filepath` and `parentDir` as metadata), so temporary workspaces follow YCoding's temporary-directory rule and other directories ask; the call's own `shell`, `read`, or `edit` authorization follows. A denied approval answers the upstream sandbox denial: a sandboxed start finishes with `sandboxDenied: true`, and a restricted filesystem call answers `-32600` "Permission denied". Calls without a sandbox context keep the Location roots alone.

### Executor-local configuration

`environmentConfig/read {cwd, configPaths, requirementsPaths}` ports upstream `exec-server/src/environment_config.rs` and `config/src/loader/local.rs` at 720fec86. Params decode like the upstream serde structs: a missing field answers `-32602` "missing field `<name>`", a wrong type "invalid type: <found>, expected <type>", a relative or non-`file` `cwd` "invalid URI: relative URL without a base" or "unsupported path URI scheme `<scheme>`", no paths at all "at least one config or requirements path is required", and an empty path "TOML paths must contain at least one key segment". The result is `{userHomeDir, codexHomeDir, hostname, config, requirements}`: `userHomeDir` is the executor home, `codexHomeDir` is `CODEX_HOME` (canonical, which must be an existing directory) or `<home>/.codex`, and `hostname` is the lowercased host name without a trailing dot.

- **Config layers**, lowest precedence first: system `/etc/codex/config.toml`, user `<codexHome>/config.toml`, the project layers, and legacy `/etc/codex/managed_config.toml`; `cloudInsertionIndex` starts after the system layer. A missing file is an empty layer. Project layers are each `<dir>/.codex/config.toml` from the project root (the nearest ancestor of `cwd` holding a marker from `project_root_markers`, default a `.git` with `HEAD`) down to `cwd`, loaded only when the directory, the project root, or the repository root is `trusted` in the merged `projects.<path>.trust_level` (canonical path first, then the spelling given), never for `<codexHome>` itself, and with the upstream project-local denylist and feature keys removed.
- **Requirements layers**: system `/etc/codex/requirements.toml`; `cloudInsertionIndex` is 1 when it exists.
- **Projection.** Each layer keeps only the requested TOML paths; a layer left empty is dropped and the cloud insertion index counts only kept layers before it. A layer reports `source` (`system (<file>)`, `user (<file>)`, `project (<dir>/.codex/config.toml)`, `legacy managed_config.toml (<file>)`, or the requirements file path), `baseDir` as a `file://` URI, and `toml` serialized the way the official executor's `toml` 0.9 writer does: key order kept, values before subtables, `[[array]]` headers for arrays of tables, and its string, float, and datetime spellings.
- **Errors.** A configuration file that cannot be parsed or read answers `-32603` "failed to load executor-local config: <file>:<line>:<column>: <reason>"; the reason text is YCoding's own.
- **Not ported**: macOS MDM managed preferences, the legacy managed-config-to-requirements mapping, linked-worktree hook layers, credential-broker requirement checks, and DNS lookup of the fully qualified host name.

These files are read directly by the executor, as upstream does, not through Location roots or Permission.

### Capability discovery

`capabilityRoots/discoverV1 {roots: [{id, path, sandbox?}]}` ports upstream `exec-server/src/capability_discovery.rs`. Each root is opened as one read tree: the executor resolves the root within its roots (and the root's sandbox workspace, as for any sandboxed call), asks Permission and Guardrail once for `read` on the root, and holds that grant for the whole scan. Reads below the root's canonical path use the grant; a path that resolves elsewhere, such as a symlink target or an ancestor plugin manifest, goes through the ordinary authorized `fs/*` call. A root's `sandbox` applies the way the official sandboxed scan does: metadata stays readable, while listing a directory or reading a file the profile does not grant fails, and the scan records "failed to scan capability path <uri>: Operation not permitted (os error 1)" or "failed to read capability file <uri>: Operation not permitted (os error 1)" as a warning. More than 128 roots answer `-32600`. Each root answers `{id, path, plugin, skills, namespaceManifests, warnings, error}` in request order: a missing root or one that is not a directory sets `error` ("failed to inspect capability root <uri>: <reason>", "capability root <uri> is not a directory"). The root is walked to depth 6, at most 2,000 directories and 20,000 entries, following directory symlinks. `skills` lists every `SKILL.md`, sorted by URI, as `{instructions: {path, contents}, metadata}` with `metadata` the sibling `agents/openai.yaml` or `null`. `plugin` is the root's first `.codex-plugin`, `.claude-plugin`, or `.cursor-plugin` `plugin.json` with its `mcpConfig` and `appsConfig` files, or `null`; `namespaceManifests` lists the inherited ancestor manifest and every nested plugin manifest. Files over 1 MiB, a bundle over 16 MiB, unreadable files, and non-UTF-8 files are skipped with a warning.

`capabilities/discoverV2 {cwd, sandbox?}` is served by `cca-capability-discovery-v2.ts` over the same read trees as V1, with the home directory, `CODEX_HOME`, and system config path that `environmentConfig/read` uses. It answers `{plugins, skills, warnings}`; a skill is `{name, description, shortDescription, path, discoveryRoot {id, path}, dependencies, policy}`. Decode failures answer `-32602` with the serde text ("missing field `cwd`", "invalid URI: relative URL without a base") and discovery failures `-32603`, both passed through unchanged. Each connection gets its own discovery instance, created with the connection's other resources and closed with them; its change subscription is not sent on the wire.

### Standalone execution

The service host behaves like a standalone `codex exec-server --remote` that no ChatGPT desktop app hosts. Every request reaches the executor handler unchanged; ChatGPT's desktop task-workspace commands are answered as described in Desktop task-workspace requests. The host sends no `thread/environmentReady` reports and opens no connection to `codex-cloud-backend.chatgpt.com`.

### Desktop task-workspace requests

ChatGPT runs the desktop project protocol as a `process/start` whose argv is `[<shell>, "-c", <script>, "task-workspace", <client>, <base64 request>, …]`. The executor answers it instead of running the script (`packages/cli/src/remote-control/cca-task-workspace.ts`, through Core's `answerProcess` hook). The script text is never examined.

- **Authorization and recording.** The start is authorized as `shell` and recorded like any process start; the answer is decided after authorization and before any spawn, and it becomes the Shell message's stdout and exit code.
- **Validation**, as ChatGPT.app's app-tools pipe validates it: standard base64 of a JSON object with `jsonrpc` `"2.0"`, an `id` that is a string or finite number, and object `params` whose nonempty `environmentId` equals this executor's ID. `taskProject/list` params hold only `environmentId`. `taskProject/assign` params hold exactly `environmentId`, `projectId`, and a nonempty `threadId`. `taskWorkspace/prepare` params need `cwd` as a nonempty string or `null`, accept a boolean `includeModelDefaults` and a `projectId`, and keep other keys. A `projectId` must be nonempty with no surrounding whitespace. Every other method, including `taskThread/read`, is rejected.
- **`taskProject/list`** answers `NativeDots.Host.projectCatalog({ environmentID })` as `{environmentId, projects: [{projectId, name, rootPaths}]}`.
- **`taskProject/assign`** answers `Host.assignProject({ environmentID, threadID, projectID })` as `{environmentId, projectId, threadId}`.
- **`taskWorkspace/prepare`** answers `Host.prepareWorkspace({ environmentID, threadID, cwd, projectID })`, with `threadID` from the start's `metadata.threadId`, as `{cwd, runtimeWorkspaceRoots, projectId?}`. `modelDefaults` is always omitted; YCoding model IDs are not ChatGPT IDs.
- **Frame limits.** The desktop answers with a frame `{id, jsonrpc, result: {payload, signature}}` whose payload is `{domain, request, <result field>}`. An answer whose frame would exceed 1 MiB for `taskProject/list`, or 64 KiB otherwise, fails.
- **Success output.** stdout is the answer's JSON with every UTF-16 unit at or above U+007F escaped as lowercase `\uXXXX` and no trailing newline; stderr is empty; exit code 0.
- **Failure output.** A rejected request, a Host error (including `not_found` for an unknown project), or an oversized frame gives empty stdout, stderr `Desktop task request failed\n`, and exit code 1.
- **Process semantics.** The answer becomes a completed process through Core's synthetic-process path: `process/output` (seq 1, the one non-empty stream), `process/exited` (seq 2), and `process/closed` (seq 3), with `process/read`, `process/write`, `process/signal`, and `process/terminate` answering as for a real process that printed the same output.

### Capability roots

The executor registers two capability roots, `{id: "codex-home-skills", path: <home>/.agents/skills}` and `{id: "ycoding-dots-skills", path: <Global data>/dots/skills}`, as `selected_capability_roots` in its Flora registration body (the desktop's `[{id, path}]` shape) and stores the registered roots in its enrollment state. Before registering, the host writes the bundled `ycoding-operator` skill to `<Global data>/dots/skills/ycoding-operator/SKILL.md`, only when the file is missing or its content differs. Capability discovery V2 scans and watches `ycoding-dots-skills` like the other standalone roots, under the request's sandbox, so sandbox denials still apply. No YCoding skill source reads that directory, so the skill is not visible to YCoding's own Sessions. Whether the cloud reads a root id other than `codex-home-skills` is verified live. When the stored roots are missing or differ from the current ones, the host re-registers with the stored `installation_id` before connecting, retrying once after 1 s; it never creates a new installation. A changed `executor_id` is saved and reported as `CCA executor registration-executor-changed`; a failed re-registration is reported as `CCA executor registration-update-failed` and the previous registration stays in use.

Paths on the wire are `PathUri` values: absolute `file://` URIs, percent-encoded, never native paths. File bodies and process I/O chunks are standard base64 (`dataBase64`, `chunk`). Supported parameter fields and response shapes follow the pinned protocol with the local limits and defaults below. Malformed supported fields are `-32602`, never coerced. Unrecognized fields do not grant capabilities or authority.

### Sandbox requests

`process/start` and the five supported `fs/*` methods accept every well-formed upstream sandbox, network, and permission-profile shape. Core `CcaPolicy.resolveSandbox` validates and maps them; a malformed shape answers `-32602` before any authorization. Shapes follow `exec-server-protocol/src/protocol.rs` at `openai/codex@720fec862a608ae1e5878d1eecb04fb93192e93c` (its serialization tests) and the serde names in the shipped `0.165.0-alpha.1.2` binary. Upstream core sends `sandbox` whenever a turn's permission profile requests sandboxing (`core/src/tools/sandboxing.rs:554-571`), and apply_patch sends it on filesystem calls (`core/src/tools/runtimes/apply_patch.rs:88-115`). YCoding has no platform sandbox backend, so `sandboxType` stays `"none"`.

Location roots, local Permission, and Guardrail apply to every request, as in Local security invariants; a sandbox never widens them. Sandbox and network intent selects roots and profile checks but is not authorization metadata: a `process/start` authorization carries only `{cwd, workdir, argv?}`, an `external_directory` authorization only `{filepath, parentDir}`, and executor filesystem authorizations carry none, so an approved action matches its retry whatever the retry's `processId` or sandbox. The spawned program runs with host-user authority, so the requested filesystem and network confinement is not applied to it. That gap is the one stated in Local security invariants.

A `process/start` is sandboxed when its profile is `managed`, its filesystem or network is restricted, and its override is not `bypassSandboxFirstAttempt`, which is when upstream would apply a platform sandbox. YCoding denies a sandboxed start when the cwd is outside the Location roots, when the profile cannot read the cwd, or when Permission or Guardrail refuses. The denial then follows upstream's sandbox-denial semantics (`exec-server/src/local_process.rs:1097-1143`):

- The start answers `{processId, sandboxType: "none"}` without spawning anything.
- It then emits `process/output` (seq 1, stderr `sandbox denied: Permission denied by YCoding policy`), `process/exited` (seq 2, `exitCode: 1`, `sandboxDenied: true`), and `process/closed` (seq 3).
- `process/read` returns that chunk with `exited`, `closed`, `exitCode: 1`, and `sandboxDenied: true`. `process/write` answers `stdinClosed`.

Upstream core treats an executor-reported denial as a sandbox denial (`core/src/unified_exec/process.rs:323-350`). It may then escalate through its own approval and retry without `sandbox` (`core/src/tools/orchestrator.rs:395-560`). The retry is an unsandboxed start, which still needs local Permission and Guardrail. Unsandboxed starts keep `-32001` for an authorization denial and `-32602` for a cwd outside the roots.

A filesystem call has a restricted filesystem when its profile restricts it and its override is not `bypassSandboxFirstAttempt`. Such a call answers `-32600` "Permission denied" when the target is outside the Location roots, the profile forbids the access (`write` for `fs/writeFile`, `read` otherwise), or Permission or Guardrail refuses. This is how upstream reports a filesystem permission error (`exec-server/src/server/file_system_handler.rs:360-367`), and its apply_patch recognizes "permission denied" as a sandbox denial. A missing path inside the roots stays `-32004`.

Process rules:

- `processId` is a client-chosen, connection-scoped handle, unique among live processes; it is not an OS pid.
- `process/read` pages retained output by `afterSeq` with optional `maxBytes` and `waitMs`; sequence numbers are only meaningful inside one process lifetime.
- `process/write` requires a nonempty `writeId`; an accepted `writeId` acknowledged twice writes bytes once.
- `process/signal` accepts only `interrupt`. `process/terminate` kills the whole process group, as does connection close.

Filesystem rules: `fs/writeFile` replaces a regular file from one base64 body; missing parent directories are created after the containment check passes on the canonicalized nearest existing ancestor. `fs/readFile` returns the whole file as `dataBase64`, bounded by the local output caps. `fs/readDirectory` is one level, bounded to 50 000 entries. `fs/canonicalize` returns the resolved absolute `PathUri`. `fs/getMetadata` reports type, size, and timestamps only.

### Network proxy

A `process/start` with `networkProxy` runs in this order: the child environment is built, the executor-local proxy (`packages/core/src/cca/network-proxy.ts`) starts on loopback and rewrites the proxy and CA variables, the shell snapshot (if any) is prepared, and the child spawns. Each executor session keeps one credential-broker cache across launches; the proxy CA lives in `cca-proxy` beside the executor state file. Host decisions follow the launch config: deny entries win, allowlisted hosts pass, local and private addresses pass only when explicitly allowlisted or when `allowLocalBinding` is set, and a host that is neither allowlisted nor denied, or is a review domain, is asked of the cloud when `policyDecisionTimeoutMs` is present. That question is a `network/policyRequest` request `{processId, request: {protocol, host, port}}` sent with the session-level `call`; a missing, late (after the timeout plus 5 s), malformed, or rejected answer, or a detached session, denies with `not_allowed`. Every decision is reported as a `network/policyDecision` notification `{processId, timestamp, scope, decision, source, reason, protocol, host, port, method?, client?, policyOverride}`; allowed connections are still authorized locally as `webfetch`. With `credentialMasking`, a `bash -c` child gets masked placeholders for brokered credentials, and the proxy restores the real values on matching requests. Other launches keep real credentials (a `zsh -lc` snapshot launch masks through the snapshot instead); the warnings the proxy returns are not sent on the wire, as upstream sends none. The proxy closes when the process closes, when its start fails, or when the session closes, and the decider's abort signal fires at the same time.

Known difference: a blocked plain-HTTP request gets `403` with `x-proxy-error` but a `text/plain` body, where the official proxy answers `content-type: application/json` with `{"status":"blocked","host","reason","decision","source","protocol","port","message"}`.

### Shell snapshots

A `process/start` with `shellSnapshot {scopeId, shell {name, path}}` and argv `[shell.path, "-lc", script]` replays a captured login-shell state instead of running the login profiles (`packages/core/src/cca/shell-snapshot.ts`). The capture is authorized as `shell` `<shell> -lc <shell snapshot capture>`, runs once per session, scope, shell, cwd, environment policy, and sandbox, and is reused by later starts with the same key; a launch whose proxy masks credentials through the snapshot captures afresh each time. Other argv shapes run unchanged. `bash`, `zsh`, and `sh` are supported; another shell name answers `-32602` "shell snapshots are unsupported for shell `<name>`". The snapshot descriptor is passed to the child on fd 10 and closed in the executor once the child has spawned. The snapshot cache closes with the session.

## Local security invariants

Remote policy is input, never authority. The effective policy for every operation is the **intersection** of the harness request, local Permission rules, and SessionGuardrail rules. No field supplied by the harness widens local authority: not `sandbox`, `envPolicy`, `metadata`, capability roots, or network decisions. Absence of harness policy means the local default applies, never an upstream default.

YCoding has no enforceable local sandbox backend. Sandbox and network intent is mapped onto Location roots, Permission, and Guardrail as described in Sandbox requests; shell snapshots are replayed as described in Shell snapshots. A process, with or without a sandbox request, starts only when local Permission and Guardrail allow it, runs with ordinary host-user authority, and is reported as `sandboxType: "none"`. Host-user authority means a spawned program can read, write, and execute anything the host user can: Location roots constrain the executor's own filesystem calls and the process working directory, they do not confine what the spawned program itself opens afterwards.

Every operation — reads as well as mutations and process control — is authorized before any side effect through a mandatory grant. The Core authorizer (`packages/core/src/cca/authorization.ts`) asserts local Permission and acquires a SessionGuardrail reservation against a real, durable YCoding Session, and returns a grant whose `release()` ends the reservation. In the service host, that Session and its authorizer come from the thread or unattributed Session scope Core resolves for the operation (see Thread Sessions). The scope's authorizer denies once the Dots access or configuration revision changes or the Session is missing, archived, or deleted; re-enabling access does not revive it. Closing the scope keeps the Session. In the task proof, the task runtime creates the Session for the CCA connection (titled "CCA task proof"). Each authorize call runs current-Session check → Permission assert → Guardrail reservation → current-Session recheck under one interruptible 15-second total deadline (configurable), with a fresh `cca:` UUID holder per request. Dots scopes (thread and unattributed) pass `defer: true` to Permission and Guardrail, so a step that needs a human decision fails at once with a review item instead of waiting; the deadline then bounds only the automated steps, and a timeout refuses with the busy text (see Decisions from Dots). The task proof runtime has no decision channel and passes no `defer`: an ask there waits for the deadline and then denies with `-32001`, without an item or busy text. Every Permission assert passes `save: <resources>`, so an "always" approval is remembered for the identical action. CCA RPCs are not tool calls, so no canonical message/call `source` is fabricated for them: the authorizer omits `source` entirely. Harness `metadata.threadId` only selects which of this executor's Sessions an operation runs in, and `toolCallId` is recorded attribution; neither is used as that `source`, as a permission resource identity, or as approval evidence, and neither widens local authority. There is no void or default authorizer: denial, and an authorizer that returns no grant, fail with the fixed `-32001` "Permission denied" and no side effect occurs. Authorization evidence is complete, not summarized: `process/start` is authorized as `shell` against the full argv joined with spaces, except that a shell wrapper `[<sh|bash|zsh path>, -c|-lc|-ic, <script>]` (exactly three elements) is authorized against its script, as the YCoding shell tool presents a command, with the full argv as JSON in the `argv` metadata; the process cwd is passed as `workdir`, so Guardrail resolves relative targets against it. `process/write` is authorized against the full decoded stdin text (bounded by the chunk cap), with any short preview carried only as additional audit metadata.

Grant lifetime matches the authorized work. Each grant is released exactly once: per-operation grants (process read/write/signal/terminate and every filesystem call) release when that operation settles, and the `process/start` grant is held for the process's whole lifetime and released only after it has exited and its output has drained. A failed preparation step, spawn failure, cancellation, or connection close releases the start grant too. Release failures never surface as success and never carry local detail: they become the fixed `-32603` "Internal error" for the operation, or for a start grant are recorded on the executor and surfaced by `close()` after teardown completes. Exited process bookkeeping is pruned only after the child has closed and its lifetime has settled, so pruning cannot discard an unreleased grant or an unrecorded release failure. `close()` kills every process, then waits for actual process teardown and every outstanding grant release before returning.

Every `PathUri` is decoded strictly, converted to a host path, canonicalized with symlink resolution, and required to lie inside the connection's Location roots before use (Core `CcaPolicy.parsePathUri` / `resolveContained`). A write target whose final component does not exist is resolved against its nearest existing ancestor and must still land inside a root. Symlink escapes, sibling-prefix paths, dot segments, and foreign authorities are rejected. Caller controls such as `followSymlinks`, `recursive`, and `force` never relax containment. Containment is a time-of-check guarantee: `resolveContained` returns a plain path and the executor opens that path, without descriptor-relative (`O_NOFOLLOW`/dirfd) opens, so a symlink swapped between canonicalization and open can redirect the operation outside the checked target. That residual risk stands; containment assures where the path pointed when checked, not where it points when used.

Process environment construction occurs after the local shell grant is acquired. With an absent or null `envPolicy`, the executor retains its local minimal base (`PATH`, `HOME`, `TMPDIR`, plus configured base entries); omission never selects full host inheritance. This differs from the pinned executor's absent-policy behavior, which uses only the request's explicit `env`. With an explicit policy, the executor snapshots the host environment plus configured base overrides: `inherit: "all"` selects all candidates, `"core"` selects only the pinned platform core names, and `"none"` selects no inherited entries. The pure builder reads no host environment and never mutates its candidate or overlay maps.

The inherited selection always removes names matching the local `TOKEN|SECRET|PASSWORD|PASSWD|API_KEY|APIKEY|PRIVATE_KEY|CREDENTIAL` filter and any supplied additional denylist. `ignoreDefaultExcludes` cannot disable that local protection. When false, it additionally applies the pinned `*KEY*`, `*SECRET*`, and `*TOKEN*` exclusions. Construction then applies custom `exclude` patterns, inserts `set`, applies a nonempty `includeOnly`, and finally overlays request `env`. Patterns are case-insensitive with only `*` and `?` special; separators and bracket characters are literal. Core-name selection and Windows key collisions are ASCII-case-insensitive; Windows later entries replace earlier case variants, while Unix preserves case-distinct keys. Caller-supplied `set` and `env` values remain explicit caller data, not inherited host secrets.

The pinned [`protocol/src/shell_environment.rs`](https://github.com/openai/codex/blob/939f5decb26456169c42bec12aac88dcdedc4b9a/codex-rs/protocol/src/shell_environment.rs) defines the core-name lists and filtering order. Its non-inheritable launch context is removed case-insensitively after all overlays: `CODEX_EXEC_SERVER_NOISE_AUTH_TOKEN`, `NODE_REPL_AUTH_TOKEN`, `CODEX_GUARDIAN_DECISIONS_API_KEY`, `OPENAI_FEDERATION_RULE_ID`, `OPENAI_IDENTITY_TOKEN_FILE`, and `OPENAI_WORKLOAD_IDENTITY_CONTEXT`. The exact key `CODEX_EXEC_SERVER_EXIT_ON_STDIN_CLOSE` is also removed, matching pinned `exec-server/src/local_process.rs`. CCA does not synthesize thread or tool identity in the child environment.

Final environments are bounded to 256 entries and 64 KiB of combined UTF-8 key/value bytes; invalid individual environment entries are omitted, malformed policy shapes fail with `-32602`, and environment values never enter diagnostic errors. Full inheritance exposes host variables whose names survive these filters: name filtering is not secret-content detection. It does not grant additional filesystem or process permissions and never bypasses Permission or Guardrail checks. Argv remains bounded to 512 entries of 32 KiB with a nonempty program (Core `CcaPolicy.buildProcessEnv` / `assertArgv`).

Local caps bound every process: wall-clock timeout, a maximum number of live processes (64 unless configured otherwise), retained output bytes, and per-read bytes are enforced executor-side regardless of harness fields, which define no timeout upstream. Retained output and process handles live with their session: they survive a dropped connection for the 30 s detach window and die when the session expires or the host stops.

Nothing replays. A dropped socket or an uncertain registry registration ends the attempt; a failed `/validate` drops only its stream. A session resumes only on an explicit `resumeSessionId`, and no RPC operation whose outcome is unknown is retried. The service host's next attempt reuses the stored Flora enrollment, `executor_id`, Noise identity, and registry registration. An uncertain Flora enrollment is never repeated, so the host never creates a second Flora device.

Secrets never reach logs, telemetry, status output, or error messages: access tokens, the signed `wss` URL, `executor_registration_id`, Noise private material, handshake authorizations, and RPC payloads are reported only as fixed categories or bounded identifiers already public to the caller.

Carrier processing upholds three ordering and resource invariants. Harness-key authorization completes before any handshake response is sent, and the carrier itself verifies that completion rather than trusting the handshake implementation to call back. Inbound frames for one stream are decrypted and delivered strictly in sequence (per-stream serialization); enqueue order never depends on cipher completion order. Queued, pending, and reassembling bytes are bounded per stream and in aggregate across all streams of a connection; overflow resets the offending stream.

## Decisions from Dots

A Dots action that needs a human decision is refused at once with the decision to make and the command that records it. Dots asks the user in chat, records the answer with `ycoding api`, and retries the identical action: an approval lets it run (once, or every time for `always`), a rejection keeps it refused. Each deferred Permission or Guardrail failure becomes one entry of `CcaAuthorizationDeniedError.pending: {kind: "permission" | "guardrail", sessionID, itemID?, action, resources, hardReview, state: "open" | "rejected" | "full", directories?}[]`; a deadline timeout sets `busy` with no item. When Permission defers with an open item, the Guardrail step still runs with `defer`: a Guardrail deferral adds its item, a Guardrail pass releases its reservation at once, and a Guardrail deny wins as a plain denial. So one refusal can list a permission item and a guardrail item, and after the user approves both once, the identical retry consumes each approval and runs in one round. A rejected or full permission item refuses before the Guardrail step. A plain denial (a deny rule, a stale scope) keeps the `-32001` "Permission denied" answer and opens no item.

A refused `process/start` completes without spawning, as a sandbox denial does: `process/output` (stderr, the refusal text and a newline), `process/exited` (`exitCode: 1`, `sandboxDenied: false`), and `process/closed`, with the same read, write, signal, and terminate answers. A refused `fs/*` or `http/request` answers `-32600` with the message `Permission denied: <text>`, untruncated. The texts are exact:

- `open` (a rejected entry takes precedence and is shown alone, then a full one; with several open items, each item's `Review item` line comes before the `Ask` line, and each item's decide lines follow in the same order):

```
YCoding did not run this: it needs the user's decision.
Review item <itemID> in Session <sessionID>: <kind> <action> <resources joined by spaces>.
Ask the user in this chat, record the answer, then retry the identical action.
 approve once:   ycoding api session.review.decide --param sessionID=<sessionID> --param itemID=<itemID> -d '{"decision":{"kind":"<kind>","reply":"once"}}'
 approve always: ycoding api session.review.decide --param sessionID=<sessionID> --param itemID=<itemID> -d '{"decision":{"kind":"<kind>","reply":"always"}}'
 reject:         ycoding api session.review.decide --param sessionID=<sessionID> --param itemID=<itemID> -d '{"decision":{"kind":"<kind>","reply":"reject"}}'
```

  The `approve always` line appears for permission items, and for guardrail items only when the review carries directories: a guardrail "always" remembers just those outside-repository directories, and any other approved guardrail item is consumed once, like "once". A hard review never shows it.
- `rejected`: `YCoding did not run this: the user rejected review item <itemID>. Do not retry it.`
- `full`: `YCoding did not run this: the review box is full. Run ycoding decision list and decide or clear items first.`
- busy: `YCoding did not run this: YCoding is busy; retry the identical action.`

Every CCA child process runs with `YCODING_SESSION_ID=<its Session id>`; the executor sets it last, so a request `env` cannot replace it.

### Outside-roots reach

A Dots scope (its authorizer passes `defer`, exposed to the executor as `authorization.defers`) reaches every path the host user can, with approval as the gate. A path target outside the scope roots is resolved canonically (symlinks followed) instead of being refused outright, then needs `external_directory` on `<canonical directory>/*` with `{filepath, parentDir}` metadata before the operation's own `read`, `edit`, or `shell` authorization. Under `defer` that ask is refused at once with an item; an approval admits the directory for that one call, and "always" saves the `external_directory` rule as the Permission service does. A symlink inside the roots that points outside asks for its real target directory. Deny rules and the permission ceiling still deny first; YCoding's temporary-directory rule still turns an `external_directory` ask under a temporary directory into an allow; a request's managed sandbox profile keeps its upstream denials (a sandboxed start with an unreadable cwd is a sandbox denial, a restricted filesystem call answers `-32600` "Permission denied"). A missing outside target answers as a missing path. The task-proof runtime does not defer and keeps the hard refusal.

| Operation | Without `defer` (task proof) | Dots scope |
| --- | --- | --- |
| `fs/readFile`, `fs/writeFile`, `fs/getMetadata`, `fs/readDirectory`, `fs/canonicalize` | Outside the roots and the call's sandbox roots: `-32600` "Operation not permitted (os error 1)", or the sandbox denial when confined. Inside sandbox roots but outside the roots: `external_directory` | `external_directory` for every outside target |
| `fs/createDirectory` (executor) | Parent outside the roots: hard refusal; no `external_directory` | `external_directory` for the parent directory |
| Extended filesystem (`fs/open` with `readBlock`/`writeBlock`/`close`, `fs/walk`, `fs/remove`, `fs/copy`, extended `fs/createDirectory`) | Hard refusal outside the roots and sandbox roots; `external_directory` for each absolute resource inside sandbox roots but outside the roots | `external_directory` for each outside resource, source and destination alike |
| `process/start` cwd | Sandboxed: sandbox denial; unsandboxed: `-32600` hard refusal; inside sandbox roots: `external_directory` | `external_directory` for the cwd; a sandbox profile that cannot read it is a sandbox denial |
| Capability discovery read trees | As the `fs/*` reads | As the `fs/*` reads |
| Shell snapshot capture | No path target of its own; runs in the authorized process cwd | Same |
| apply_patch | No RPC of its own; upstream applies patches through `fs/*`, so the `fs/*` rows apply | Same |
| `process/read`, `process/write`, `process/signal`, `process/terminate`, `http/request` | No path target | Same |

## Stop in Dots

Stop in Dots sends nothing to the executor. Upstream `Op::Interrupt` keeps resumable unified-exec processes running, and ChatGPT.app 26.1023 sends only `turn/interrupt` to its app server. A running command therefore stops only through an explicit kill: `process/terminate`, the process timeout, or the connection or executor closing.

## Proof status journal

The task-proof script may be given `--status-file <absolute-new-file>` to preserve sanitized phase evidence when stdout is unavailable. The parent directory must already exist; the file is created exclusively with mode `0600`, existing files and symlinks are never overwritten, and creation failure stops the script before credential resolution or external activity. Without the option, stdout remains the only proof output.

Each complete JSON Lines record contains only a sequence number, a closed-set phase and event, elapsed milliseconds, and bounded numeric channel/request/response/notification/bridge counts when applicable, plus the optional fixed RPC method, outcome and `resumeRequested` fields and the resource status and counts described below. The journal never copies stdout, proof preambles, RPC objects or payloads, wire, session or process identifiers, hashes, account or thread data, tokens, signed URLs, local paths, argv, environment, command output, credentials, personal data, arbitrary method names, or arbitrary error text.

RPC records use the phases `rpc-received`, `rpc-response`, and `rpc-notification`. `rpc-received` is `observed`. `rpc-response` and `rpc-notification` are `completed` only after the send returns and `failed` if the send fails. Each carries a method from a fixed allowlist or `other`; the allowlist is the implemented methods plus the capability-discovery names `capabilities/discoverV2` and `capabilityRoots/discoverV1`, so an attempt at a missing method can be identified. Recognition in the journal adds no support for that method. The outcome is one of `result`, `invalid_request`, `method_not_found`, `invalid_params`, `internal_error`, `permission_denied`, `other_error`, `notification`, `send_failed`, or `aborted`. An `initialize` record adds the boolean `resumeRequested`, true when `resumeSessionId` is supplied non-null and non-undefined. The existing local request and channel counts are the only other RPC data.

Two further phases report process resources: `main-returned` is recorded after `main` resolves and the final summary log call, and a one-shot `process-before-exit` phase is recorded on `beforeExit`. Each carries `resourceStatus` `available` or `unavailable`. `available` adds aggregate counts of timers, sockets, pipes, processes, filesystem handles, and other handles. `unavailable` omits the counts. Under Bun the status is `unavailable` with no counts: Bun 1.4.4's API returned an empty list while a live timer and socket existed. The phases remain useful as markers, but the counts are not a live-handle measurement. Both phases occur only on natural successful return; explicit failure and abort exits do not emit `beforeExit`, so neither phase proves the process exited. An observer must still verify process exit and stdout and stderr EOF. Journal close can fail after the success summary is printed; the final exit 1 with the fixed error is authoritative. Records are written synchronously up to a fixed 64 KiB cap without truncating the complete prefix, so completed records remain readable after process termination. Overflow, write, observer, or close failure is sticky: no later record is written, including after an incomplete write tail, and sequence/byte accounting advances only for complete records. The failure does not reorder or mask cleanup; it surfaces after actual teardown as one fixed sanitized failure, preserving a genuinely nonzero primary failure while upgrading an otherwise exit-0 abort outcome.

A phase is marked completed only after the observed stage returns; a started phase without a terminal record remains closing or unfinished, never clean. The journal covers script start, preflight, state load, credential selection, identity creation, runtime startup, transport start/open, channel establishment, abort observation, transport close, bridge drain, handler close, executor close, authorization release, runtime graph close, and script completion. Handler close is the composite task-proof boundary; executor close wraps only the executor's own close inside that composition, before authorization release and runtime graph close. Post-open preflight and state-load failures use the same finalization path as later stages, recording their failed phase and a failed script completion before the journal closes. The journal is diagnostic evidence for an unlocated live timeout; it does not identify or fix that timeout and introduces no new deadline or wire behavior. The journal never forces a success exit, adds retries, or changes authorization or attachment. Failures stay visible as the fixed diagnostic failure, and the 64 KiB cap is never silently truncated. Because RPC records are written per message, high-volume traffic can exhaust the 64 KiB cap; overflow is reported as a failure and later lifecycle records may then be absent. The journal is a bounded diagnostic trial, not full traffic logging.

## Open unknowns

- Whether the harness ever sends a string `resumeSessionId` in practice. Absent and `null` decode as no resume request under the pinned `Option<String>` contract and initialize fresh; any string is rejected (`-32600` unknown session) and resumes nothing. Actual harness behavior is unknown.
- Whether the precedence of upstream deny and nested grant entries matches YCoding's rule (deny always wins, otherwise the most specific grant). The upstream filesystem-policy crate is not in the pinned sources; YCoding's rule is never less restrictive.
- Whether `traceparent` / `tracestate` frame fields must be echoed, propagated into local telemetry, or are safe to accept and drop. The contract accepts and drops them.
- Which additional upstream methods the harness requires in practice. Each addition needs its own local authorization, containment, and caps before leaving the `-32601` set.
