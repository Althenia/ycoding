# Process-global Chrome browser contract

## Paired profile access

Pairing automatically exposes eligible existing and future Chrome tabs, including the active tab, to the paired backend identity and permits Session-owned tab creation. The worker sends authenticated `profile_access enabled:true` before any profile-tab metadata on pairing and reconnect; Core ignores profile-tab frames without that state and removes profile projections on revocation. Profile tab IDs and observations are new after reconnect. Every active Session can use the process-global paired profile through the authenticated API, subject to model-tool per-site permissions. Forget pairing removes access and durable trust.

Chrome's native debugger banner identifies **YCoding** while attached and its **Cancel** detaches the tab. Native Cancel blocks that tab from profile rediscovery for the current pairing, including worker restart, until pairing is forgotten and renewed. It never induces an automatic reattach loop. The extension requests `tabs` for profile-wide tab URL/title metadata and `tabGroups` for group operations in addition to `alarms`, `debugger`, and `storage`, with host access limited to loopback. It declares `history` and `downloads` only as optional permissions; the popup requests them during pair and reconnect clicks, and history search or download waiting fails with a reconnect instruction when the user has not granted the relevant permission. No broad site-content host permission is requested.

The `group` and `ungroup` semantic actions require one profile source tab and a fresh observation fence. The request names one to eight distinct paired member tab IDs; group also supplies a bounded title, and ungroup supplies the group ID returned by group. Group creates a new Chrome tab group only for inactive, ungrouped members in the same window. Ungroup applies only to the exact unchanged membership of an extension-created group in the current connected pairing while all members are inactive. Grouping can reorder named member tabs, but no other tab is moved, activated, focused, or closed. Groups remain Chrome state after the bridge disconnects or pairing is forgotten; Chrome's UI can ungroup them when extension group ownership has ended. Model-tool profile lists, observations, captures, and scrolls require per-site `browser_read` permission but no standard profile-access review; profile navigate/click/type/group/ungroup require site permissions, `browser_control` for group changes, and hard `browser_profile_mutation` review. Hard reviews cannot be bypassed by any autonomy mode, custom allow rules, or reusable approvals.

## Agent-owned background tabs

The paired extension also accepts Session-owned tab creation. `browser.open` requires a current bridge generation, credential-free HTTP(S) URL, and original call ID. The worker creates `about:blank` with `active: false`, attaches the debugger only to the new tab, then navigates it to the approved origin. It never attaches an existing tab on this path. The returned `Tab` has `mode: "owned"` and retains its creating Session ID. `browser.list` exposes owned tabs only to that Session; observe, action, and close reject foreign Sessions. Moving, archiving, or deleting the owner Session revokes its owned grants: inactive owned tabs close, active user-controlled owned tabs remain open with the debugger detached, and paired profile tabs remain available to other Sessions. The model tool requires explicit `mode: "owned"` and filters personal profile tabs out of that mode. Omitted mode selects paired profile tabs.

Owned open needs per-site `browser_navigate` and `browser_read` permissions before dispatch; the standard guardrail profile has no owned-open review, and custom guardrail rules for `browser_owned_open` still apply. The model tool applies source-site and known destination-site permissions and `browser_mutation` guardrails for later owned semantic mutations. Close requires `browser_control`, source-site read approval, and `browser_mutation`; only agent-created inactive tabs can be closed, with the current bridge generation. Direct authenticated Session API requests use the existing user-authority boundary. Open calls are not automatically replayed: a reused call ID in one bridge is rejected, and a lost result requires tab-list reconciliation. Reconnect clears tabs, pending calls, and semantic references; the worker closes inactive owned tabs on disconnect, stop, and debugger detach, leaving a currently active user-controlled tab open and detached. Active owned tabs remain available for observation and semantic action, but not close or automatic cleanup. Site navigation outside approved origins revokes its grant before destination metadata is returned.

## Ownership and pairing

- `Browser.Service` and mode admission have process-global coordinators. Each caller must be an active Session; one paired extension exposes eligible profile tabs to all active Sessions on the backend, including other Locations. Caller-owned tabs remain Session-private. Tab read models carry the requesting Session ID plus bridge and document generations. Tool permissions and guardrails apply separately to every caller.
- Pairing creation requires the normal authenticated HTTP and Session-location path. It returns a random one-time secret that expires after two minutes. Core retains only its SHA-256 digest, consumes it after one successful connection, and limits rejected attempts.
- Successful bootstrap issues one durable random reconnect credential to the extension installation. Core persists only its SHA-256 digest through the existing credential store, with binding metadata for the extension ID, a durable random server identity, and the initiating Session as provenance. Reconnect and revocation do not require that Session. No database schema change is required. Location-specific credentials do not authorize the backend-wide bridge; a fresh pairing is required.
- `Browser.Status.paired` is true while that durable trust credential exists, including when the extension is disconnected or the bridge is unavailable. A disconnected paired status is distinct from an unpaired status; the Mini and full TUI show that it is waiting to reconnect and do not offer implicit re-pairing. The user explicitly forgets trust before creating a replacement pairing.
- The extension and Core use bridge protocol version 5. The first frame rejects pairing and reconnect attempts from any other version before consuming a one-time secret or accepting durable trust, so a worker without the control-marker, release, frame-session, and history/key/wait messages cannot report a connected bridge. A missing, invalid, or late first handshake closes with a transient non-4403 code; 4403 is reserved for actual authentication rejection so transient failures cannot erase extension trust.
- The connect URL contains no credential. The Server accepts only the exact secret-free WebSocket path, validates an exact `chrome-extension://<extension-id>` Origin, and requires the same extension ID plus either the one-time secret or the durable credential and server identity in the first bounded frame before attaching the transport. Origin or extension ID alone never authenticates.
- A successful durable authentication creates a new empty process-local bridge generation. Chrome startup and extension-worker restoration reconnect from saved local credentials, and the extension's recovery alarm retries after unexpected worker termination. YCoding service restarts retain deterministic local service ports and the extension retries without a new code. Restart recovery does not restore debugger attachments, observations, pending calls, settlements, or actions. Paired Chrome reenumerates eligible tabs with fresh IDs after reconnect. The extension uses alarm-backed exponential reconnect from one to 30 seconds to the backend without a Session ID. Moving, archiving, or deleting the initiating Session does not disconnect the bridge or revoke trust; any in-flight mutation from that Session becomes uncertain.
- Creating pairing for another explicit Session revokes the previous backend trust and disconnects its bridge before issuing the new secret. Stop detaches tabs and disables automatic reconnect without deleting trust; reconnect requires the popup's explicit **Reconnect** action. Forget removes server trust and local credential state; unknown and revoked credentials fail closed.
- A replacement bridge cannot displace a connected owner. Stop revokes the shared bridge and attachments for all Sessions; forget may use any active Session to revoke the credential.

## Profile tab control

- A profile tab has at most one holder Session. Core records the holder on the tab in the process-global bridge; `Browser.Tab.lease` is `self` for the caller's tab, `other` for a tab another Session holds, and absent for a free tab or an owned tab. The projection never carries the other Session's identity.
- Observe and every action claim the tab at dispatch, atomically with the bridge's single pending command; `group` and `ungroup` claim every named member or none. A Session that is not the holder receives an ownership error before any permission request, dispatch, or retained settlement, while `status` and `tabs` continue to answer. A command that fails before dispatch, or an action the extension rejects before dispatch, releases only the claim that command made, and the extension detaches and clears the marker on a tab that command attached, so a released claim never leaves an attached or marked tab without a holder. A failure after dispatch keeps the holder.
- `browser.release` (`POST /api/session/:sessionID/browser/release`, `{ tabID, generation, callID }`) succeeds without a frame for a free tab, fails with an ownership error for a tab another Session holds and a fence error for a stale generation, and otherwise sends `relinquish { callID, tabID, generation }` as the bridge's single pending command. The holder is cleared, and the tab's observation fence reset, only after the extension answers `relinquished` with the same identity. A timeout or extension error leaves the holder, and the tab stays held and possibly marked, until a retry is acknowledged, the Session's next execution end retries the release, or the bridge stops, forgets, or disconnects. An acknowledgement for a tab that is already revoked settles the release.
- Session execution ending (`session.execution.succeeded`, `failed`, or `interrupted`) and Session move, archive, or delete release that Session's profile tabs by the same acknowledged path. The release waits for the bridge's pending command to settle, including an uncertain mutation, and never clears a holder while its physical action can still settle. Execution ending does not close or revoke agent-owned tabs; owner lifecycle events keep their existing owned-tab rules.
- Bridge stop, forget, disconnect, service shutdown, and profile revocation remove the tabs and therefore every holder. There is no override that moves control between Sessions.
- The lease covers the `browser` tool and Session API over paired Chrome. The `computer` tool's `webbrowser.*` Apple Events actions address Chrome by window and tab index outside this bridge and are not fenced by it.

## Deferred permission identity

Permission digests bind the tab, operation, submitted payload, and semantic target independently of connection generation, document generation, observation revision, and semantic ref. Every action, including capture, scroll, and group changes, binds a private full-page URL digest independently of semantic elements. Query-only and fragment-only page changes alter that identity. Fresh observations must supply current fences and a target whose role, name, description, page, and exact destination still match the approved identity. Raw observed URL query and fragment values and private page hashes remain absent from public tabs, observations, and durable review payloads. A changed target or payload cannot consume the approval. Indistinguishable semantic targets cannot consume a deferred once grant; configured Allow and matching saved Always policies still authorize their distinct current refs. An unchanged, unambiguous action can consume its approval after execution-end release and a fresh observation, even when the ref or observation revision changes.

## Control marker

- Before an observe or action is dispatched, the extension shows the fixed title prefix `Ⓨ ` (U+24CE and one space) on the tab, reads it back, and rejects the operation with `dispatched: false` when it cannot; a tab it attached for that operation is detached again. Group and ungroup mark and confirm every member before the group changes. Owned open marks the new tab before reporting it open.
- The prefix preserves the page's own title, including later changes, and cleanup restores the last page-authored title and removes a title element only when the marker created it and the page never authored one. Titles reported to Core exclude an installed prefix and never other text.
- A pinned tab is refused because the tab strip shows only its icon.
- Explicit release, stop, forget, disconnect, and revocation clear the marker with a bounded wait before detaching. Without a command path (native Cancel, worker loss or reload, crash) the page removes the marker when its 15-second deadline, refreshed every 5 seconds while control lasts, passes; it also checks on visibility and resume events. The deadline is held in the page, so a page frozen and thawed after expiry cleans up on thaw.
- Marker commands for one tab run in order. Cleanup waits, up to its bound, for a marker command already sent, and a marker command that has not been sent when cleanup starts is dropped, so a late refresh cannot repaint a cleared marker or restart the refresh timer.
- When the page removes the marker element, the page restores the title only if it still holds the marker's own text; a title the website authored, including one that starts with the marker prefix, is kept.
- The extension keeps one isolated-world context per document because `Page.createIsolatedWorld` creates a new world on every call.
- The cursor label is the YCoding mark followed by one of `Click`, `Type`, `Scroll`; the cursor tip lands on the coordinates of the dispatched action and reduced-motion preferences remove its animation. Visual rules are in `extensions/chrome/DESIGN.md`.

## Profile and non-interruption boundary

The unpacked Manifest V3 extension, shipped beside release executables as `ycoding-chrome-extension`, has a fixed ID from its manifest public key and requests `alarms`, `debugger`, `storage`, `tabs`, and `tabGroups`, declares optional `history` and `downloads`, and keeps loopback host access only for its YCoding connection. It attaches eligible profile tabs after pairing. Restricted Chrome pages and debugger-policy failures remain unavailable; there is no fallback to profile copying, a remote-debugging port, host UI automation, or arbitrary CDP.

The extension never activates, focuses, or closes the user's existing tab or window and never injects host-global keyboard, pointer, or clipboard input. Explicit profile group actions may rearrange only named granted inactive tabs inside one window. Active profile and owned tabs remain controllable for observation and semantic action; foreground-sensitive owned close and group operations remain restricted to inactive tabs. Explicit requested pauses, uncertain mutations, and bridge disconnects still block operations.

Profile navigate, click, and type use the tab-scoped debugger after model-tool source-site and known destination-site approval. A site-action approval explicitly includes the risk of an incidental download: Chrome permits `Fetch` interception and `Target` auto-attach through `chrome.debugger`, but neither can stop every page-script or client-generated download before it starts. User Chrome rejects deprecated `Page.setDownloadBehavior` with CDP error `-32000`; its `Browser.setDownloadBehavior` replacement is in the browser-wide `Browser` domain excluded from `chrome.debugger`. There is no claim of a pre-download guard. The extension rejects explicit download links as click targets. The typed download action only waits for and reports a download already caused by page behavior; the typed upload action sets files directly on a file input after Core verifies each model-supplied absolute path exists and is a regular file, without opening a file chooser. Full-CDP and arbitrary-JavaScript tools are not part of this contract.

Routine observations are bounded accessibility-tree projections. They omit input values (including text rendered inside editable controls), raw DOM, query strings, fragments, credentials, cookies, storage, and screenshots. Explicit capture rejects pages containing password inputs in any frame, inspecting out-of-process iframes through their own debugger sessions, and returns at most 1 MiB of PNG data. File inputs outside the typed upload action, password inputs, explicit download links, popups, external protocols, credential-bearing URLs, and unapproved origins fail closed.

## Actions and settlement

Observe requires an active caller Session, shared tab, bridge generation, and call ID. An observation returns document generation and observation revision plus at most 200 semantic elements, at most 100 readable text entries (headings, static text, and table cells outside editable controls), and at most 32 child-frame completeness entries. The extension auto-attaches iframe targets as flat debugger sessions and merges each permitted frame's accessibility tree (depth at most 32) into one observation; an element or text entry from a child frame carries that frame's page. A child frame whose origin is not yet approved, or whose tree cannot be read, contributes no content and appears in the frame list with `observed: false`. Core accumulates frame origins from observation metadata and supplies them on later observe and action commands; the model tool asserts `browser_read` for each child-frame site before exposing its content and re-observes once after approval, and asserts `browser_read` plus `browser_interact` for the frame site before click or type on a framed element. A subframe navigation invalidates only that frame's semantic references; a top-level navigation invalidates every reference and frame session.

Every action requires the same caller Session identity, original call ID, bridge generation, document generation, and observation revision. Click and type additionally require a current semantic element reference. Every debugger attachment enables Chrome focus emulation before the tab is usable. Click and scroll use CDP mouse input in background tabs and in unfocused or minimized windows without activating or focusing the tab or window. While attached, the controlled page reports `document.visibilityState === "visible"` and is not background-throttled; detaching ends focus emulation. Core permits only navigate, click, type, scroll, explicit capture, back, forward, reload, key (named keys and single characters with Alt/Control/Meta/Shift modifiers), wait (document load or a current reference, bounded to 30 seconds), clipboard read/write, upload, download waiting, log reading, MHTML export, and WebMCP list/invoke; neither the public API nor model tool accepts arbitrary JavaScript or CDP commands. Back and forward stay within origins approved for the current action; a history entry on another origin is rejected before dispatch. Click dispatches mouse input on the main session at main-viewport coordinates derived from the child frame's element quad and its iframe owner quad; type focuses and inserts text on the element's own frame session. Peripheral actions use the same fences: `clipboard_read` first passes the capture password inspection and returns at most 64 KiB of text, `clipboard_write` writes at most 64 KiB, `upload` accepts one to eight Core-validated regular files for a current file-input reference, `download` waits at most 30 seconds for the latest Chrome download to complete, `logs` returns at most 100 bounded console or exception entries captured per controlled tab (child-frame entries carry their frame page and the buffer clears on top-level navigation or release), `export` transfers at most 8 MiB of MHTML for Core to save under the global data directory's `browser-exports` folder and returns only its path and byte count, and `webmcp_list`/`webmcp_invoke` use only a page's native `document.modelContext` or `navigator.modelContext` without injecting a shim, failing when it or the named tool is absent; invoke re-lists tools under the current fence before dispatch. History is a separate bridge-generation-fenced operation, not a per-observation action: it accepts a bounded query, limit, and optional time range, filters credential-bearing or non-HTTP(S) URLs, and returns at most 100 entries. Google Docs/GSuite-specific export by URL rewriting is excluded because it depends on proprietary Google endpoints and the user's Google credentials.

Only one command may be unsettled per bridge. Retained action settlements are keyed by caller Session and call ID. Internal error frames require an explicit `dispatched` boolean. A pre-dispatch rejection reports `false`, so Core retains a `rejected` settlement without introducing mutation uncertainty. A mutation failure after dispatch, timeout, or disconnect without a known terminal result remains `uncertain` and pauses the tab. An exact retry returns the retained settlement; reuse of that call ID with different fences or action input is rejected. Neither settlement permits automatic replay. Resume is explicit and invalidates prior semantic references. A disconnect marks retained tab projections unavailable and clears their observations. An unexpected top-level origin revokes sharing before its metadata is forwarded; the destination may already have received navigation.

## Public operations and generated clients

The Session-location Protocol group exposes status (including the durable-pairing and profile-grant indicators), tabs (with explicit profile mode and lease projection), start, open, close, release, observe, action (including group/ungroup), control, stop, and forget under `/api/session/:sessionID/browser`. The extension-only WebSocket endpoint is `GET /api/browser/connect` and authenticates by exact extension Origin and first-frame credential, without a Session path parameter. Forget uses `DELETE /api/session/:sessionID/browser/pairing`. Normal HTTP operations retain existing server authentication. Schema owns all bounded wire shapes, and generated Promise and Effect clients follow the assembled `HttpApi`; generated files are never edited directly.

The built-in `browser` model tool omits start/pairing controls. Omitted mode and explicit `mode: "profile"` select paired Chrome tabs; explicit `mode: "owned"` and `mode: "isolated"` retain their separate ownership boundaries. It applies `browser_read`, `browser_navigate`, `browser_interact`, or `browser_control` permission checks at the leaf. Profile actions check the source site and any known destination site before dispatch; permission requests warn that site actions may cause incidental downloads. Profile read/list/capture/scroll/wait/clipboard-read/logs/download/export/WebMCP-list use read permissions (history uses a non-site `browser_read` request) without standard access review, while profile mutations including group/ungroup, back, forward, reload, key, clipboard write, upload, and WebMCP invoke reserve hard `browser_profile_mutation`. Authenticated direct user Session API actions are not model-tool permission grants.

## Validation boundary

Automated Schema, Core, Protocol, Server, tool, extension-protocol, and service-worker boundary tests cover the typed bounds, single-use pairing, durable server-restart authentication, extension identity, backend-wide reconnect independent of initiating Session, explicit switching, revocation, unknown/revoked fail-closed behavior, reconnect backoff, worker restart without tab or action replay, safe URL projection, stale fences, one-writer behavior, uncertain-mutation deduplication, permission/guardrail ordering, route shape, approved navigate/click/type, static cross-site denial before dispatch, and unexpected-origin revocation without metadata exposure. JavaScript parse checks cover extension entrypoints.

Core and model-tool tests cover authenticated profile-frame ordering, default profile tab filtering, site permissions before tab metadata release, guardrail evaluation before profile mutations, and active-tab observe/action while explicit pauses still block control. The disposable Chrome for Testing suite `packages/server/test-integration/browser-owned-chrome.test.ts` verifies the tab-title marker, strict CSP and Trusted Types pages, dynamic titles, release, transfer, pinned refusal, navigation, isolated-world reuse, stop, and expiry after worker loss on visible, hidden, and frozen pages, plus a cross-origin out-of-process iframe whose elements and text are observed after frame approval, whose button and input accept click and type, and whose capture succeeds without password fields and fails closed with one inside the child frame. Chrome-worker checks must separately verify enumeration, restricted pages, inactive group/close safety, and native Cancel behavior; headless Chrome does not render tab-strip pixels or the debugger infobar. Incidental page-triggered downloads remain possible; download prevention must not be claimed.

The separate [isolated-browser contract](./isolated-browser.md) uses temporary headless state without personal logins. Its Session API, generated clients, model-tool mode, and TUI lifecycle controls are implemented, with full production acceptance pending. It does not replace extension pairing semantics. The two modes share exclusive Session admission; a conflicting start or reconnect cannot replace the active mode or revoke extension trust.
