# Process-global Chrome browser contract

## Paired profile access

Pairing automatically exposes eligible existing and future Chrome tabs, including the active tab, to the paired backend identity and permits Session-owned tab creation. The worker sends authenticated `profile_access enabled:true` before any profile-tab metadata on pairing and reconnect; Core ignores profile-tab frames without that state and removes profile projections on revocation. Profile tab IDs and observations are new after reconnect. Every active Session can use the process-global paired profile through the authenticated API, subject to model-tool per-site permissions. Forget pairing removes access and durable trust.

Chrome's native debugger banner identifies **YCoding** while attached and its **Cancel** detaches the tab. Native Cancel blocks that tab from profile rediscovery for the current pairing, including worker restart, until pairing is forgotten and renewed. It never induces an automatic reattach loop. The extension requests `tabs` for profile-wide tab URL/title metadata and `tabGroups` for group operations in addition to `alarms`, `debugger`, and `storage`, with host access limited to loopback. No broad site-content host permission is requested.

The `group` and `ungroup` semantic actions require one profile source tab and a fresh observation fence. The request names one to eight distinct paired member tab IDs; group also supplies a bounded title, and ungroup supplies the group ID returned by group. Group creates a new Chrome tab group only for inactive, ungrouped members in the same window. Ungroup applies only to the exact unchanged membership of an extension-created group in the current connected pairing while all members are inactive. Grouping can reorder named member tabs, but no other tab is moved, activated, focused, or closed. Groups remain Chrome state after the bridge disconnects or pairing is forgotten; Chrome's UI can ungroup them when extension group ownership has ended. Model-tool profile lists, observations, captures, and scrolls require per-site `browser_read` permission but no standard profile-access review; profile navigate/click/type/group/ungroup require site permissions, `browser_control` for group changes, and hard `browser_profile_mutation` review. Hard reviews cannot be bypassed by YOLO 3, custom allow rules, or reusable approvals.

## Agent-owned background tabs

The paired extension also accepts Session-owned tab creation. `browser.open` requires a current bridge generation, credential-free HTTP(S) URL, and original call ID. The worker creates `about:blank` with `active: false`, attaches the debugger only to the new tab, then navigates it to the approved origin. It never attaches an existing tab on this path. The returned `Tab` has `mode: "owned"` and retains its creating Session ID. `browser.list` exposes owned tabs only to that Session; observe, action, and close reject foreign Sessions. Moving, archiving, or deleting the owner Session revokes its owned grants: inactive owned tabs close, active user-controlled owned tabs remain open with the debugger detached, and paired profile tabs remain available to other Sessions. The model tool requires explicit `mode: "owned"` and filters personal profile tabs out of that mode. Omitted mode selects paired profile tabs.

Owned open needs per-site `browser_navigate` and `browser_read` permissions before dispatch; the standard guardrail profile has no owned-open review, and custom guardrail rules for `browser_owned_open` still apply. The model tool applies source-site and known destination-site permissions and `browser_mutation` guardrails for later owned semantic mutations. Close requires `browser_control`, source-site read approval, and `browser_mutation`; only agent-created inactive tabs can be closed, with the current bridge generation. Direct authenticated Session API requests use the existing user-authority boundary. Open calls are not automatically replayed: a reused call ID in one bridge is rejected, and a lost result requires tab-list reconciliation. Reconnect clears tabs, pending calls, and semantic references; the worker closes inactive owned tabs on disconnect, stop, and debugger detach, leaving a currently active user-controlled tab open and detached. Active owned tabs remain available for observation and semantic action, but not close or automatic cleanup. Site navigation outside approved origins revokes its grant before destination metadata is returned.

## Ownership and pairing

- `Browser.Service` and mode admission have process-global coordinators. Each caller must be an active Session; one paired extension exposes eligible profile tabs to all active Sessions on the backend, including other Locations. Caller-owned tabs remain Session-private. Tab read models carry the requesting Session ID plus bridge and document generations. Tool permissions and guardrails apply separately to every caller.
- Pairing creation requires the normal authenticated HTTP and Session-location path. It returns a random one-time secret that expires after two minutes. Core retains only its SHA-256 digest, consumes it after one successful connection, and limits rejected attempts.
- Successful bootstrap issues one durable random reconnect credential to the extension installation. Core persists only its SHA-256 digest through the existing credential store, with binding metadata for the extension ID, a durable random server identity, and the initiating Session as provenance. Reconnect and revocation do not require that Session. No database schema change is required. Location-specific credentials do not authorize the backend-wide bridge; a fresh pairing is required.
- `Browser.Status.paired` is true while that durable trust credential exists, including when the extension is disconnected or the bridge is unavailable. A disconnected paired status is distinct from an unpaired status; the Mini and full TUI show that it is waiting to reconnect and do not offer implicit re-pairing. The user explicitly forgets trust before creating a replacement pairing.
- The extension and Core use bridge protocol version 3. The first frame rejects version-2 pairing and reconnect attempts before consuming a one-time secret or accepting durable trust, so a worker without profile-access grant announcements cannot report a connected bridge. A missing, invalid, or late first handshake closes with a transient non-4403 code; 4403 is reserved for actual authentication rejection so transient failures cannot erase extension trust.
- The connect URL contains no credential. The Server accepts only the exact secret-free WebSocket path, validates an exact `chrome-extension://<extension-id>` Origin, and requires the same extension ID plus either the one-time secret or the durable credential and server identity in the first bounded frame before attaching the transport. Origin or extension ID alone never authenticates.
- A successful durable authentication creates a new empty process-local bridge generation. Chrome startup and extension-worker restoration reconnect from saved local credentials, and the extension's recovery alarm retries after unexpected worker termination. YCoding service restarts retain deterministic local service ports and the extension retries without a new code. Restart recovery does not restore debugger attachments, observations, pending calls, settlements, or actions. Paired Chrome reenumerates eligible tabs with fresh IDs after reconnect. The extension uses alarm-backed exponential reconnect from one to 30 seconds to the backend without a Session ID. Moving, archiving, or deleting the initiating Session does not disconnect the bridge or revoke trust; any in-flight mutation from that Session becomes uncertain.
- Creating pairing for another explicit Session revokes the previous backend trust and disconnects its bridge before issuing the new secret. Stop detaches tabs and disables automatic reconnect without deleting trust; reconnect requires the popup's explicit **Reconnect** action. Forget removes server trust and local credential state; unknown and revoked credentials fail closed.
- A replacement bridge cannot displace a connected owner. Stop revokes the shared bridge and attachments for all Sessions; forget may use any active Session to revoke the credential.

## Profile and non-interruption boundary

The unpacked Manifest V3 extension, shipped beside release executables as `ycoding-chrome-extension`, has a fixed ID from its manifest public key and requests `alarms`, `debugger`, `storage`, `tabs`, and `tabGroups`, with loopback host access only for its YCoding connection. It attaches eligible profile tabs after pairing. Restricted Chrome pages and debugger-policy failures remain unavailable; there is no fallback to profile copying, a remote-debugging port, host UI automation, or arbitrary CDP.

The extension never activates, focuses, or closes the user's existing tab or window and never injects host-global keyboard, pointer, or clipboard input. Explicit profile group actions may rearrange only named granted inactive tabs inside one window. Active profile and owned tabs remain controllable for observation and semantic action; foreground-sensitive owned close and group operations remain restricted to inactive tabs. Explicit requested pauses, uncertain mutations, and bridge disconnects still block operations.

Profile navigate, click, and type use the tab-scoped debugger after model-tool source-site and known destination-site approval. A site-action approval explicitly includes the risk of an incidental download: Chrome permits `Fetch` interception and `Target` auto-attach through `chrome.debugger`, but neither can stop every page-script or client-generated download before it starts. User Chrome rejects deprecated `Page.setDownloadBehavior` with CDP error `-32000`; its `Browser.setDownloadBehavior` replacement is in the browser-wide `Browser` domain excluded from `chrome.debugger`. There is no claim of a pre-download guard. The extension rejects explicit download links and file inputs; download/upload/history/full-CDP tools are not part of this contract.

Routine observations are bounded accessibility-tree projections. They omit input values, raw DOM, query strings, fragments, credentials, cookies, storage, and screenshots. Explicit capture rejects pages containing password inputs and returns at most 1 MiB of PNG data. File inputs, password inputs, explicit download links, popups, external protocols, credential-bearing URLs, and unapproved origins fail closed.

## Actions and settlement

Observe requires an active caller Session, shared tab, bridge generation, and call ID. An observation returns document generation and observation revision plus at most 200 semantic elements.

Every action requires the same caller Session identity, original call ID, bridge generation, document generation, and observation revision. Click and type additionally require a current semantic element reference. Core permits only navigate, click, type, scroll, and explicit capture; neither the public API nor model tool accepts arbitrary JavaScript or CDP commands.

Only one command may be unsettled per bridge. Retained action settlements are keyed by caller Session and call ID. Internal error frames require an explicit `dispatched` boolean. A pre-dispatch rejection reports `false`, so Core retains a `rejected` settlement without introducing mutation uncertainty. A mutation failure after dispatch, timeout, or disconnect without a known terminal result remains `uncertain` and pauses the tab. An exact retry returns the retained settlement; reuse of that call ID with different fences or action input is rejected. Neither settlement permits automatic replay. Resume is explicit and invalidates prior semantic references. A disconnect marks retained tab projections unavailable and clears their observations. An unexpected top-level origin revokes sharing before its metadata is forwarded; the destination may already have received navigation.

## Public operations and generated clients

The Session-location Protocol group exposes status (including the durable-pairing and profile-grant indicators), tabs (with explicit profile mode), start, open, close, observe, action (including group/ungroup), control, stop, and forget under `/api/session/:sessionID/browser`. The extension-only WebSocket endpoint is `GET /api/browser/connect` and authenticates by exact extension Origin and first-frame credential, without a Session path parameter. Forget uses `DELETE /api/session/:sessionID/browser/pairing`. Normal HTTP operations retain existing server authentication. Schema owns all bounded wire shapes, and generated Promise and Effect clients follow the assembled `HttpApi`; generated files are never edited directly.

The built-in `browser` model tool omits start/pairing controls. Omitted mode and explicit `mode: "profile"` select paired Chrome tabs; explicit `mode: "owned"` and `mode: "isolated"` retain their separate ownership boundaries. It applies `browser_read`, `browser_navigate`, `browser_interact`, or `browser_control` permission checks at the leaf. Profile actions check the source site and any known destination site before dispatch; permission requests warn that site actions may cause incidental downloads. Profile read/list/capture/scroll use site read permissions without standard access review, while profile mutations including group/ungroup reserve hard `browser_profile_mutation`. Authenticated direct user Session API actions are not model-tool permission grants.

## Validation boundary

Automated Schema, Core, Protocol, Server, tool, extension-protocol, and service-worker boundary tests cover the typed bounds, single-use pairing, durable server-restart authentication, extension identity, backend-wide reconnect independent of initiating Session, explicit switching, revocation, unknown/revoked fail-closed behavior, reconnect backoff, worker restart without tab or action replay, safe URL projection, stale fences, one-writer behavior, uncertain-mutation deduplication, permission/guardrail ordering, route shape, approved navigate/click/type, static cross-site denial before dispatch, and unexpected-origin revocation without metadata exposure. JavaScript parse checks cover extension entrypoints.

Core and model-tool tests cover authenticated profile-frame ordering, default profile tab filtering, site permissions before tab metadata release, guardrail evaluation before profile mutations, and active-tab observe/action while explicit pauses still block control. Chrome-worker and disposable-browser integration checks must separately verify enumeration, restricted pages, debugger attachment, inactive group/close safety, and native Cancel behavior. Incidental page-triggered downloads remain possible; download prevention must not be claimed.

The separate [isolated-browser contract](./isolated-browser.md) uses temporary headless state without personal logins. Its Session API, generated clients, model-tool mode, and TUI lifecycle controls are implemented, with full production acceptance pending. It does not replace extension pairing semantics. The two modes share exclusive Session admission; a conflicting start or reconnect cannot replace the active mode or revoke extension trust.
