# Session Interaction

On macOS 14 or newer, the packaged `ycoding` or `ycoding-node` server mounts the signed native chooser and isolated Chrome approval when `YCoding Interaction.app/Contents/MacOS/ycoding-interaction` is executable beside the server binary. Starting with version 0.12.0, macOS release archives and the Desktop backend bundle ship this app beside the binary. For independent staging, run `bun packages/cli/script/build-interaction-macos.ts '/absolute/staging/path/YCoding Interaction.app'` with the YCoding release signing identity available to `codesign` and match the packaged server's architecture. The launcher verifies the app and its process against the pinned certificate and bundle ID `app.ycoding.interaction` before private native IPC. It accepts no runtime path or trust override.

The Chrome extension socket requires a server listener on `http://127.0.0.1:<port>` and a successful startup handshake with the signed macOS helper. Without either, the upgrade request returns `503 Service Unavailable`. The socket accepts only loopback peers. The extension popup starts enrollment by sending a random profile ID and a label of 1–64 UTF-16 code units. The server rejects labels with surrounding whitespace or any Unicode control or format character before asking for consent. The popup and the helper's consent panel both display the same eight-character match code derived from that profile ID, together with the label. Only an explicit Allow on the Mac enrolls the profile; Deny, closing the panel, helper loss, and expiry after 60 seconds refuse it, and the connection closes when no decision arrives within 75 seconds. One enrollment runs at a time. An allowed profile receives a random credential once; the server stores only its SHA-256 digest with the profile ID and label in `interaction-chrome-profiles.json` under the YCoding state directory, keeping at most 32 profiles. Later connections authenticate with the stored credential without a panel, and the extension retries while the service is unreachable. Forget authenticates with the credential and deletes the stored digest; the extension deletes its copy. Neither HTTP nor the browser relay can enroll a profile or read a credential.

A bound Session can request control of an exact Chrome tab or macOS window. The request is not a grant. Only an authenticated local platform adapter can attest to consent given in its own visible surface. Chrome owned and isolated requests include one credential-free HTTP or HTTPS URL; the adapter binds consent to the canonical URL before it opens a tab. Isolated control requires its own adapter registration and never uses an enrolled Chrome profile as a fallback.

Isolated Chrome's native confirmation authorizes launch only. Action confirmation and irreversible actions return `refused` with reason `unsupported`, without a pending offer or browser dispatch.

The backend verifies the Session, adapter, target, generation and observation revision before it dispatches typed input. Chrome reads, previews and actions apply browser policy to the verified top-level document. The adapter verifies the document origin and sends only the query-free pathname with the native observation. Explicit navigation must match the exact approved URL; it cannot widen a grant to another path. A successful navigation invalidates the previous action revision, and a redirect or an unverifiable document cannot expose content or accept input. One call identity can dispatch at most once in a grant. Actions with irreversible effects require a separate one-use native confirmation for the exact action and revision. Every consent offer handled by the macOS helper (a window attach, an action confirmation or an isolated Chrome launch) ends with a definite outcome. When the adapter offers no matching target, the server retries the inventory for about 1.5 seconds within the offer's lifetime and then rejects the offer; an offer whose consent is refused, declined or cancelled is rejected at once. A rejected attach request ends `stopped` with reason `rejected`. A rejected confirmation is withdrawn, so the next `perform` of that action returns `refused` with `confirmation_required` and a new confirmation can be requested. The server logs one warning per rejected offer with the driver, purpose, Session ID and a reason code. On macOS, the helper's confirmation is retried up to four times within the offer's lifetime while the helper reports the window as not yet readable or another authentication as in progress; the helper raises both refusals before its authentication prompt, so a retry never shows a second prompt. Platform permission, policy, sensitive inputs and CAPTCHA refusals still apply. An action with an uncertain outcome is not replayed and the grant is revoked.

Adapters act only in the background. They never activate an app, raise a window, switch Spaces, focus a tab or window, or take keyboard focus. Chrome itself can still raise its window when a page opens a new tab or window, and when a page in the selected tab of its window opens a JavaScript dialog (`alert`, `confirm` or `prompt`); the adapter requests neither. The raise happens as the dialog opens, before the paused result reaches the Session, and it also happens without any YCoding control of the tab. The adapter sends no focus, activation or emulation command; keeping the user's app in front would require answering or suppressing the page's dialog. The adapter never answers, dismisses or suppresses a page dialog and never changes site or OS permissions to avoid one. The action or run that opened the dialog returns `paused` with reason `dialog` on its first attempt, and the adapter refuses to resume its lease while the dialog stays open. A step that needs the user returns `paused` with one reason: `foreground_required`, `file_chooser`, `dialog`, `captcha`, `sensitive` or `user_takeover`, and the adapter reports the pause for its exact lease. A browser or computer action that needs focus pauses on its first attempt with its reason and waits for the user's Resume or Stop; the adapter never retries it with focus emulation or any other focus workaround. Status becomes `paused` with that reason and the target category. While paused, observation fails with `paused` and actions return `{ outcome: "paused", reason }` without an adapter call; preview and Stop behave as for an active grant. Pausing clears the action revision, so the next action needs a fresh observation. The adapter resumes its own lease after the user acts in its surface. `POST /api/session/:sessionID/interaction/resume` with the generation fence asks the adapter to resume and returns the current status; it fails with a conflict unless that generation is paused. A refused resume leaves the grant paused.

A Chrome grant also accepts Script and Code mode runs through the `interaction` tool only. A run carries `mode` (`script` or `code`), `source` (1–65536 characters) and an optional `timeoutMs` of 100–60000 (default 10000). It requires the owning Session's active grant at the current observation revision, consumes that revision like an action, and is never replayed; a paused grant returns `{ outcome: "paused", reason }` and an unsupported target or adapter (every macOS window) returns `refused` with `unsupported`, both without dispatch. An invalid request is refused with `policy` without consuming the revision. `script` runs an async function body once in a fresh isolated world of the granted tab's top frame; `code` runs with REPL semantics in one isolated world kept per lease, so bindings persist until navigation, Stop, revocation or the end of the lease. A JavaScript dialog or file chooser that opens on the granted tab during a run settles it `paused` with reason `dialog` or `file_chooser`, without logs, and pauses the grant. Neither world receives user gestures, activates or focuses a tab or window, or reaches another tab. Before user source runs, sensitive input values read as empty and `document.cookie`, `localStorage`, `sessionStorage` and `indexedDB` throw `SecurityError`. The result is `completed` (with a JSON `value` of at most 65536 serialized bytes, or `valueTruncated: true`), `error` (`name`, `message`, optional `stack`), `timeout`, `stopped`, `refused` or `paused`; the first four carry at most 200 console entries from the run's own world, then `logsTruncated: true`. Console text, errors and values pass through the shared redaction. Stop and revocation abort the run, terminate script execution and return the adapter's `stopped` result. A missing, malformed or failed adapter result revokes the grant as `uncertain`. After every run the adapter re-verifies the top-level document and revokes the grant when it no longer matches the approved URL, still returning the run result. Each run asks the `interaction`, `browser_read` and `browser_script` permissions for the granted origin and path and reserves the same browser mutation guardrail as an action. The `browser_script` permission ask carries only the run mode, the source's SHA-256 digest and a single-line source preview of at most 200 characters; the TUI, Web and Desktop permission prompts show the mode, that preview and the first 12 digest characters. Full script source, values and logs appear only in the calling Session's tool result: no HTTP operation, relay operation, live event, status, capture or preview carries them.

Each native consent offer carries the Session title as its label after control characters are replaced and runs of whitespace collapse, limited to 128 characters. An unreadable Session withdraws the request with reason `permission`.

A capture originates only from a user action in the adapter's surface for an active or paused lease. The frame must pass the preview image checks. The backend applies the shared text and URL redaction to the optional title and address, drops either one if it is still invalid, rechecks that the Session is bound and not archived, and admits one steer input to the lease's own Session: a single text line naming the target category, title and address, and the frame as an image attachment. Unknown, replaced, stopped and revoked leases admit nothing, and an archived Session also revokes the grant. No tool, HTTP operation or relay operation requests a capture.

Stop revokes the matching generation before adapter cleanup and cancels pending native consent for that generation. Cleanup can remain pending or fail; neither condition reopens the grant. Session movement, archive or deletion, adapter disconnection, target loss and expiry also revoke control.

The local HTTP surface exposes status, a pending request, preview, exact-generation revocation and exact-generation resume. The relay exposes only Session- and device-owned status, preview, Stop and Resume. Active status identifies the target category without revealing native labels or document addresses. Preview is a private PNG or JPEG of at most 960 × 720 pixels and 160 KiB decoded. The image header must match the declared dimensions. Preview is non-cacheable and withheld if capture overlaps a stale target or document transition; there is no whole-screen fallback. Each status transition or applied action emits one live `session.interaction.changed` event with only the Session ID and generation in its data. Clients re-read status on connection and after invalidation, and refresh a preview only while it is visible. The event, grants, consent and previews are not persisted or restored after backend restart. Semantic tool results use normal transcript settlement.
