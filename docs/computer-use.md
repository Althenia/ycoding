# Native computer use

YCoding exposes one platform-neutral `computer` tool. Core owns capability reporting, Session ownership, revision fencing, cancellation, permissions, and guardrails. The provider is an isolated native macOS helper; Windows and Linux report `unsupported`.

## Supported capabilities

| Platform | Application | Read operation                                                                                     | Mutation                                                                                                          |
| -------- | ----------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| macOS    | iTerm       | Inspect one explicit window, tab, and session identity                                             | Send text, optionally followed by a newline, to that exact session                                                |
| macOS    | Finder      | Inspect one canonical file path                                                                    | Move that file to one canonical destination directory                                                             |
| macOS    | Desktop     | List regular running apps and layer-0 windows; inspect an explicit window's bounded Accessibility tree; capture it as JPEG | Launch without activation; AX control actions or target-pid pointer, wheel, and keyboard events |
| macOS    | Safari and Google Chrome | List windows and tabs with titles, URLs, active tabs, and per-window revisions | Navigate, back, forward, reload, create/close a tab, or evaluate bounded JavaScript in one explicit tab |

`status` reports the current platform and its filtered capability list. Unsupported platforms report `unsupported` with no capabilities and reject an application operation before invoking a native helper.

`desktop.list` requires `platform: "macos"` and returns at most 64 regular applications (`bundle_id`, `pid`, `name`, `is_active`, `is_hidden`) with at most 32 layer-0 windows each (`window_id`, `title`, point-space `bounds`, `on_screen`). Off-Space or minimized windows usually have `on_screen: false`. It makes no Session window claim. `desktop.launch` accepts a bundle ID, reuses a running process or launches without activation or recent-items insertion, and returns its PID and windows. Its permission resource is `macos.bundle_id/<bundle_id>/launch`; list uses `macos.desktop/list`. `desktop.quit` takes the exact running bundle ID and PID and requests a graceful app quit through `NSRunningApplication.terminate`. It never force-kills; it waits up to ten seconds and returns `exited: true` or `false`. Save prompts and refusals belong to the app. Quit uses `macos.bundle_id/<bundle_id>/quit` permission and invalidates Session claims for that PID's windows. Only quit when asked.

Window targeting requires the exact bundle ID, PID, and Core Graphics window ID. The helper verifies the process and layer-0 window identity and bounds independently of Accessibility. The target need not be frontmost or on the current Space. When macOS omits an off-Space window from its AX list, the helper probes the application's remote AX identifiers, bounded to 2,000 identifiers and one second. AppKit creates remote AX element IDs lazily: a window not AX-accessed while visible can remain absent from the AX list and bounded probe. In that case `desktop.inspect` returns `accessible: false`, `elements: []`, and a revision hashed only from the Core Graphics bundle/PID/window identity, bounds, and title. Capture and coordinate click/drag/scroll remain available, while element-path operations fail `target_not_found`. An ambiguous AX match fails closed. When AX is available, inspect returns `accessible: true` and at most 400 AX elements breadth-first, to depth 12 and 64 children per level. Each element has a child-index `path`, role, label, optional window-local `frame`, advertised supported actions, enabled/focused flags, and a value of at most 200 characters. Secure-role values are not read or returned. Values contribute to the AX revision hash.

Off-Space Safari page headings, text, and links can be read and pressed through AX even when WebKit does not paint page content into its window capture. Off-Space Chrome tab-strip AX controls can also be pressed. Prefer AX elements on another Space: PID-targeted command shortcuts may be ignored, and non-frontmost application menus may expose disabled items even when their frontmost equivalents are enabled.

`desktop.capture` uses ScreenCaptureKit for the same window. For window bounds in points, scale is `min(1, 1280 / max(width, height))`; JPEG quality steps through 0.6, 0.45, 0.3, and 0.2 until the image fits 600 KB, or capture fails. The result includes pixel `width`, `height`, and `scale`. AX frames and pointer coordinates share this window-local image pixel space. The helper recomputes scale against current bounds on each call. Capture requires macOS 14 or later and the helper's Accessibility and Screen Recording grants.

### Electron debug bridge

For an off-Space Electron window, Core checks the exact PID's Electron framework and inspect fuse. It uses a renderer CDP endpoint only when its localhost listener belongs to that PID and a page target exactly matches the window bounds and title. Otherwise, when `EnableNodeCliInspectArguments` is on, Core sends SIGUSR1 to that PID, waits up to three seconds for a **new** PID-owned localhost inspector, and addresses only the BrowserWindow whose `getMediaSourceId()` is `window:<CG window ID>:0`. It captures with `webContents.capturePage` and sends content-local input through `webContents.sendInputEvent` or `insertText`. It always requests `require('inspector').close()` after the call and verifies the listener disappears; `inspector_close_failed` reports an unknown outcome if cleanup cannot be confirmed. The inspector is an unauthenticated localhost debug port for the duration of the call. Core never sends SIGUSR1 unless the fuse is on: without that handler, the signal may terminate the app. Current-Space Electron input stays native; an on-screen native capture uses the bridge only if native capture fails.

The bridge preserves the desktop image coordinate contract: it scales content to at most 1280 pixels on the window's longest dimension, pads nonzero window-chrome offsets from content bounds, and converts image pixels to content DIPs. Captures are capped at 600 KB. Bridge mutation `effect` compares bridge images before and after; its revision comes from native window inspection. An exact-window or PID ownership mismatch fails closed.

Inspector captures repaint the hidden page, then return once two captures agree, bounded to about 750 ms. An action's `effect` compares up to three such captures with the pre-action capture because hidden pages can apply input after throttled timers.

### Agent display

`desktop.stage` moves one explicitly targeted window onto a private agent display after verifying its exact inspected revision. It requires a movable Accessibility window element: a window macOS has never exposed through Accessibility, or a full-screen window, cannot be staged and fails `background_unavailable`. On the agent display, pixel input and capture reach Chromium, Electron, and WebKit windows that ignore them or do not paint on another Space. The helper saves the original point-space frame, moves the window to the display with its size clamped to fit, and returns a settled revision. `desktop.unstage` restores the saved frame without requiring another revision; it sets position, then size, then reapplies position if it differs by more than one point. If the window has closed, unstage returns `target_not_found` and Core clears its staged record. Unstage restores the frame on the main display's current Space, not the Space the window came from: macOS rejects moving another application's window between Spaces while System Integrity Protection is enabled.

The `computer` permission resource for both actions is `macos.bundle_id/<bundle_id>/stage`; guardrail review is skipped while deny rules still apply. Core keeps one display owner per Location while windows are staged. It restores a Session's staged windows on release and all staged windows on Location shutdown, then stops the owner when no windows remain. The owner also stops when Core exits or dies. The private display is part of the macOS display arrangement: the pointer can reach it, and macOS may place new windows there. The display uses a private macOS API. If the owner dies, macOS moves its windows to a remaining display.

`desktop.launch` with `remote_debugging: true` explicitly enables a renderer CDP route for an Electron app whose inspect fuse is off. It uses `macos.bundle_id/<bundle_id>/remote_debugging` permission and computer guardrail deny evaluation. If no PID-owned renderer endpoint already exists, the helper requests graceful quit, waits up to ten seconds, returns `quit_pending` if the app stays open, and never force-kills. It relaunches without activation using `--remote-debugging-port=0` and Core checks for a PID-owned renderer endpoint. This unauthenticated localhost CDP port remains open until the app quits. Ordinary launch does not enable it.

Desktop mutations require the latest exact inspected or captured revision for that Session and window. `desktop.click` uses AX Press with `element`, or accepts `x,y` with left/right button and single/double count, which always delivers pointer events at that pixel. `desktop.drag` uses `from_x,from_y,to_x,to_y`. `desktop.scroll` uses an AX scrollbar plus `direction` or pixel-space `x,y,delta_x,delta_y`; `desktop.type` replaces an AX text field/area value by `element` or inserts up to 4096 UTF-8 bytes at app focus by targeted Unicode keys. `desktop.key` accepts named navigation, editing, function keys F1–F12, or one printable character with optional command/shift/option/control/fn modifiers; Enter on an AX element without modifiers uses AX Confirm. Raw coordinate and PID-keyboard routes briefly shift AppKit key focus from the user's original process/window to the target window, deliver only target-PID events, and restore the original key focus even when event delivery fails. User keystrokes during this interval may reach the target. AX element routes do not shift focus. Neither route posts to the global HID/session tap, warps the hardware cursor, raises windows, or switches Spaces. If the original focus cannot be restored or the original process is not frontmost afterward, `focus_restore_failed` reports an unknown outcome and requires inspection before further mutation; if background routing cannot start, `background_unavailable` reports `not_started`. Every successful pointer or keyboard mutation reports `effect`: `changed` when the settled AX revision differs or, when it does not, when a 240-pixel window image taken before and after the action differs; `unchanged` when neither changed; `unverified` when the window has no AX tree and no window image can be taken. A blinking caret or animation can make an image differ, so `changed` reports an observed change, not proof of the intended one. Core runs desktop mutations for all Sessions one at a time so focus shifts never overlap. Pixel pointer events reach AppKit and SwiftUI windows on any Space and Chromium/Electron windows on the current Space; Chromium/Electron windows and some toolbar controls on another Space ignore them and report `unchanged`, while targeted keyboard input and AX element routes still reach them. For Electron applications, each inspect sets `AXManualAccessibility`, which lets the application build its web-content AX tree for later inspections. A capture that ScreenCaptureKit refuses fails `native_failure` with the macOS reason in its message. Clipboard access is not used. Desktop control uses Accessibility and process-bound input; iTerm, Finder, Safari, and Chrome use fixed Apple Event templates with model-provided values carried only as typed descriptors. Desktop operations request Accessibility, capture additionally requests Screen Recording, and iTerm/Finder request their Automation access. Missing grants cause a closed failure and macOS may prompt; allow the app in Privacy & Security before retrying. Automation answers arriving after the 30-second response limit fail the call.

## Safari and Chrome Apple Events

`webbrowser.tabs` accepts only `com.apple.Safari` and `com.google.Chrome`. It returns at most 16 windows per browser and the first 100 tabs of each window. Each window includes its Apple Event ID, browser window index, a revision, and tabs with 1-based index, title, URL, and active-tab state. Titles are capped at 200 UTF-8 bytes and URLs at 400 UTF-8 bytes. The per-window revision hashes the listed tabs' titles and URLs in order, the active-tab index, and the window's total tab count. `webbrowser.new_tab` appends a tab to the end of the window and returns its `tab_index`; it fails when the window already has 100 or more tabs.

Tab-targeted mutations name the browser bundle ID, window ID, 1-based tab index, and exact window revision returned by `webbrowser.tabs`; `webbrowser.new_tab` targets a window and revision without a tab index. Each mutation re-lists the window every 150 ms until two snapshots agree, bounded to about two seconds, and returns that settled revision for chaining; a page that is still loading after that bound can return a revision that later becomes stale. Operations are `webbrowser.navigate`, `webbrowser.back`, `webbrowser.forward`, `webbrowser.reload`, `webbrowser.new_tab`, `webbrowser.close_tab`, and `webbrowser.eval`. Navigation and optional new-tab URLs must be absolute HTTP or HTTPS URLs. Evaluation accepts JavaScript source up to 65,536 UTF-8 bytes and returns a string capped at 16,384 UTF-8 bytes with a `truncated` flag. JavaScript runs only through `webbrowser.eval`. `webbrowser.eval` and Safari's history/reload templates require the user-enabled “Allow JavaScript from Apple Events” setting. Browser control does not activate or raise the browser, change focus, or switch Spaces. Permission resources are scoped by bundle ID and operation, so users can deny evaluation separately. The `computer` guardrail skips ordinary review and still evaluates deny rules.

Browser requests use fixed Apple Event event classes, event IDs, object specifiers, and typed descriptors. Model-provided URLs and JavaScript source travel only as text descriptors; they are never compiled as AppleScript. Safari history navigation and reload use fixed JavaScript templates, while Chrome uses native history/reload commands. Navigation sets the selected tab URL; tab creation and closing use the browser's tab objects and standard make/close events. Browser Automation access is requested from the YCoding Computer Use app and must be allowed in Privacy & Security before retrying.

## Ownership and mutation safety

An inspect operation claims the exact target for the observing Session and returns a revision. A mutation must come from the same Session and include that exact revision. Another Session, a stale revision, a released Session, or an uncertain prior result requires a fresh inspect.

iTerm text uses the normal `computer` permission boundary and shell guardrail deny evaluation before native execution. Finder paths are canonicalized through the Location mutation boundary; external paths require external-directory permission, and a move uses file-mutation guardrail deny evaluation. Cancellation targets an active call owned by the same Session.

Every desktop operation requires `computer` permission before native dispatch; window resources include bundle ID, PID, and window ID. Computer calls (including desktop, iTerm shell, and Finder file mutation) skip guardrail review decisions, but guardrail deny decisions still block. Desktop mutations re-snapshot at 50 ms intervals until two consecutive revisions agree, bounded to approximately 750 ms, and return that settled revision for chaining actions without an intervening inspect. `effect` reports an AX revision difference or a bounded image difference when AX is unchanged; `changed` is not proof of the intended outcome, `unchanged` means neither observation changed, and `unverified` means neither can establish one. On `unchanged`, do not repeat the same action; inspect for an AX element route or report no effect. A stale revision requires reinspection; an uncertain mutating result invalidates the claim and requires inspection before further mutation.

If a mutating helper process settles ambiguously, YCoding reports an unknown outcome and invalidates the claim. It does not replay the mutation automatically.

Cancellation and Session release invalidate the claim immediately, but retain the active target lock until the native invocation settles. A late successful response cannot restore a cancelled claim or report that cancelled call as successful; another call must wait for settlement and inspect again.

## Helper discovery

Packaged macOS TUI and Node executables resolve `YCoding Computer Use.app` only as a sibling of the running executable. macOS release archives after v0.7.1 contain the executable, that ad-hoc signed app bundle (whose executable is `Contents/MacOS/ycoding-computer-use`), and the `ycoding-chrome-extension` folder. Releases v0.2.0 through v0.7.1 also contain a separate `ycoding-computer-helper` executable, and v0.7.1 contains the `ycoding-computer-helper.app` bundle with identifier `app.ycoding.computer-helper`. Installing a later release removes a sibling `ycoding-computer-helper` and `ycoding-computer-helper.app` and restores them if the installation fails. The curl installer verifies the checksum and exact archive entry set for each supported version before installation.

The app bundle displays as **YCoding Computer Use** with the YCoding icon in macOS privacy settings, which list an app bundle by its filename. Its installed filename and bundle identifier are `YCoding Computer Use.app` and `app.ycoding.computer-use`; the separate bare helper can appear under its executable name.

Source development is explicit and does not write beside the user's Bun executable or compile native code during runtime startup:

```sh
bun run build:computer-use
bun dev
```

On macOS, the first command compiles and ad-hoc signs the current source into the repository-ignored `packages/core/.cache/computer-use/YCoding Computer Use.app` bundle, replacing any previous build there. A source process running under Bun resolves that fixed development path. If it has not been built, computer operations fail as helper unavailable; YCoding does not compile it automatically. The build requires the macOS command-line developer tools and supports host `arm64` or `x64`.

Every computer operation uses an app-context invocation: Core writes a request file in a private temporary directory, launches the sibling `YCoding Computer Use.app` with LaunchServices, waits for its response file, and removes the directory. The app executable accepts request and response absolute file paths as arguments. Missing, invalid, cancelled, or timed-out response after a mutation has an uncertain outcome and requires reinspection. Release builds are ad-hoc signed, so macOS ties privacy grants to each release; after installing or updating, remove the existing **YCoding Computer Use** entries and allow the new ones. An archive downloaded with a web browser carries the `com.apple.quarantine` attribute; after extracting it, run `xattr -dr com.apple.quarantine <extracted-folder>` before starting `ycoding`. The curl installer and `ycoding update` download without that attribute. A source build is also ad-hoc signed unless `YCODING_MACOS_SIGNING_IDENTITY` names a code-signing identity in the build user's keychain; macOS ties an ad-hoc app's grants to that exact build. After an ad-hoc rebuild, turning the existing **YCoding Computer Use** entry off and on does not grant the new app; remove the entry with **−**, and the next operation adds it again for the user to allow.

## Packaging and installation

The ordinary Bun and Node CLI builds emit only complete artifacts. A macOS host can build their supported macOS architectures and matching signed app bundles. A non-macOS host explicitly reports that it is skipping macOS targets rather than creating Darwin artifacts without the required helper; an explicit unavailable Node target fails instead of succeeding without output. Release CI builds each Darwin target on a matching macOS runner and stages the main executable and app bundle.

For macOS releases from v0.7.1, the curl installer and `ycoding update` prepare the executable, the app bundle, and any version-specific `ycoding-computer-helper` in the install directory, preserve installed components, and restore them when a replacement fails. This is rollback-based recovery across renames, not a crash-atomic swap. If a restore rename also fails, the updater retains the only old backup, reports its exact path and destination, and exits unsuccessfully. Published macOS releases from v0.2.0 through v0.7.0 contain the executable and `ycoding-computer-helper`; explicit self-update rollback to a published pre-v0.2.0 release accepts its historical single-file archive and leaves any sibling helper unchanged. Linux archives through v0.7.1 contain only the main executable; later Linux archives add the `ycoding-chrome-extension` folder.
