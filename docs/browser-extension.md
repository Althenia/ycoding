# Chrome extension browser bridge

YCoding connects eligible existing and future Chrome tabs through one explicit pairing in the YCoding Manifest V3 extension. Release installs place it in `ycoding-chrome-extension` beside the `ycoding` executable, for example `~/.local/bin/ycoding-chrome-extension`; a source checkout uses `extensions/chrome`. The **Connect Chrome** dialog shows the folder for the running YCoding. Paired tabs retain their existing login state; agent-owned mode creates new background tabs. Neither mode copies cookies, profile files, passwords, or browser storage into YCoding.

## Security and non-interruption boundary

- Pairing is initiated from one Session. The authenticated YCoding API creates a random one-time secret that expires after two minutes and becomes invalid after one successful connection. The secret is sent only in the first WebSocket frame, never in a URL, log, tab projection, or model tool result.
- A successful one-time pairing issues a random durable reconnect credential to that extension installation. The extension stores the credential in `chrome.storage.local`; Core stores only its SHA-256 digest in the existing credential store. Trust is bound to the exact extension installation ID and a durable random server identity. The manifest's public `key` fixes that ID to `emlogajckgpjjigcbcbfbpbeencgghfb` wherever the extension folder is loaded from, so reloading or moving the folder keeps the pairing; the key is public and is not a credential. The initiating Session is recorded with the credential but is not required for reconnect or revocation; the process-global bridge serves every active Session. Origin and extension ID are checks, not credentials.
- The WebSocket endpoint accepts only an exact `chrome-extension://<extension-id>` Origin. Every connection's first frame must name that same extension ID and contain either the active one-time secret or the durable credential plus server identity. Ordinary websites, including pages served from localhost, cannot authenticate.
- An enabled pairing maintains a repeating Chrome recovery alarm at 30-second intervals and uses a separate alarm for connection retry backoff. The recovery alarm wakes the worker after unexpected termination and reauthenticates without reopening the popup or requesting another pairing code; Chrome may delay alarms and does not wake a sleeping device. A connected worker does not open a second bridge when the alarm fires. After Chrome, the worker, or the YCoding server restarts, eligible existing tabs are listed with fresh identities and attach only on their next approved operation. Agent-owned tabs must be newly opened. Restart never restores debugger attachments, semantic references, pending actions, or mutation settlements.
- The unpacked extension requests `alarms`, `debugger`, `storage`, `tabs`, and `tabGroups`, with host access only to loopback for its YCoding connection. `tabs` permits profile-wide tab URL/title metadata after pairing; `tabGroups` permits grouping and ungrouping paired inactive tabs. There is no blanket site-content host permission. The debugger attaches to an eligible existing tab only when an approved operation needs it, including if the tab is active; owned mode attaches only to newly created tabs and stays attached between steps. Chrome's native debugger infobar identifies **YCoding** while attached and offers **Cancel**; Chrome enforces the infobar and extensions cannot hide it. The per-tab toolbar badge says **ON** while attached and is clear when detached or never attached. Cancel revokes that tab and suppresses reattachment for the current pairing; a new pairing resets this denial.
- Pairing authorizes enumeration of eligible existing and future tabs. Enumeration skips restricted and credential-bearing URLs, exposes only query-free page projections through the authenticated Session API, and never eagerly attaches a debugger to every tab. An explicit stop disconnects and detaches tabs while retaining pairing for manual Retry; Forget revokes trust. Future eligible tabs join while the pairing is connected.
- If initial pairing cannot save its credential, establish recovery, or enumerate tabs, the worker requests trust revocation, clears its local pairing, and closes the bridge rather than reporting a connected profile with no grant.
- Agent-owned mode requires the same one-time pairing. A `mode: "owned"` open creates `about:blank` with `active: false`, attaches only that newly created tab, and navigates it to the approved HTTP(S) target. Only the creating Session may list, observe, act on, or explicitly close it. An owner Session's move, archive, or deletion revokes its owned tabs without disconnecting paired tabs: inactive owned tabs close, while active owned tabs stay open with the debugger detached. The same active-tab close boundary applies when the shared bridge stops or disconnects. No tab or semantic reference is restored after reconnect. An owned tab remains controllable while active, but explicit close waits until it is inactive.
- When the opened page fails the model's returned-page read permission check, YCoding attempts one owner-scoped close without exposing page metadata. If the tab became active or the close cannot be confirmed, the tool returns its opaque tab ID and asks the user to switch away and close it manually; it does not retry an uncertain close.
- YCoding never activates, focuses, or closes an existing user tab or window. An explicit group action may rearrange only its paired inactive tab members within one window; it never moves tabs outside the paired set. It never uses global mouse or keyboard injection, the host clipboard, Chrome notifications, explicit downloads or uploads, external protocols, arbitrary JavaScript evaluation, or arbitrary CDP commands. An approved site action may indirectly trigger a browser download.
- An active paired or owned tab remains available for approved observation and actions; YCoding never switches tabs, activates a window, or restores focus. An explicit bridge pause still blocks actions.
- The browser tool lists eligible paired tabs by default (`mode: "profile"` is equivalent). Model-driven list/observe/capture/scroll requires per-site read permission. Navigate/click/type require source-site and any known destination-site permissions before dispatch; group/ungroup also require browser-control permission. Browser tool calls are never guardrail-reviewed, while guardrail deny rules still block them. Group creates one new Chrome group of one to eight paired, ungrouped, inactive tabs in the same window and may set its title; ungroup reverses only a group created in the current connection and only while every member is inactive and unchanged. Neither operation closes tabs. Chrome groups remain as browser state after disconnect or revocation; use Chrome's UI to undo a group after its extension ownership is lost.
- Restricted Chrome pages and enterprise-blocked debugger attachments are reported as unavailable. The bridge has no fallback to a profile copy, remote-debugging port, or host UI automation.
- The separate `computer` tool's `webbrowser.*` actions control Safari and Chrome tabs through Apple Events outside this bridge. They need no pairing and no site permissions: navigation, history, tab changes, and JavaScript evaluation are gated by `computer` permission resources scoped to the browser bundle ID and operation. See [Native computer use](./computer-use.md#safari-and-chrome-apple-events).
- Model-driven navigate, click, and type require source-site and any known destination-site permissions before dispatch. The permission prompt warns that a permitted site action may trigger a download without another prompt: Chrome's extension debugger cannot stop every page-script or client-generated download before it starts. Explicit download links and file inputs remain unsupported. The extension checks static link destinations and revokes a tab that reaches an unapproved origin without forwarding its destination metadata. A destination produced by page script cannot always be known before a click, so revocation is a post-navigation privacy boundary, not a claim that the navigation never occurred. An authenticated user making a direct Session API request controls a paired tab; model tool calls use the separate site permissions.
- Links requesting a new tab, explicit download links, file inputs, password inputs, credential-bearing URLs, and explicit capture while password fields are present fail closed. Before capture, a bounded pierced DOM inspection covers child-frame documents and open or closed shadow roots; an incomplete, malformed, over-deep, or over-limit inspection rejects without requesting a screenshot. Scroll and capture remain available because they do not dispatch the guarded navigation, click, or text-input paths.

Page observations use the Chrome accessibility tree and include bounded role/name/description metadata only. Input values, raw DOM, query strings, URL fragments, credentials, cookies, tokens, and screenshots are absent from routine status and observation output. An explicit capture returns at most 1 MiB of PNG data and is retained only by the existing bounded tool-output lifecycle or the immediate authenticated API response.

## Manual installation and pairing

1. Open `chrome://extensions` in the Chrome profile you intend to pair.
2. Enable **Developer mode**, choose **Load unpacked**, and select the extension folder shown in the **Connect Chrome** dialog: `ycoding-chrome-extension` beside the installed `ycoding` executable, or `extensions/chrome` in a source checkout.
3. In the Mini or full YCoding Session command palette, choose **Connect Chrome** and press **p** to create a one-time pairing code. The authenticated `POST /api/session/:sessionID/browser/start` API provides the same code. This explicit action revokes any prior extension trust on the backend before issuing the new secret. Copy the returned secret directly to the extension popup; do not paste it into chat or a model prompt.
4. In the extension popup's pairing form, enter the code and choose **Connect YCoding**. **Local service address** is visible in that form and defaults to loopback; enter a different local address if the **Connect Chrome** dialog provides one. The extension remembers the address and reconnect credential. Pairing lists eligible tabs, including the active tab, for approved operations; every active Session on this backend can request access under its own Session identity and create new background tabs. Chrome's debugger warning appears when an operation attaches to a tab.
5. A paired offline connection with automatic reconnect enabled shows **Reconnecting** and retries in the background without another code. An explicit bridge stop retains trust but disables automatic reconnect and clears recovery alarms; the popup shows the saved connection as paused instead of offering a pairing form. Choose **Retry connection** to resume the approved backend. Choose **Forget pairing** to clear local trust, clear recovery alarms, and revoke the server credential; if the server is temporarily unavailable, the extension retains only the pending revocation and completes it after reconnect. The authenticated `DELETE /api/session/:sessionID/browser/pairing` operation revokes backend trust from any active Session.

For agent-owned tabs, choose `mode: "owned"` in the browser tool, inspect bridge status for its current generation, then open an approved URL. Preserve the returned tab and document fences for observation and actions. Use the explicit close operation when finished; selecting an existing tab in Chrome never grants owned-mode access to it. A Chrome native debugger-banner **Cancel** detaches and blocks the affected existing tab from being rediscovered under the current pairing. The toolbar badge is per tab, not a count of listed tabs.

The popup shows the local service address alongside the one-time code before pairing. Moving, archiving, or deleting the initiating Session leaves the backend connection and durable credential intact. Its in-flight mutations settle as uncertain, while other active Sessions retain access to shared tabs. Any active Session can revoke the credential through the authenticated API. Credentials issued by a Location-specific browser store do not authorize this backend-wide bridge; create a new code to pair.

The extension requires no package installation or build step.

After `ycoding update`, the installer, or a checkout change replaces the extension folder, run the matching YCoding and select **Reload** for the unpacked YCoding extension in `chrome://extensions`. Chrome does not guarantee that changing files on disk replaces an already loaded service worker. The extension and backend use bridge protocol version 3; a version-2 worker cannot authenticate and will not appear as a connected bridge with an empty profile grant. If the popup becomes unpaired after a version mismatch, create a new pairing code and connect again.

## Public operations

All normal HTTP operations retain the server's existing authentication and Session-location middleware.

| Operation        | Method and path                                  | Result                                                                                                                                       |
| ---------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Status           | `GET /api/session/:sessionID/browser`            | Safe bridge state, generation and pending call identity.                                                                                     |
| Tabs             | `GET /api/session/:sessionID/browser/tabs`       | Eligible paired and caller-owned tabs with query-free page metadata and freshness generations.                                               |
| Start            | `POST /api/session/:sessionID/browser/start`     | One-time `{ secret, expiresAt }` pairing value.                                                                                              |
| Observe          | `POST /api/session/:sessionID/browser/observe`   | Bounded semantic observation for a paired or caller-owned tab/generation/call ID.                                                            |
| Open             | `POST /api/session/:sessionID/browser/open`      | Create a new background tab for the caller Session from `{ generation, url, callID }`; return its safe tab projection.                       |
| Close            | `POST /api/session/:sessionID/browser/close`     | Close only the caller's agent-created tab, fenced by `{ tabID, generation, callID }`.                                                        |
| Action           | `POST /api/session/:sessionID/browser/action`    | One fenced semantic action; profile mode also accepts group/ungroup on explicitly named inactive tab members, returning the Chrome group ID. |
| Control          | `POST /api/session/:sessionID/browser/control`   | Explicit `pause` or `resume`; resume invalidates prior semantic references.                                                                  |
| Stop             | `DELETE /api/session/:sessionID/browser`         | Stops the shared bridge and debugger attachments for all Sessions.                                                                           |
| Forget pairing   | `DELETE /api/session/:sessionID/browser/pairing` | Revokes backend trust from an active Session and disconnects the shared bridge.                                                              |
| Extension bridge | `GET /api/browser/connect`                       | Secret-free WebSocket URL; exact extension Origin plus first-frame pairing authenticates it.                                                 |

The process-global Core `Browser.Service` exposes corresponding `status`, `list`, `start`, `open`, `close`, `observe`, `action`, `control`, `stop`, and `forget` methods. Each operation validates its caller Session; normal HTTP Session-location middleware and model permissions remain caller-scoped. Its transport-only `attach` method validates a first-frame pairing or reconnect handshake and returns scoped `receive`/`detach` hooks for Server.

The `browser` model tool intentionally omits pairing controls. Its default and explicit `mode: "profile"` return eligible paired tabs; `mode: "owned"` returns the caller's created tabs, and isolated mode returns temporary headless tabs. Owned open requires target-site permissions and close requires control/read permissions. Paired list/observe/capture/scroll actions require site read permissions; paired mutations also require site, destination when known, and control permissions for group changes. Browser tool calls bypass guardrail reviews; deny rules continue to block operations. Group and ungroup use the Action endpoint with a source tab, fresh observation fence, member tab IDs, title for group or returned group ID for ungroup. An exact action retry returns its retained settlement; conflicting reuse is rejected. Owned open call IDs cannot create a second tab in one bridge generation.

## Mutation boundary

Approved paired-tab navigate, click, and type use the tab-scoped debugger transport. Approval of the source site includes the possibility of incidental downloads; there is no separate pre-download prompt for such side effects. A known link to another site needs that destination approved before clicking; an unexpected destination revokes the tab before its metadata or content is returned. Explicit downloads, uploads, browser history, and full CDP access are not exposed.

Before click, type, and scroll input, the extension animates a separate **YCoding** arrow cursor to the CDP input point and shows a brief ripple for clicks. The fixed maximum-z-index overlay is an extension-owned script evaluated in a named isolated world with target coordinates passed as JSON; it uses a closed shadow root and a pointer-events-none host, and is removed best-effort when its debugger attachment is revoked. This bounded overlay is not model-supplied JavaScript: the browser tool exposes no arbitrary page-script evaluation or arbitrary CDP commands. Cursor injection is best-effort and does not block the browser action when unavailable. The cursor remains separate from the operating-system pointer and does not focus the window or intercept page hit-testing.

The separate [isolated browser](../specs/v2/isolated-browser.md) mode uses temporary headless state without personal logins. It is not a fallback for this extension. A Session must stop its current browser mode before starting the other; isolated startup does not revoke stored extension trust.
