# Chrome extension browser bridge

## Connect Chrome

Use the signed macOS package with Chrome and the YCoding service on the same Mac. The service must listen on `127.0.0.1`. The **Connect Chrome** command in the terminal shows these steps:

1. In `chrome://extensions`, turn on **Developer mode**, choose **Load unpacked**, and select `ycoding-chrome-extension` beside the `ycoding` executable. After an update, select **Reload** if the popup still shows the old extension.
2. Open the **YCoding Interaction** popup and choose **Connect**. The popup shows a short match code, and the Mac shows a native panel with the Chrome profile label and the same code. Choose **Allow** only when the codes match. Deny, closing the panel, or waiting 60 seconds refuses the profile. If YCoding listens on another loopback port, set **Local service address** under **Advanced** before connecting; the default is `http://127.0.0.1:42188`.
3. Chrome reconnects on its own after that. Each Session still asks separately for tab control, and you approve it in the popup.

### Profile authorization

- The extension generates a random 256-bit profile ID and keeps it, with the server address and credential, in `chrome.storage.local`. The match code is the first 40 bits of `SHA-256("ycoding-chrome-profile:" + profileID)` in Crockford base32, shown as `XXXX-XXXX`. The extension and the server compute it independently.
- On **Allow**, the server issues a random 256-bit credential to that connection once and stores only its SHA-256 digest, with the profile ID, label and creation time, in `interaction-chrome-profiles.json` under YCoding's global state directory. The file is written with mode `0600` and keeps at most 32 profiles; enrolling a 33rd drops the oldest. An unreadable or malformed file authorizes nobody.
- A stored credential reconnects without a prompt when the service worker starts, when Chrome starts, after an extension reload, after a YCoding restart, and after a dropped connection. Reconnecting restores only the link: no Session control, debugger attachment, tab group, capture or preview comes back, and each Session asks for tab control again. The extension discards a stored credential or profile ID that is not a 43-character base64url value and shows **Not connected**. Retries back off from 1 to 30 seconds, and a 30-second alarm wakes a stopped worker. While connected, the worker sends a keepalive frame every 20 seconds.
- An unknown profile, a wrong or forgotten credential, and a refused enrollment close the socket with code `4401`. The extension then clears its credential and shows that this Chrome profile is no longer allowed; it never enrolls again without another **Connect**. Only one enrollment waits at a time, and one Chrome profile holds the connection; another profile receives `4409`.
- **Forget this profile** under **Advanced** stops control in this browser, deletes the server's digest for the profile, and then clears the extension's credential. If YCoding is unreachable, the extension keeps only the pending revocation and finishes it when the service is reachable again.

### Control in Chrome

- An approved existing tab, or a new background tab that YCoding opens, joins one adapter-owned **YCoding control** group per window, created on first control and reused for later controlled tabs. A tab in one of your own groups is never moved; the popup asks you to move it out first. When the last control in a window ends, YCoding ungroups its tabs, so the group disappears while every tab stays open. YCoding closes only the background tabs it opened, and only while they are inactive.
- While a tab is controlled, its toolbar icon switches to the active YCoding icon, its badge reads **ON**, and its favicon shows the YCoding mark. Chrome's native debugger infobar with **Cancel** stays visible. When control ends (Stop, revocation, lease expiry, a lost tab, or about 8 seconds after the extension stops renewing the mark), YCoding restores the idle toolbar icon and removes its favicon from the page, leaving no YCoding element behind. A page with its own icon links gets those links back unchanged. On a page without an icon link, Chrome reloads the site's `/favicon.ico`, or shows its default icon if the site has none.
- Actions never activate a tab, focus a window, or raise Chrome. A JavaScript dialog (`alert`, `confirm` or `prompt`) is the exception YCoding cannot prevent: when a page in the selected tab of its window opens one, Chrome itself brings its window to the front and the dialog takes keyboard focus, so anything you type next goes to Chrome. This happens even when YCoding is not controlling the tab. YCoding does not answer, dismiss or suppress page dialogs and does not change site or macOS permissions to avoid them. When a step needs you, such as a page file chooser, a JavaScript dialog, a human check, a sensitive field, or **Take over** in the popup, control pauses at once without retrying the step. The popup and mini panel show **Paused** with the reason and **Resume**, and YCoding refuses further observations and actions until you resume or the Session requests resume. For a dialog, answer it in Chrome first; Resume is refused while the dialog is still open.
- A Session's Script or Code run executes in an isolated world of the controlled tab. It consumes the current observation. If the tab no longer shows the approved page after a run, control ends and the run's result is still returned. The extension confines each run to the one tab the control grant authorizes:
  - **One tab.** Every debugger command a run sends goes to that tab's ID through the debugger session YCoding attached for control. A command naming another tab is refused.
  - **Method allowlist.** A run may send only `Runtime.enable`, `Runtime.disable`, `Runtime.evaluate`, `Runtime.callFunctionOn`, `Runtime.releaseObjectGroup`, `Runtime.terminateExecution`, `Page.getFrameTree`, `Page.createIsolatedWorld`, `Page.addScriptToEvaluateOnNewDocument` and `Page.removeScriptToEvaluateOnNewDocument`. Every other command is refused before it reaches Chrome. That includes every `Target`, `Browser`, `Storage` and `Network` command (so no cookie reads), navigation, screenshots, input dispatch and request interception.
  - **No other targets.** The extension never attaches to child targets or popups and never sends a `Target` command, including `Target.setAutoAttach` and `Target.setDiscoverTargets`.
  - **Event scope.** Debugger events that come from a child session or another target are dropped. A run receives only events from its own tab's top-level target, and its result, console entries and errors go only to the lease and Session that started it. A request that names another Session's lease is refused.
  - **Related tabs.** A run is refused with `policy`, and control stays active, when its tab was opened by another tab or has opened one (Chrome's `openerTabId`), because such tabs can reach each other's windows.
  - **Stop and revocation.** Stop, revocation, lease expiry or the debugger detaching first aborts the run and, while the debugger is still attached, sends `Runtime.terminateExecution` through the tab's debugger session. The extension then discards the run's isolated worlds and detaches the debugger. The run settles as `stopped` at once. A later run on that grant is refused `stale` by YCoding, and the extension refuses any request on the revoked lease with `ownership`.
  - **Inside the page.** Runs and model clicks carry no user activation, so a page cannot open a file picker or a popup from them. The isolated world each run uses restricts page APIs as follows:
    - `window.open` and three-argument `document.open` return `null` and open nothing.
    - `opener`, and `postMessage` or `MessageEvent.source` for any window outside this tab's own frames, throw `SecurityError`.
    - `BroadcastChannel`, `Worker`, `SharedWorker` and `navigator.serviceWorker` throw `SecurityError`.
    - `localStorage`, `sessionStorage`, `indexedDB`, `document.cookie`, `cookieStore`, `caches`, `navigator.locks` and `navigator.storage` throw `SecurityError`.
    - `URL.createObjectURL` throws `SecurityError`.
    - Creating or inserting `script`, `iframe`, `frame`, `frameset`, `object`, `embed`, `base`, `meta`, `link`, `portal` or `fencedframe` elements, or SVG `script`, `animate` or `set`, throws `SecurityError`. This covers clones, fragments, shadow roots and `Range` insertion.
    - Changing an attribute or the text of an existing `script`, `frame`, `object`, `embed`, `base`, `meta`, `link` or `portal` element throws `SecurityError`.
    - Setting any `on*` attribute throws `SecurityError` through every attribute-writing API.
    - A `javascript:` URL in `href`, `src`, `action`, `formaction`, `xlink:href` or another URL-valued attribute throws `SecurityError`, including with leading spaces, embedded tabs or mixed case.
    - `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `setHTMLUnsafe`, `Document.parseHTMLUnsafe`, `document.write`, `document.writeln`, `execCommand`, `Range.createContextualFragment`, `DOMParser` and `srcdoc` throw `SecurityError`.
    - `click()`, a dispatched `click` or `DOMActivate` event, `submit()` and `requestSubmit()` throw `SecurityError` when the link or form would leave this tab: a named target, `_blank`, a `<base target>` or a `javascript:` URL. Same-tab `_self`, `_parent` and `_top` are allowed.
    - Sensitive form fields read as empty through `value`, `defaultValue`, `getAttribute`, `Attr.value` and `FormData`.
    - Every override is non-configurable and lives only in the isolated world, so neither the page nor the run can undo it.
    - Discarding a world removes its timers, listeners and observers.
- **Stop control** in the popup or mini panel revokes action admission at once, before Chrome cleanup finishes. The Session's control status reports the same cleanup result the extension saw. If Chrome refuses to ungroup or close a controlled tab, Stop reports that cleanup was not confirmed and the tab stays in the YCoding control group until you move it out.

### Mini panel

**Mini panel** in the popup opens a small Chrome popup window, 360 by 480 pixels, for the controlled tab. It shows the controlling Session's title, the status, a live preview, **Capture**, **Stop**, and **Resume** while paused. After a capture is sent, the status briefly reads **Capture sent**; failures appear as an alert below the buttons. Only your click opens or focuses it. The live preview stays in the panel and never leaves the browser.

**Capture** sends one frame to the Session that owns that control, and only on your click. Before the screenshot leaves the browser, the extension paints opaque boxes over password, one-time-code, payment, email, phone and address fields, elements marked `data-sensitive` or `data-private`, and visible text that matches the redaction patterns. The page title and URL are redacted before sending, and YCoding applies the same text redaction again before the Session receives the capture. Capture is refused on pages with child frames or more elements than it can inspect.

## Legacy browser bridge

The released model uses the Interaction tool for browser and desktop control. The Browser and Isolated Browser HTTP and SDK operations are separate from the Interaction tool.

The separate Manifest V3 extension in `extensions/chrome` uses the authenticated Session browser API below. Paired tabs retain their browser login state; agent-owned mode creates new background tabs. Neither mode copies cookies, profile files, passwords, or browser storage into YCoding.

## Security and non-interruption boundary

- Pairing is initiated from one Session. The authenticated YCoding API creates a random one-time secret that expires after two minutes and becomes invalid after one successful connection. The secret is sent only in the first WebSocket frame, never in a URL, log, tab projection, or model tool result.
- A successful one-time pairing issues a random durable reconnect credential to that extension installation. The extension stores the credential in `chrome.storage.local`; Core stores only its SHA-256 digest in the existing credential store. Trust is bound to the exact extension installation ID and a durable random server identity. The manifest's public `key` fixes that ID to `emlogajckgpjjigcbcbfbpbeencgghfb` wherever the extension folder is loaded from, so reloading or moving the folder keeps the pairing; the key is public and is not a credential. The initiating Session is recorded with the credential but is not required for reconnect or revocation; the process-global bridge serves every active Session. Origin and extension ID are checks, not credentials.
- The WebSocket endpoint accepts only an exact `chrome-extension://<extension-id>` Origin. Every connection's first frame must name that same extension ID and contain either the active one-time secret or the durable credential plus server identity. Ordinary websites, including pages served from localhost, cannot authenticate. A separate extension installation needs its own normal pairing; the extension identity does not transfer credentials or browser storage.
- An enabled pairing maintains a repeating Chrome recovery alarm at 30-second intervals and uses a separate alarm for connection retry backoff. The recovery alarm wakes the worker after unexpected termination; Chrome's startup event also wakes the saved pairing and authenticates with its durable credential. Reconnection does not reopen the popup or request another pairing code. Chrome may delay alarms and does not wake a sleeping device. A connected worker does not open a second bridge when the alarm fires. After Chrome, the worker, or the YCoding server restarts, eligible existing tabs are listed with fresh identities and attach only on their next approved operation. Agent-owned tabs must be newly opened. Restart never restores debugger attachments, semantic references, pending actions, or mutation settlements.
- The unpacked extension requests `alarms`, `debugger`, `storage`, `tabs`, and `tabGroups`, with host access only to loopback for its YCoding connection. `tabs` permits profile-wide tab URL/title metadata after pairing; `tabGroups` permits grouping and ungrouping paired inactive tabs. There is no blanket site-content host permission. The debugger attaches to an eligible existing tab only when an approved operation needs it, including if the tab is active; owned mode attaches only to newly created tabs and stays attached between steps. Chrome's native debugger infobar identifies **YCoding** while attached and offers **Cancel**; Chrome enforces the infobar and extensions cannot hide it. The per-tab toolbar badge says **ON** while attached and is clear when detached or never attached. Cancel revokes that tab and suppresses reattachment for the current pairing; a new pairing resets this denial.
- **Control marker.** Every tab YCoding controls, paired or agent-owned, shows the YCoding logo as its tab-strip favicon — the mint pixel-Y mark on its dark tile. The extension shows no visible in-page control indicator. It replaces the page's `link[rel~=icon]` elements through the same debugger transport, so it needs no site permission and does not focus or reorder any tab. It snapshots the page's own icon links first, re-asserts the logo when page script rewrites its favicons, and restores the page's icons exactly when control ends. The page title is never written. It verifies before every observe or action that the favicon image actually loads and reads the installed favicon back, and rejects the operation before dispatch when it cannot be shown or confirmed; a tab attached for the failing operation is detached again. A page whose Content Security Policy blocks `data:` images (`img-src` without `data:`) therefore cannot be controlled, because Chrome would not render the marker. A pinned tab shows only its favicon with no room for a distinguishable marker state, so the extension refuses to control it until it is unpinned. Titles reported to YCoding are the page's own.
- **Green group marker.** An inactive, ungrouped profile tab receives a temporary singleton group using Chrome's native `green` color. An active, ungrouped tab retains favicon-only control. An existing group requires the explicit `group_control` action with all its member tab IDs before observe or ordinary action can control it. The action requires every member to be inactive, unpinned, in one window, permitted for its site, and leased to the same Session. Pairing alone does not grant group control. The marker preserves the group's title, collapsed state, member order, and window. Membership, position, appearance, or grant changes end control of its members without rewriting the changed group. Normal release restores the saved appearance, or removes a temporary singleton group, only while ownership and inactive membership remain unchanged. Otherwise restoration is skipped. Crash or restart can leave a green group; the extension never infers cleanup authority from its color or title.
- **Marker lifetime.** Explicit release, stop, forget, disconnect, and revocation clear the marker with a bounded wait before the debugger detaches. When the extension cannot run a command, such as after Chrome's native Cancel, a worker or extension reload, or a crash, the page removes the marker itself: the extension refreshes a page-held deadline every 5 seconds, and the page removes its marker and restores its own favicons when 15 seconds pass without a refresh. The page checks every second, and immediately when the tab becomes visible or resumes from a frozen state. While YCoding's debugger remains attached, focus emulation keeps the controlled page visible and unfrozen, so if the worker can no longer refresh the marker, the page timer removes it within the 15-second expiry plus one-second check interval. If detachment leaves a page hidden, it relies on Chrome's throttled timers and removal can take longer; a frozen page cleans up when it resumes. The extension holds one isolated-world context per document rather than creating one per refresh. Marker commands for a tab run in order, so a refresh cannot repaint a marker after cleanup; if the page removes the marker element itself, the page restores its own favicons without installing a second logo.
- Pairing authorizes enumeration of eligible existing and future tabs. Enumeration skips restricted and credential-bearing URLs, exposes only query-free page projections through the authenticated Session API, and never eagerly attaches a debugger to every tab. An explicit stop disconnects and detaches tabs while retaining pairing for manual Retry; Forget revokes trust. Future eligible tabs join while the pairing is connected.
- If initial pairing cannot save its credential, establish recovery, or enumerate tabs, the worker requests trust revocation, clears its local pairing, and closes the bridge rather than reporting a connected profile with no grant.
- Agent-owned mode requires the same one-time pairing. A `mode: "owned"` open creates `about:blank` with `active: false`, attaches only that newly created tab, and navigates it to the approved HTTP(S) target. Only the creating Session may list, observe, act on, or explicitly close it. An owner Session's move, archive, or deletion revokes its owned tabs without disconnecting paired tabs: inactive owned tabs close, while active owned tabs stay open with the debugger detached. The same active-tab close boundary applies when the shared bridge stops or disconnects. No tab or semantic reference is restored after reconnect. An owned tab remains controllable while active, but explicit close waits until it is inactive.
- Profile control is exclusive per Session. The first approved observe or action on a paired tab claims it for that Session; another Session receives an ownership error before any permission prompt or page access, while status and tab listings stay available and mark the tab `lease: "other"`. Group, ungroup, and group-control claim every member together or none. Releasing one member of a controlled group ends control of the other members as well. A Session gives control back with the `release` operation, and control also ends when the Session's execution ends (succeeded, failed, or interrupted) and when the Session is moved, archived, or deleted. Ending execution releases only profile control; owned tabs follow their own lifetime. A release completes only after the extension confirms it cleared the favicon marker and detached, and it waits for an in-flight command from the same Session to settle first. Native group restoration is best effort. An unconfirmed release keeps the holder and can be retried. Stop, forget, and bridge disconnect clear every lease. The native `computer` tool's `webbrowser.*` actions use Apple Events outside this bridge and are not covered by the lease.
- When the opened page fails the model's returned-page read permission check, YCoding attempts one owner-scoped close without exposing page metadata. If the tab became active or the close cannot be confirmed, the tool returns its opaque tab ID and asks the user to switch away and close it manually; it does not retry an uncertain close.
- YCoding never activates, focuses, or closes an existing user tab or window. An explicit group action may rearrange only its paired inactive tab members within one window; it never moves tabs outside the paired set. It never uses global mouse or keyboard injection, the host clipboard, Chrome notifications, external protocols, arbitrary JavaScript evaluation, or arbitrary CDP commands. Form filling, option selection, checking, hovering, explicit waits, page clipboard access, file upload to a page file input or through a file chooser the page opens, waiting for a page-triggered download, history search, console logs, MHTML export, and page WebMCP tools exist only as typed, fenced actions; history and downloads additionally need their optional extension permissions, granted from the popup. An approved site action may indirectly trigger a browser download.
- An active paired or owned tab remains available for approved observation and actions; YCoding never switches tabs, activates a window, or restores focus. An explicit bridge pause still blocks actions.
- The browser tool lists eligible paired tabs by default (`mode: "profile"` is equivalent). Model-driven list/observe/capture/scroll requires per-site read permission. Navigate/click/type require source-site and any known destination-site permissions before dispatch; group/ungroup also require browser-control permission. Browser tool calls are never guardrail-reviewed: each mutation is evaluated against the `browser_profile_mutation` (paired profile) or `browser_mutation` (owned) guardrail action, whose deny rules still block it and whose decision is recorded as an audit event, and no review is requested. Group creates one new Chrome group of one to eight paired, ungrouped, inactive tabs in the same window and may set its title; ungroup reverses only a group created in the current connection and only while every member is inactive and unchanged. Neither operation closes tabs. Chrome groups remain as browser state after disconnect or revocation; use Chrome's UI to undo a group after its extension ownership is lost.
- Restricted Chrome pages and enterprise-blocked debugger attachments are reported as unavailable. The bridge has no fallback to a profile copy, remote-debugging port, or host UI automation.
- The separate `computer` tool's `webbrowser.*` actions control Safari and Chrome tabs through Apple Events outside this bridge. They need no pairing and no site permissions: navigation, history, tab changes, and JavaScript evaluation are gated by `computer` permission resources scoped to the browser bundle ID and operation. See [Native computer use](./computer-use.md#safari-and-chrome-apple-events).
- Model-driven navigate, click, and type require source-site and any known destination-site permissions before dispatch. The permission prompt warns that a permitted site action may trigger a download without another prompt: Chrome's extension debugger cannot stop every page-script or client-generated download before it starts. Clicking an explicit download link remains unsupported; files reach a page only through the typed upload action. The extension checks static link destinations and revokes a tab that reaches an unapproved origin without forwarding its destination metadata. A destination produced by page script cannot always be known before a click, so revocation is a post-navigation privacy boundary, not a claim that the navigation never occurred. An authenticated user making a direct Session API request controls a paired tab; model tool calls use the separate site permissions.
- Links requesting a new tab, explicit download links, file inputs, password inputs, credential-bearing URLs, and explicit capture while password fields are present fail closed.
- Owned tabs intercept page file choosers while YCoding is attached. On a paired tab, YCoding intercepts choosers while a managed click, type, key, fill, select, check, upload, or WebMCP invoke action runs. Choosers opened between actions behave normally. A click that opens a chooser reports the cancellation and suggests `upload`. `upload` sets files directly on a file input, including a hidden one, or clicks an element and fills the chooser it opens without showing a native dialog. Files go only to the same frame and document that received the click. Page pickers without a file input, such as `showOpenFilePicker`, cannot receive files. A dispatched click that cannot complete the selection settles as uncertain and pauses the tab. If Chrome cannot turn off interception on a paired tab, YCoding detaches the debugger. Upload never activates, focuses, or raises the tab or its window.
- Sensitive fields fail closed. A field is sensitive when it is an `input`, `textarea`, or contenteditable element that is a password input, carries an `autocomplete` token `current-password`, `new-password`, `one-time-code`, `cc-number`, `cc-csc`, `cc-exp`, `cc-exp-month`, or `cc-exp-year`, or whose `name`, `id`, `aria-label`, `placeholder`, associated `<label>` text, `aria-labelledby` text, or accessible name looks like a password, passcode, passphrase, one-time or verification code, security code, card number, a `secret` token (such as `client_secret`, `apiSecret`, or `secret_key`), OTP, TOTP, MFA, 2FA, PIN, CVV, CVC, or CSC. `fill` and `type` on a sensitive field or a file input are rejected before dispatch, so no text, key event, or value write reaches the page. key checks the active focus in profile, owned, and isolated modes. Only Tab, Shift+Tab, Escape, ArrowUp, ArrowDown, ArrowLeft, ArrowRight, Home, End, PageUp, and PageDown bypass active-focus inspection, with no Ctrl, Meta, or Alt and Shift allowed only for Tab. Every other supported key requires verified focus, including printable characters with Shift or Alt, Space, Enter, Backspace, Delete, Insert, Shift+Insert, and all Ctrl or Meta chords, including V and X. Focus inspection refuses sensitive password, one-time-code, payment, or secret-named fields, file inputs, and unverified focus (including closed shadow roots and unreachable cross-origin frames) before any key event with dispatched:false. Do not use key to bypass a sensitive-field refusal in any mode. Name-based detection can also flag an ordinary field such as one named `pin`, which then refuses entry. A secret field with no secret-like attribute, label, or accessible name is not detected automatically; the tool's hand-off rule, never to enter passwords, one-time codes, or payment secrets, covers that case. Before capture, a bounded pierced DOM inspection covers child-frame documents and open or closed shadow roots; an incomplete, malformed, over-deep, or over-limit inspection rejects without requesting a screenshot. Scroll and capture remain available because they do not dispatch the guarded navigation, click, or text-input paths.

Page observations use the Chrome accessibility tree and include bounded role, name, description, and control state: `checked` and `pressed` (`true`, `false`, or `"mixed"`), `expanded`, `selected`, and, for text boxes, search boxes, comboboxes, spin buttons, and sliders, the current `value` (at most 1024 characters). File inputs missing from the accessibility tree, such as `display: none` or `hidden` inputs, are listed with role `button` and description `Hidden file input`; their name comes from `aria-label`, label text, or `title`, and is `File input` when none of those exist. The `date`, `time`, `datetime-local`, `month`, `week`, `color`, and `range` inputs are observed form controls with their values. Inside an open popup (the same-frame target of an expanded control's `aria-controls` or `aria-owns`, or a visible `listbox` or `menu`), rows that have no ARIA role but show a pointer cursor are listed with role `clickable` and their visible text as the name, excluding `aria-hidden` and hidden text. Only the outermost such row is listed, and rows that contain a link, button, input, select, textarea, iframe, summary, or any element with a role, tabindex, or contenteditable attribute are skipped. A `wait` locator with role `clickable` matches these rows by name. A row must be rendered and receive the hit test at its center (rows clipped by a scrolling container are kept) and is hit-tested again before a click, which fails before dispatch when something else covers it. The scan visits at most 16 popups and 2,000 nodes, skips hidden subtrees, and lists at most 100 rows per frame; reaching a limit or failing to inspect a frame marks the observation truncated. A sensitive field is listed with `sensitive: true` and no value, so the model can see that the user must take over. Raw DOM, DOM attributes, text inside editable controls outside `value`, query strings, URL fragments, credentials, cookies, tokens, and screenshots are absent from routine status and observation output. An explicit capture returns at most 1 MiB of PNG data and is retained only by the existing bounded tool-output lifecycle or the immediate authenticated API response.

## Manual installation and pairing

The legacy extension also loads unpacked in Edge or Brave. Pairing binds to the extension installation; pair each browser separately.

1. Open `chrome://extensions` in the Chrome profile you intend to pair.
2. Enable **Developer mode**, choose **Load unpacked**, and select the legacy `extensions/chrome` folder.
3. Call authenticated `POST /api/session/:sessionID/browser/start` to create a one-time pairing code and replace prior trust. Enter the code in the legacy extension popup, not in chat or in a model prompt.
4. In the legacy popup enter the loopback service address and choose **Connect YCoding**. The extension remembers the address and reconnect credential. Pairing lists eligible tabs for approved operations; active Sessions request access under their own identities. Chrome displays its debugger warning when an operation attaches to a tab.
5. A paired offline connection with automatic reconnect enabled shows **Reconnecting** and retries in the background without another code. An explicit bridge stop retains trust but disables automatic reconnect and clears recovery alarms; the popup shows the saved connection as paused instead of offering a pairing form. Choose **Retry connection** to resume the approved backend. Choose **Forget pairing** to clear local trust, clear recovery alarms, and revoke the server credential; if the server is temporarily unavailable, the extension retains only the pending revocation and completes it after reconnect. The authenticated `DELETE /api/session/:sessionID/browser/pairing` operation revokes backend trust from an active Session.

For agent-owned tabs, choose `mode: "owned"` in the browser tool, inspect bridge status for its current generation, then open an approved URL. Preserve the returned tab and document fences for observation and actions. Use the explicit close operation when finished; selecting an existing tab in Chrome never grants owned-mode access to it. A Chrome native debugger-banner **Cancel** detaches and blocks the affected existing tab from being rediscovered under the current pairing. The toolbar badge is per tab, not a count of listed tabs.

The compact popup is 320 CSS pixels wide and keeps pairing scope visible before Connect. Expand **Browser control details** for secondary guidance. It shows the local service address alongside the one-time code before pairing. Moving, archiving, or deleting the initiating Session leaves the backend connection and durable credential intact. Its in-flight mutations settle as uncertain, while other active Sessions retain access to shared tabs. Any active Session can revoke the credential through the authenticated API. Credentials issued by a Location-specific browser store do not authorize this backend-wide bridge; create a new code to pair.

The agent is instructed to ask before irreversible submissions, purchases, payments, deletions, sending messages, or accepting legal terms, to proceed without asking for reading, navigation, and reversible input that submits nothing, and to never solve CAPTCHAs or enter passwords, one-time codes, or payment secrets, handing the page to the user instead. These are guidance rules in the tool description; the dispatch-time permission and guardrail checks above are unchanged and remain the enforcement boundary.

The legacy extension loads its source modules unbundled and uses bridge protocol version 6. After changing those files, select **Reload** on the legacy extension in `chrome://extensions` and use a matching backend. A worker on another version cannot authenticate.

## Public operations

Profile tab listings include `groupID` for grouped tabs and omit it for ungrouped tabs. To control an existing group, select every listed tab with that group ID and submit `action: { type: "group_control", tabIDs: [...] }` using a member's current listing fences. Native membership is checked again before any group mutation or debugger attachment. A later navigation or group change ends the current group grant; stale membership must not be reused.

All normal HTTP operations retain the server's existing authentication and Session-location middleware.

| Operation        | Method and path                                  | Result                                                                                                                                       |
| ---------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Status           | `GET /api/session/:sessionID/browser`            | Safe bridge state, durable `paired` indicator, generation and pending call identity.                                                         |
| Tabs             | `GET /api/session/:sessionID/browser/tabs`       | Eligible paired and caller-owned tabs with query-free page metadata and freshness generations.                                               |
| Start            | `POST /api/session/:sessionID/browser/start`     | One-time `{ secret, expiresAt }` pairing value.                                                                                              |
| Observe          | `POST /api/session/:sessionID/browser/observe`   | Bounded semantic observation for a paired or caller-owned tab/generation/call ID; `diff: true` returns only added/changed elements plus removed locators. |
| Open             | `POST /api/session/:sessionID/browser/open`      | Create a new background tab for the caller Session from `{ generation, url, callID }`; return its safe tab projection.                       |
| Close            | `POST /api/session/:sessionID/browser/close`     | Close only the caller's agent-created tab, fenced by `{ tabID, generation, callID }`.                                                        |
| Release          | `POST /api/session/:sessionID/browser/release`   | Give up the caller's control of a paired tab, fenced by `{ tabID, generation, callID }`; returns after the extension confirms cleanup.       |
| Action           | `POST /api/session/:sessionID/browser/action`    | One fenced semantic action; profile mode also accepts group, ungroup, and group_control on explicitly named inactive tab members, returning the Chrome group ID. |
| Control          | `POST /api/session/:sessionID/browser/control`   | Explicit `pause` or `resume`; resume invalidates prior semantic references.                                                                  |
| Stop             | `DELETE /api/session/:sessionID/browser`         | Stops the shared bridge and debugger attachments for all Sessions.                                                                           |
| Forget pairing   | `DELETE /api/session/:sessionID/browser/pairing` | Revokes backend trust from an active Session and disconnects the shared bridge.                                                              |
| Extension bridge | `GET /api/browser/connect`                       | Secret-free WebSocket URL; exact extension Origin plus first-frame pairing authenticates it.                                                 |

The process-global Core `Browser.Service` exposes corresponding `status`, `list`, `start`, `open`, `close`, `release`, `observe`, `action`, `control`, `stop`, and `forget` methods. Each operation validates its caller Session; normal HTTP Session-location middleware and model permissions remain caller-scoped. Its transport-only `attach` method validates a first-frame pairing or reconnect handshake and returns scoped `receive`/`detach` hooks for Server.

The following `browser` tool behavior describes the legacy implementation. The signed package registers Interaction for model calls and retains the Browser HTTP and SDK APIs.

The `browser` model tool intentionally omits pairing controls. Its `deliver` operation (`mode: "owned"`) marks a caller-owned tab to remain open after control ends and has no HTTP counterpart. Its `release` operation (`mode: "profile"`) gives back the caller's control of a paired tab and needs no site permission. Its default and explicit `mode: "profile"` return eligible paired tabs; `mode: "owned"` returns the caller's created tabs, and isolated mode returns temporary headless tabs. Owned open requires target-site permissions and close requires control/read permissions. Paired list/observe/capture/scroll actions require site read permissions; paired mutations also require site, destination when known, and control permissions for group changes. Browser tool calls bypass guardrail reviews; deny rules continue to block operations. Group and ungroup use the Action endpoint with a source tab, fresh observation fence, member tab IDs, title for group or returned group ID for ungroup. An exact action retry returns its retained settlement; conflicting reuse is rejected. Owned open call IDs cannot create a second tab in one bridge generation.


**Tab departures.** When a paired tab leaves the list, the extension tells Core why: `closed` (Chrome closed the tab), `navigated` (the tab left the approved origins and its sharing was revoked), `detached` (the debugger detached, including Chrome's native **Cancel**; the optional `detachReason` carries Chrome's reason, at most 64 characters) or `access_revoked` (paired-profile access was turned off, or the pairing was stopped or forgotten). When a tab that left the approved origins is listed again, its new `shared` frame names the previous tab ID, so the model can see that the new ID is the same Chrome tab. Core keeps the 64 most recent departures per bridge connection, never exposes a title, URL, or origin for a departed tab, and discards them when the connection ends. A listed successor is never claimed automatically: observe it to take control of it.

When the `browser` tool is given a tab ID that is not usable it names the cause instead of a generic failure: a tab that exists in another mode names that mode and the `mode` value to pass; a departed tab states its reason and, when the same Chrome tab is listed again, its new ID with an instruction to observe it before acting; an ID the current connection does not list says to list tabs again. A paired tab ID used with `mode: "isolated"`, and an isolated tab ID used with a paired mode, are reported the same way. A Session never learns that another Session's owned tab exists. The diagnosis replaces only the generic missing-tab failure and adds no page data; for a listed tab the lease, permission, and guardrail checks run unchanged.

## Mutation boundary

Profile release acknowledges a handoff only after Chrome confirms debugger detachment. If detachment fails without confirmation, the Session keeps its lease and the worker rejects observations, actions, and group control for that tab. A matching late native detachment lets an explicit release retry finish without detaching again; it does not turn an earlier error into a success. Chrome's native **Cancel** revokes access for the current pairing instead of releasing the tab for another Session.

Explicit close checks Chrome's selected-tab state after reading the owned tab's navigation history. If Chrome does not report the tab as inactive, YCoding leaves it open and does not retry. Automatic cleanup also requires an explicitly inactive tab. Chrome exposes separate activity-read and tab-remove operations, not an atomic close-if-inactive operation; selection can still change between those calls.

Approved paired-tab navigate, click, type, fill, select, check, and hover use the tab-scoped debugger transport. Approval of the source site includes the possibility of incidental downloads; there is no separate pre-download prompt for such side effects. A known link to another site needs that destination approved before clicking; an unexpected destination revokes the tab before its metadata or content is returned. Full CDP access is not exposed; downloads, uploads, and browser history are exposed only as the typed actions and history operation described above.

Every observed element also carries a stable locator of the form `role=<role>[name="<accessible name>"]` (with an `|nth=` suffix when several elements share role and name). Click, type, fill, select, check, hover, and upload accept that locator instead of a semantic ref; YCoding resolves it against the current observation before dispatch, inside the same fences, and rejects a malformed locator before dispatch. Wait also accepts a locator for an element that has not appeared yet and matches it on each poll.

The form-control actions are typed and fenced like click and type, and each needs the source site's interact permission (plus read and interact on a child frame's site for a framed element):

- `fill` replaces a field's text, and `text: ""` clears it. Text fields, text areas, and contenteditable elements receive inserted text after their existing contents are selected; `date`, `time`, `datetime-local`, `month`, `week`, `color`, and `range` inputs have their value set followed by `input` and `change` events. The result reports the field's resulting `control.value`, with a message when it differs from the requested text.
- `select` picks options of a native `<select>` by `values`, `labels`, or `indexes` (exactly one list of one to 32 entries), rejecting a missing or disabled option and several options on a single select before dispatch. On an open ARIA listbox it clicks one rendered option chosen by label or index; a collapsed combobox is rejected so the model opens it, observes, and selects. Options are clicked at their rendered position, scrolling the option into view inside its own popup container first. The result reports `control.selected` only after the requested option reports `selected`, or, when the option has left the page, after the controlling combobox's displayed value or text changed to include the option's label. Otherwise `control.selected` is empty and the message is `The selection could not be confirmed`; a popup that merely closed is not evidence of a selection. Menu items, including `menuitemcheckbox` and `menuitemradio`, are observed and clicked like other controls.
- `check` sets a checkbox, radio, or switch to `checked: true` or `checked: false`. It does nothing when the state already matches, refuses to uncheck a radio, clicks once otherwise, and reports the observed `control.checked`, with a message when the state did not change.
- `hover` moves the pointer to the element with one mouse-move event and no press.
- `wait` takes at most one condition and fails with a wait timeout when it is not met: a ref or locator with `state` `attached`, `visible`, `hidden`, or `detached` (default `visible` for a locator, `attached` for a ref; matching uses the accessibility tree of the page and its approved frames, so an element hidden with `display: none` counts as detached); `url`, a pattern over the page origin and path in which `*` matches any characters and the query and fragment are never matched; `load` of `domcontentloaded` or `load` from the document ready state, or `networkidle`, met when no network request has been pending for 500 ms (on a paired tab attached while requests were already running, only requests started after attach are seen); or `text` that must appear in the page's rendered text. `timeoutMs` defaults to 5,000 and is at most 30,000; a wait without a condition waits for `load`. A wait is a read: it never navigates and returns only completion, plus the matching child frame's page when the match was in a frame, after that frame's site passes read permission. YCoding extends its command deadline by the wait timeout so a slow wait reports a wait failure rather than a lost response.

Form-control work runs fixed extension functions in a named isolated world (`ycoding-control`) created per frame document; model-supplied text and option criteria are passed only as JSON call arguments, never as script source, and the browser tool exposes no arbitrary page-script evaluation or arbitrary CDP commands. Events dispatched from that world reach page listeners, but a page that accepts only trusted `input` or `change` events can ignore a native select or value-set fill. Observing with `diff: true` returns only elements added or changed since the previous observation of the same document, with `delta.removed` listing locators that disappeared; the first observation is always full. Capture accepts a `clip` rectangle, `fullPage: true`, or a `ref` to capture one element, under the same password-field inspection and size limit. A JavaScript dialog opened by the page is remembered per tab: the `dialog` action without `accept` reports its kind and message, and with `accept` (and optional prompt `text`) answers it; other actions stall behind an open dialog until it is answered. An agent-owned tab can be marked with the tool's `deliver` operation so it stays open in Chrome as the work product — marker removed, debugger detached — instead of closing when control ends.

A lost execution context invalidates the cached control world but never repeats the failed control function. A fill or select that reached its apply step returns a dispatched failure when its result is lost; it may already have changed the page or triggered page listeners. Observe again before deciding whether another action is needed. A later explicit call creates a fresh world when required; reconstructing that world does not replay prior actions.

The extension shows no visible in-page control indicator: no cursor, label, or ripple. Dispatched actions such as clicks, typing, and scrolling still act on the page as ordinary input; only the control indicator is absent. The favicon marker, native green group where eligible, and toolbar badge identify controlled tabs. The tool exposes no arbitrary page-script evaluation or arbitrary CDP commands. The marker's appearance is specified in `extensions/chrome/DESIGN.md`.

Every debugger attachment enables Chrome focus emulation before the tab is usable. Click, hover, and scroll always use CDP mouse input, including in background tabs and in unfocused or minimized windows. While the debugger is attached, the controlled page reports `document.visibilityState === "visible"` and is not background-throttled; detaching ends focus emulation. The tab and window are not activated or focused. If Chrome does not acknowledge CDP mouse input within two seconds, the action fails as dispatched and its outcome is uncertain. Typing uses text insertion on the focused element. Enter and Space key presses carry their character (`\r` and a space) so the focused element's default activation, such as a button click or form submission, runs along with page key handlers.

The separate [isolated browser](../specs/isolated-browser.md) mode uses temporary headless state without personal logins. It is not a fallback for this extension. A Session must stop its current browser mode before starting the other; isolated startup does not revoke stored extension trust.
