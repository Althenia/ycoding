# Chrome selected-tab bridge

Status: **partial. Pairing, sharing, and observation work in user Chrome; navigate, click, and type remain unavailable.**

YCoding can control only Chrome tabs that a user explicitly shares from the unpacked Manifest V3 extension in `extensions/chrome`. The bridge uses the user's existing tab and therefore its existing login state without copying cookies, profile files, passwords, or browser storage into YCoding.

## Security and non-interruption boundary

- Pairing is Session-scoped. The authenticated YCoding API creates a random one-time secret that expires after two minutes and becomes invalid after one successful connection. The secret is sent only in the first WebSocket frame, never in a URL, log, tab projection, or model tool result.
- A successful one-time pairing issues a random durable reconnect credential to that extension installation. The extension stores the credential in `chrome.storage.local`; Core stores only its SHA-256 digest in the existing credential store. Trust is bound to the exact extension installation ID, a durable random server identity, the approved Session, and that Session's Location. Origin and extension ID are checks, not credentials.
- The WebSocket endpoint accepts only an exact `chrome-extension://<extension-id>` Origin. Every connection's first frame must name that same extension ID and contain either the active one-time secret or the durable credential plus server identity. Ordinary websites, including pages served from localhost, cannot authenticate.
- After Chrome, the extension worker, or the YCoding server restarts, the extension reconnects only to its stored approved Session, using alarm-backed exponential backoff from one to 30 seconds. Restart never restores debugger attachments, shared-tab grants, semantic references, pending actions, or mutation settlements; tabs must be shared again explicitly.
- The unpacked extension requests `activeTab` and `debugger`. Chrome displays its debugger warning while a selected tab is attached; the popup states this behavior. The extension has no blanket site-content permission and does not inspect tab content or attach the debugger until the user presses **Share current tab**.
- YCoding never activates, focuses, moves, or closes the user's browser window or tab. It never uses global mouse or keyboard injection, the host clipboard, Chrome notifications, downloads, uploads, external protocols, arbitrary JavaScript evaluation, or arbitrary CDP commands.
- A shared tab pauses whenever it becomes active. Automation can continue only after the user switches away. YCoding does not switch back or restore focus for the user.
- Restricted Chrome pages and enterprise-blocked debugger attachments are reported as unavailable. There is no fallback to a profile copy, remote-debugging port, personal-tab attachment, or host UI automation.
- Navigate, click, and type currently fail closed in the extension before it issues any action or guard CDP command. Chrome allows the extension to use the `Fetch` and `Target` domains, but those mechanisms cannot prevent every download caused by page script or a client-generated URL. The deprecated target-level `Page.setDownloadBehavior` command is rejected by user Chrome with CDP error `-32000`, while the replacement `Browser.setDownloadBehavior` belongs to the browser-wide `Browser` domain that [`chrome.debugger` does not expose](https://developer.chrome.com/docs/extensions/reference/api/debugger#restricted-domains). Adding the profile-wide [`downloads` permission](https://developer.chrome.com/docs/extensions/reference/api/downloads) would also observe or cancel a download only after it begins and is outside this selected-tab permission boundary. The extension therefore does not weaken or approximate the no-download guarantee.
- Links requesting a new tab, explicit download links, file inputs, password inputs, credential-bearing URLs, and explicit capture while password fields are present fail closed. Before capture, a bounded pierced DOM inspection covers child-frame documents and open or closed shadow roots; an incomplete, malformed, over-deep, or over-limit inspection rejects without requesting a screenshot. Scroll and capture remain available because they do not dispatch the guarded navigation, click, or text-input paths.

Page observations use the Chrome accessibility tree and include bounded role/name/description metadata only. Input values, raw DOM, query strings, URL fragments, credentials, cookies, tokens, and screenshots are absent from routine status and observation output. An explicit capture returns at most 1 MiB of PNG data and is retained only by the existing bounded tool-output lifecycle or the immediate authenticated API response.

## Manual installation and pairing

1. Open `chrome://extensions` in the Chrome profile whose existing tab you intend to share.
2. Enable **Developer mode**, choose **Load unpacked**, and select this repository's `extensions/chrome` directory.
3. In YCoding, create browser pairing for the intended Session through `POST /api/session/:sessionID/browser/start`. This explicit action revokes any prior extension trust in the same Location before issuing the new secret. Copy the returned secret directly to the extension popup; do not paste it into chat or a model prompt.
4. Enter the local YCoding service URL, Session ID, and one-time secret in the extension popup, then choose **Pair selected Session**. Selecting another Session requires a new one-time secret and disarms the previous grant; changing text in the Session field alone grants nothing.
5. Open the tab to share, open the extension popup, and choose **Share current tab**. Chrome's debugger warning is expected.
6. Switch to another tab before asking YCoding to observe or act. Return to the shared tab at any time to make automation yield. Choose **Revoke current tab** to detach it, or stop the Session bridge to revoke all its shared tabs.
7. An explicit bridge stop retains trust but disables automatic reconnect. Choose **Connect selected Session** to resume the same approved Session without sharing a tab. Choose **Forget pairing** to clear local trust and revoke the server credential; if the server is temporarily unavailable, the extension retains only the pending revocation and completes it after reconnect. The authenticated `DELETE /api/session/:sessionID/browser/pairing` operation is the server-side revocation path.

The extension is source-only and requires no package installation or build step.

## Public operations

All normal HTTP operations retain the server's existing authentication and Session-location middleware.

| Operation        | Method and path                                  | Result                                                                                                                                                 |
| ---------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Status           | `GET /api/session/:sessionID/browser`            | Safe bridge state, generation and pending call identity.                                                                                               |
| Tabs             | `GET /api/session/:sessionID/browser/tabs`       | Explicitly shared tabs with query-free page metadata and freshness generations.                                                                        |
| Start            | `POST /api/session/:sessionID/browser/start`     | One-time `{ secret, expiresAt }` pairing value.                                                                                                        |
| Observe          | `POST /api/session/:sessionID/browser/observe`   | Bounded semantic observation for an owned tab/generation/call ID.                                                                                      |
| Action           | `POST /api/session/:sessionID/browser/action`    | One strict navigate/click/type/scroll/capture action fenced by tab, bridge generation, document generation, observation revision and original call ID. |
| Control          | `POST /api/session/:sessionID/browser/control`   | Explicit `pause` or `resume`; resume invalidates prior semantic references.                                                                            |
| Stop             | `DELETE /api/session/:sessionID/browser`         | Revokes only this Session's bridge and debugger attachments.                                                                                           |
| Forget pairing   | `DELETE /api/session/:sessionID/browser/pairing` | Revokes durable extension trust and disconnects the Session bridge.                                                                                    |
| Extension bridge | `GET /api/session/:sessionID/browser/connect`    | Secret-free WebSocket URL; exact extension Origin plus first-frame pairing authenticates it.                                                           |

The Core `Browser.Service` exposes corresponding `status`, `list`, `start`, `observe`, `action`, `control`, `stop`, and `forget` methods. Every method validates the owning Session against the active Location. Its transport-only `attach` method validates a first-frame pairing or reconnect handshake and returns scoped `receive`/`detach` hooks for Server.

The `browser` model tool intentionally omits pairing. It exposes status/list/observe/action/control/stop, uses the canonical tool settlement path, and applies `PermissionV2` at execution, including before shared-tab metadata is exposed. Navigate/click/type additionally reserve `SessionGuardrail` action `browser_mutation` before dispatch. The extension rejects those guarded actions before any CDP action command and reports `dispatched: false` in its internal error frame. Core returns a retained `rejected` settlement without marking the tab uncertain. A mutation error after dispatch, timeout, or connection loss without a proven terminal result remains `uncertain` and pauses the tab. An exact retry returns the retained settlement; conflicting reuse of the call ID is rejected. Neither rejection nor uncertainty causes automatic replay.

## Current validation limit

Automated tests cover Schema bounds, route shapes, strict extension-origin pairing, single-use bootstrap, durable restart authentication, Session/Location binding, explicit switching, revocation, unknown/revoked fail-closed behavior, reconnect backoff, worker restart without tab/action replay, Session/tab ownership, stale observation rejection, one-writer dispatch, uncertain-mutation deduplication, permission/guardrail ordering, safe URL projection, extension protocol helpers, and zero CDP command dispatch for rejected navigate, click, and type actions. JavaScript parse checks validate the extension entrypoints. A real user-Chrome run verified pairing, sharing, and observation and reproduced `Page.setDownloadBehavior` rejection; it did not establish guarded mutation support. A release must not claim selected-tab mutation support unless an allowed, selected-tab-scoped no-download mechanism and a non-uncertain pre-dispatch settlement are implemented and manually validated with focus, active-tab choice, unrelated tabs, typing, pointer, and clipboard unchanged.

The separate [isolated-browser implementation](../specs/v2/isolated-browser.md) uses temporary headless state without personal logins. Its Session API, generated clients, model-tool mode, and TUI lifecycle controls are implemented and locally validated on macOS arm64 with Chrome 152, including Bun and Node packaged runtimes. The contract records remaining validation limits. It is not a fallback for this extension and cannot add mutation support to a personal Chrome tab. A Session must stop its current browser mode before starting the other; isolated startup does not revoke stored extension trust.
