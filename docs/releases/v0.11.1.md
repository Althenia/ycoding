# YCoding v0.11.1

## Added

- `ycoding decision watch <root> --family --follow` keeps one native observer armed on a root Session and its descendants until you cancel it or it stops with an error. It does not end when a decision is pending, a reply arrives, the root goes idle with work unfinished, or an execution completes. It prints one JSON line per observation containing identifiers only: Session, request and event IDs, request kind, event type and sequence, whether the root is active, and a resolution when a request leaves the pending list. Request text, decide commands, answers and transcripts are never printed.
- Follow covers pending permission, guardrail, question, form and review requests, observed replies, durable execution, step, input, work-completion, task and review events, and descendants created after the watch starts. When the native connection fails or a stream ends, it reconnects with backoff, rereads current pending requests and replays missed history from its saved positions; it stops with an error after ten consecutive failed attempts, and a recovery that makes progress resets the count. Other failures, such as an unauthorized or malformed response, stop it immediately. Between observations it reads nothing extra: it rereads current state only at startup, after a reconnect, for a newly created child and for review-box changes. Between observations it prints a heartbeat line at the `--timeout` interval (default 300 seconds, at most 3600). The heartbeat shows only that the follow process is running; it does not prove the native stream is connected, and a silently dead connection is detected only when the runtime reports a failure or the stream ends.
- Follow keeps a private state file, by default under the application data directory and named for the server and root Session, or at the path you give with `--state`. It stores a history cursor per Session, which advances only after an observation has been printed and saved, plus the pending requests and the request and terminal records that suppress repeats, so a restarted follow continues from them. The file is bound to the root Session, the server address and the server's process epoch; a different root, server or restarted server is refused instead of reused. It is created with owner-only permissions. Symbolic links, links to other files, files owned by another user or open to group or other access, and a concurrent writer are refused, and each update replaces the file atomically instead of overwriting it in place. A failure prints only a classification (`epoch-mismatch`, `state-lock-held`, `state-invalid`, `state-conflict`, `cursor-ahead`, `budget-exhausted`, `output-failed` or `observer-failed`), never a path, server address, version or request content.

## Changed

- `--follow` requires `--family` and rejects `--input`, `--after` and `--checkpoint`; `--state` requires `--follow`. Without `--follow`, `ycoding decision watch` behaves exactly as before: one bounded result, then exit.

## Limits

- Follow runs only while its process runs. It observes and prints identifiers; it never answers, approves, resumes or retries anything. It does not wake an idle or completed Dots, cloud or other external task, so keep a native follow process or task running for as long as you need notifications.
- Delivery is at-least-once, not exactly-once: after a crash or a failed output write, a restarted follow can print an observation again. Every line carries stable identifiers, so ignore a repeat you already handled, and reread current state before acting.
- A family is limited to 64 Sessions including the root, and a follow state to 1 MiB with at most 8,192 request and terminal records, whichever comes first. The global connection and each stream stop after ten consecutive failed reconnects. Exceeding a limit stops the follow with an error instead of dropping records. Durable events are tracked by the cursor alone, so they never fill a ledger. Replay depends on retained history: pruned history, and requests that appeared and disappeared while follow was disconnected, cannot be reconstructed. After a server restart, start a new state file.
- Run follow in the foreground or as an active background task. Nothing restarts it if it ends, and a background shell task has a finite lifetime.
