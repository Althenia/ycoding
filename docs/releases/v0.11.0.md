# YCoding v0.11.0

## Added

+ Projects pair one Master Session with member Sessions in any directory. Create a Project, add an existing Session, create a new Session in a directory, remove a Session from the Project, or delete it, from the TUI Projects screen (`/projects`) or the web Projects view. A Session belongs to at most one Project. Project creation resolves a leading `~` or `~/` against the home directory and shows an absolute-directory correction for other relative paths before any Session is created. It retains form values and a confirmed new Session when membership fails; retry checks membership and reuses that Session, and an unknown creation outcome blocks another creation. Recovery lasts for the current TUI lifetime.
+ Opening a Project opens its Master chat. You give instructions there; the Master directs members with the `project` tool (list, send, answer, interrupt, inspect, assign and release), either directly or through its own subagents. Members' finished, failed and interrupted turns and their questions, permission asks and reviews arrive in the Master chat, or with the Master subagent driving that member, and wake it automatically. Pending decisions and failures reach the supervising Session even while dispatch is paused. `inspect` reads one pending member request: bounded, redacted action and resources (or question fields), review rules and flags, escalation reasons, and whether it may be approved or declined, only declined, escalated, or is human-only.
+ Project members can have a recorded owner. The Master assigns a member Session to a subagent it launched, or owns it directly; the owner then receives that member's requests and lifecycle notices, including execution starts and settled-step progress, even while idle. Members without an owner route to the Master. Only the Master assigns or transfers ownership, and the Master or the owner releases it as completed or released. Idling, failure, interruption and a settled turn never release it; removing the member, deleting the owner or replacing the Master does. Executor children of an owner receive no Project control. Project participants report their owner to clients.
+ The Master is labeled and pinned first in every member list, and member chats name their Project and Master with a way back. Member rows show live state, last activity and the Master subagent driving them. The Projects tab in the Session composer (`<leader>p`) shows the roster and native actions. Projects keep selection stable and provide direct Add session and Members actions; Enter opens the Master, and wide-layout member previews open the selected member. Project Session pickers show titles and directories on separate rows, retain complete selected details, and filter as you type without taking editing keys away from Find. Assigned Sessions stay visible but unavailable when choosing an existing Master, and Add session lists unassigned candidates.
+ Your message in the Master chat activates its Project; interrupting the Master or a backend restart pauses it until your next message. An optional Project concurrency limit refuses new work with a reason instead of queueing it. The CLI (`ycoding coordination list|get|create|update|delete`) and the remote web client use the same Project operations.
+ Routine delegated questions, permission asks and ordinary guardrail reviews use the existing native decision paths under a centrally revocable policy. Project settings can narrow that policy. Supervisors can decline routine requests and escalate unresolved decisions with an attributed reason chain. A decline can reject an ordinary unclassified permission ask or standard review but never approves one, and under Manual a decline is sent to you instead of settling. Denies, permission ceilings, hard reviews and human-only decisions retain their existing authority.
+ External notification filters can limit TUI attention, web System alerts and phone push to Master Sessions and selected event categories. Each client keeps its own filter; in-app notices, pending questions, permissions and reviews remain visible.
+ Enable ChatGPT and Claude account connectors in Sessions through hosted MCP. Both providers default off and use an existing YCoding OAuth profile with per-connector allow and deny policies. Connector tools retain their selected account binding and recheck profile replacement, provider disablement and connector denial before dispatch. Actions ask by default and preserve permission ceilings and Session guardrails. Claude organization-blocked tools are unavailable. Organization-required approvals and tools requiring user interaction need a fresh human decision; saved approvals and automation cannot satisfy them.
+ Account connector tools are called in Code Mode at readable paths built from the connector and tool names. Matching names get a short suffix from the connector ID, and two tools with the same Code Mode path are rejected instead of one replacing the other. Permission rules, saved approvals and tool capability settings match each tool's registered name. Permission prompts show readable, escaped connector and tool names, and disabled connector calls return a configuration error with a native/local-tool next action.
+ Native ChatGPT Library tools list files, materialize mounted files, download managed attachments and upload files up to 20 MiB. These tools remain available independently of hosted connector discovery and enforce profile, permission and transfer-destination checks. Code Mode `tools.chatgpt.library.prepare` reads an authorized nonempty local file of at most 20 MiB into managed attachment storage for a later Library upload. It needs `read` permission and, for a path outside the project, `external_directory` permission, and makes no network request. A Library upload whose account changes after the upload started is reported as uncertain and is not retried.
+ Permissions, guardrails and answers each have their own autonomy mode: Manual (the default), YOLO or Auto. One Autonomous control sets them: `/autonomous` in the TUI and web, the command palette, and `ycoding run --permissions|--guardrails|--answers <mode>`. Up/Down selects a category, Left/Right cycles its mode, and `1`, `2` or `3` sets every category to Manual, YOLO or Auto. Manual leaves every unresolved request to you and makes no model call. Auto applies fixed rules only: permissions approve ask requests, guardrails approve ordinary standard reviews while you are awake, and answers use only a valid default or a single option labelled Recommended. YOLO lets that category's model evaluator settle what the rules leave open. Hard and custom-rule reviews always need you. The Autonomous dialog identifies inherited-mode sources.
+ Session footers show the effective Permissions, Guardrails and Answers modes beside shell metadata in a single row of content inside a three-row band that matches the header, in standard, BTW and subagent footers. Each known category and mode is one filled chip, such as Permissions Auto: Manual is green, Auto red and YOLO yellow, with readable ink, and unknown modes stay subdued. Project shortcuts sit beside Usage, and Project headers match the normal header band. The sidebar keeps goals and waiting reviews without a separate autonomy section.
+ YOLO evaluators use current task context and applicable consent to resolve routine decisions without repeated questions. Missing facts, explicit denies and human-only reviews remain blocking. YOLO option assessments show the evaluator-reported confidence and evidence for each actual option. A single-choice recommendation requires a unique highest-confidence option at or above 0.8; a multiselect recommendation requires a separately validated compatible set of actual options meeting that threshold. The TUI and web show Assessing options while a YOLO assessment is pending, then the reported assessed or unavailable state and reason. A validated recommendation may answer automatically; weak, ambiguous, invalid, refused, failed or timed-out assessments leave the question waiting for you rather than inventing a recommendation. For these option questions, Manual and Auto make no model call and show Not assessed. Settled views distinguish automatic YOLO answers from answers supplied by you. Assessments do not approve unrelated actions.
+ While a Session has an active goal, YCoding re-checks the pending permission requests, guardrail reviews, Forms, Questions and subagent questions in that Session and its subagents. It does this whenever one is asked or settled and whenever autonomy changes, for example when a mode is switched to Auto or YOLO; it never polls. A routine request is settled only by applying the requesting Session's own current Auto rules or YOLO evaluator, so a goal grants no extra permission. Manual modes, hard and custom-rule guardrail reviews, requests that need an explicit decision, non-routine actions, review-box items, and requests outside the delegated-decision policy always wait for you. Each outcome is recorded in the goal Session, and when a request it was waiting on is answered, the goal Session resumes once, provided it is idle with no subagent, review or shell still in progress.
+ A parent can switch a direct subagent to an explicitly selected provider, model, profile and advertised variant at the next Step boundary, without interrupting or replaying work; idle children remain idle. Omit the profile to use the target provider's default; the previous provider's profile is not transferred automatically. A parent can select a directly owned child's model regardless of causal input origin; direct ownership, effective permission, final deny, revision and Step-boundary checks remain enforced. The profile binding, questions, task state, permission ceiling, ownership and launch retry identity stay intact. A stale expected selection or an incompatible context, provider connection, profile or variant leaves the selection unchanged, and a parent that cannot switch a child's model because the child is not its direct child receives a sanitized explanation. Reading the selected model does not prove that a provider request was made with it.
+ Antigravity subscription accounts: connect a Google account you own with `/connect` and run its Antigravity models, with per-model quota in Usage. The TUI and web Usage views use the quota group headings the gateway reports, with Weekly limit before Five hour limit; missing quota stays unreported, and a failed refresh shows an error without substitute data. Sign-in and token refresh use the OAuth client pair embedded during native and Node builds, installed clients ignore runtime overrides, and custom builds must supply both client values at build time. Effort-specific gateway models that share a base model appear as one model with selectable effort variants, and image, video and PDF input follow what the gateway reports. Streaming preserves multiline responses and fragmented UTF-8, including thinking, assistant text, tool signatures and cache usage, and stream cancellation and read failures propagate to the source. Claude requests preserve full JSON Schema tool inputs, including union-root inputs, across effort variants, and carry tool call ids on every function call and its matching response; a call or result without a matching id fails locally before sending. Requests send no client cache resources or cache breakpoints, so the Cloud Code gateway chooses the implicit Gemini prefix, and missing cached-input telemetry stays unreported instead of displaying a zero cache read. Google may change or restrict the gateway.
+ Every visible built-in tool is available through Code Mode `execute`, not only plugin and MCP tools. Nested calls use the same permissions, guardrails and hooks as direct calls, and each completed nested call is recorded before the program continues, so completed work survives a later program failure or restart. Regex operations in Code Mode programs run in a separate process with a one-second default deadline; an expired operation fails the program with `TimeoutExceeded`. `codemode: false` on an MCP server or plugin tool registration also advertises the tool's direct definition while it stays available in Code Mode. Permissions apply to both paths; disabling `execute` disables Code Mode and leaves independently advertised direct tools available.
+ The browser tool reads cross-origin iframes: page text and elements from approved frames appear in observations, actions work inside child frames, and screenshots no longer fail on every page that contains an iframe. Frames from unapproved origins contribute nothing and are reported as unobserved. New actions: back, forward, reload, key, wait, history search, clipboard read and write, file upload, download wait, developer logs, MHTML export, and WebMCP tool listing and invocation, all under the existing per-site permissions. Isolated mode accepts the actions that need no user profile; history, clipboard, upload and download wait stay profile-only.
+ The computer tool adds `desktop.query`, `desktop.select_text` and `desktop.perform_action`, and lists recently used applications that are not running.
+ Speed is measured for every provider request attempt, including fallback models, background title, goal, compaction, decision, prediction and prompt-generation calls, and replies shorter than one second. Each request records whether it completed, failed or was cancelled. The TUI sidebar and subagent footer keep the last measured speed instead of blanking at each step, and hide the row until something is measured. The Usage screens in the TUI and web add mean and aggregate speed, first-output and total latency percentiles, concurrency and error-rate columns, speed charts in the web Usage page, and a live block that polls only while requests run. Requests recorded before this release carry no outcome. Session and subagent speed show estimated received-output throughput: the first output chunk is excluded, a rate appears only after at least one second of observed output, live rates use a trailing five-second window and restart for each provider attempt, and Usage reports keep provider-counted output and their existing timing rules.
+ Native Dots: set global `dots.enabled: true` and `dots.profile` naming an exact OpenAI OAuth profile, then connect from the Dots connection dialog. Project configuration cannot enable Dots or replace the pinned account. Dots task admission and typed decisions use private server-process Channels. Live turns stream assistant text and canonical Session execution events, with distinct completed, failed and interrupted outcomes. Native decisions require the exact typed candidate and current source and revision; YCoding permissions, explicit denies, ceilings, guardrails and autonomy remain authoritative, and ownership, archive state, account replacement, access revocation and connection retirement invalidate stale authority. Unknown outcomes are not replayed automatically, and prompt text cannot settle a decision.
+ Dots access is one persisted choice covering every existing and future eligible Session on this backend. It starts Off. Connect enables global access and starts the native connection; Disconnect disables access and closes that connection without interrupting admitted work. Failed or unknown access changes are not replayed automatically. `dots.get` (`GET /api/dots`) and `dots.set` (`PUT /api/dots`) read and change it with `{ enabled, expectedRevision }`. Native frames that omit `env_id` route through the authenticated socket's environment, and an explicit mismatching or malformed `env_id` is rejected without dispatching work or retiring another stream.
+ `/dots` in the TUI and Dots connection in the TUI and web command palettes show Computer, Profile, Configuration, Access and actual native Transport separately, including configuration and connection errors, and whether this computer is attached. Open the dialog without selecting a Session or from any root or child Session. Access On does not mean Transport Connected. In the web dialog, Connect or Disconnect, Refresh and the attach control stay usable and the status text stays in place during the five-second background refresh, which is announced to assistive technology instead. A confirmation to use this computer for Dots tasks stays open through refreshes and closes only when the computer, access, connection or read actually changes.
+ Reading Dots status is bounded. The check of your Dot's computers finishes within 20 seconds and otherwise reports that your Dot's computers could not be read; it never reports a computer as attached or detached from a read that did not finish. Status reads and access changes allow 30 seconds in the web client and attaching a computer allows 90 seconds, so a slow read does not turn Connect into a timeout. When a change's outcome is unknown, the dialog reads the current state again and never repeats the change.
+ The YCoding service keeps this computer's Dots executor online while Dots access is On. It reuses one stored device enrollment, reconnects after drops with backoff, runs Dots task commands and file operations under local permission checks, and stops when access turns Off. Each ChatGPT Dots task gets its own YCoding Session in the task's folder, which records the task's commands, file changes and denials; Dots can list your YCoding projects and pick one as the task's folder. After a dropped connection, a Dots task can resume its executor session, including running commands, for 30 seconds. The executor runs ChatGPT commands and file operations that request a sandbox instead of rejecting them: it applies the requested filesystem restrictions to its own file operations and to the command's working folder, under your home directory and the usual permission checks, and reports a refusal as a sandbox denial so ChatGPT can ask for approval and retry.
+ A Dots action that needs your decision is refused at once without running. It opens a review item in the task's Session and returns the exact `ycoding api session.review.decide` commands for once, always or reject; hard reviews offer no always. After you approve, Dots retries the identical action; a rejected action stays refused, and a full review box refuses without opening an item. A file, directory or working directory outside the task's folders asks `external_directory` for its resolved directory, and explicit denies still refuse.
+ A Dots task command can upload one file of up to 20 MiB to your ChatGPT Library through YCoding's private helper channel, selected by a leading `/usr/bin/env CODEX_APPS_MCP_URL=ycoding-library://process`. The task's sandbox, read authorization, Library permission and guardrails apply; the channel never returns credentials or signed transfer URLs, and uncertain writes are not replayed. Default and custom hosted endpoints are unchanged.
+ `ycoding decision list [--json]` and `decision.list` (`GET /api/decision`) list pending permission asks, guardrail asks, questions, forms and open review-box items across Sessions and Locations, with their exact decide commands. Requests are read only from loaded Locations; listing does not start services to find more.
+ `ycoding decision watch <session>` waits on one Session and prints one bounded result: exit 2 with up to 20 pending decisions and their decide commands, exit 0 when the execution settles or the input is rejected, exit 3 with progress after its timeout (default 300 seconds), and exit 1 on an error. With `--input`, succeeded, failed or interrupted is reported only when retained history proves which execution ran that input; otherwise the status is `unknown`, which is never reported as succeeded. Settled and timeout results add a work assessment read once at exit: `completed` only with a current accepted work-completion receipt, otherwise `needs-decision`, `running`, `lost`, `background`, `unconfirmed`, `incomplete` or `idle`, with open todos, pending decisions, child tasks, running Sessions and pending inputs. Settled results include their start and end events and a command that watches the next transition. Exit 0 reports only that an execution settled, never that the work is finished, and `--family` includes the work of a root Session's descendants. The watch never answers, approves or retries a decision.
+ `ycoding dots attach` and `dots.attach` (`POST /api/dots/computer`) attach this computer's Dots executor to your Dot, which ChatGPT's own settings cannot do for a computer other than the one ChatGPT runs on. Attaching detaches your other computers from the Dot, so the command asks for confirmation unless `--yes` is given and reports the state ChatGPT lists afterwards. The Dot, thread and environment shown before confirmation are forwarded as `expectedTarget`, and the attachment is refused when the observed target has changed; the TUI and web ask for confirmation before replacing your other computers. Calls without `expectedTarget` remain valid.
+ Native Dots clients can create a root Session in any existing local directory, and rename, archive, unarchive or delete eligible roots. Delete removes the whole root family only when no descendant is foreign-owned. Pending permission, guardrail, Form, Question, deferred-review, recovery and managed-child decisions on eligible roots reach the native Dots client immediately, including roots it has not opened. Pending requests keep reaching a connected native client after a temporary failure: a failed read of pending decisions no longer stops later requests for that Session on the connection, is retried after 1, 2, 4, 8 and 16 seconds, and no longer reports a request that is still pending as resolved.
+ When a pending request is answered on one connected native Dots stream, by another client or in YCoding, every other connected native stream that shows it receives its resolution exactly once, even if the answer lands while that stream is still reading its pending requests. Connected native Dots clients receive a thread status change for every Session they watch, including runs started elsewhere: idle, active, or waiting on an approval or an answer. A status is sent only when it changes, and a thread read never shows an older status than one already sent. A pending Question that ends because its run is interrupted or the service shuts down is reported as ended, so connected native clients clear it instead of keeping a stale request.
+ `dots.name` in trusted global configuration sets the label this computer shows in ChatGPT's computer lists: 1–100 printable ASCII characters without leading or trailing spaces. Without it, a new registration uses the host name followed by a six-character suffix derived from this installation, such as `studio.local (3f9a1c)`, so computers sharing a host name stay distinguishable; an existing registration keeps its label. Renaming this computer uses ChatGPT's own rename request and confirms the returned name before saving it. The executor is registered before any rename, so a refused registration stops without a rename and its log line names the HTTP status. If ChatGPT answers a rename with a different executor or no confirmation, YCoding keeps the current executor, records the outcome, and does not send that rename again, including after a restart. It never adopts an offered executor automatically, and a rename never selects which computer is attached. The TUI and web Dots connection views show the registered name and the executor name ChatGPT reports beside the computer's host name.
+ The service keeps one installation ID in `remote-control.json` and shares it between the native Dots connection and the Dots executor. A state file whose installation ID is missing or unreadable is an error and is never rewritten. Dots capability discovery reloads after its file watcher fails instead of trusting a stale cached result.
+ The service log records how many native Dots streams are open and initialized whenever a stream initializes, closes, or the connection retires. Each line carries only counts and a time, never identifiers or content.
+ The service installs the bundled `ycoding-operator` skill where this computer's Dots executor advertises it to Dots; YCoding's own Sessions do not load it. Whether ChatGPT reads that skill location is unverified.
+ Settings and Usage sections carry a numbered `§01`, `§02`… marker before their headings. The numbers follow the sections actually shown, so Office on a phone leaves no gap, and screen readers skip the marker. Usage keeps its icon-led headings and the Group select. Every transcript turn opens with a folio head: a `§NN` marker, a role label, and the turn's delivery receipt or response details. Markers keep their number as older history loads and the window scrolls, and a turn whose position from the start of the Session is not reported shows no marker. Usage figures and labels use larger figure type with uppercase labels, so spend and generation values read at a glance.
+ For source builds, `YCODING_MACOS_SIGNING_KEYCHAIN` names the keychain that holds the macOS signing identity, and `bun run install:local --preserve-computer-helper` installs the CLI and Chrome extension while keeping an existing, validated `YCoding Computer Use.app`.

## Changed

+ Agents now put new ad-hoc scratch files, logs, snapshots and patches in a per-task folder under YCoding's data directory (`<data>/tasks/<task>`) instead of a repository `.cache` folder. Existing repository and tool caches are left in place; nothing is moved or deleted.
+ Built-in agents can now read and write anywhere in YCoding's data directory without an outside-directory prompt, where before only shell output and worktrees were allowed. That directory also holds account profiles, Session databases and keys. Newly defined custom agents do not inherit this built-in permission default; configured overrides of built-in agents retain it unless their permissions override it. The default ask elsewhere, `.env` asks, configured overrides, explicit denies, Session ceilings and guardrail reviews are unchanged.
+ Breaking Change: incoming Relay MCP/OAuth, webhook Events, `local.app` tools and `artifact.demo` tools are retired, including `ycoding remote mcp`. Replace that connection setup with global `dots.enabled: true` and `dots.profile` naming an exact OpenAI OAuth profile, then connect Dots from the Dots connection dialog. Ordinary browser Remote, configured outbound MCP and Task MCP remain available.
+ Breaking Change: the `human-input` built-in instruction selector is renamed `decision-input`. Configuration that still uses `human-input` in `builtin_instructions` is invalid and is not rewritten; replace it with `decision-input`.
+ Breaking Change: the separate YOLO and automatic-approval commands, palette entries and flags are removed in favour of the Autonomous control. Existing Session autonomy settings convert once: an automatic toggle becomes Auto, otherwise YOLO stays YOLO, otherwise Manual.
+ Machine display names are account-owned aliases shared across browsers. Rename an owned machine inline in Settings, including while it is offline; the hostname and stable machine identity remain unchanged. Browser-local aliases are not imported, and failed saves retain the draft and confirmed name.
+ Built-in Git worktree guidance creates worktrees at `<data>/worktrees/<repo-key>/<name>`, the managed worktree location, and built-in agents reach every managed worktree without an outside-directory prompt.
+ Messages the Master sends to members use the same first-person user-message presentation as typed instructions, without a separate sender persona. Authenticated origin stays in audit metadata, and message text cannot settle native controls.
+ ChatGPT OAuth, model, catalog, quota, connector, Library and Dots connections share the Codex Desktop identity. Public OpenAI API-key requests retain their own identity, and signed file transfers never receive account credentials.
+ Interactive and deferred Session approval remember the same tool and displayed resource patterns without granting access to other Sessions; deletion or a backend restart clears those grants. Canonical system temporary paths do not trigger outside-repository prompts. Symlink escapes, explicit denies, ceilings and destructive-action checks remain enforced.
+ Built-in agent guidance: maintained agents use native or local tools for YCoding operations and do not discover or call YCoding's ChatGPT connectors; select focused test files or cases at every checkpoint, including integration and merge, and never run full-repository, workspace-wide or entire-package test suites, including scripts or batches that recreate them, while retaining affected non-test checks; ask for one consolidated verification pass per finished feature, batching corrections, rerunning only invalidated checks, and stopping only at completion, a blocker or an approval gate. Session titles lead with the distinguishing action and subject, built-in primary agents and Project controllers delegate bounded implementation, retain integration ownership and reuse valid verification evidence, and replies use plain Markdown without HTML `details` or `summary` wrappers, leave the full list of changed paths to the native Captured changes (TUI) and Edited files (web) summaries, and cite a repository-relative path only where it explains a finding, behavior, action or handoff.
+ macOS Keep machine awake holds display sleep as well as idle system sleep and declares native user activity immediately and every second, independently of shared lid-control ownership. The TUI Status dialog and web Settings → Machine report display and activity separately, including errors and unsupported parts. Activity confirms that the native assertion succeeded; it does not report an unlocked screen or guarantee that automatic lock is prevented, and deliberate locks and managed security policy remain effective.
+ The Usage dashboard opens from prepared, render-ready data instead of aggregating request history on every open. One `usage.dashboard` read (`POST /api/usage/dashboard`) returns a preparing, error or ready view with provider quota filling in separately; clients poll only while a view is preparing and keep table position, paging and sort while quota loads. Existing usage endpoints are unchanged. A one-time startup migration rebuilds the usage tables from retained request records; the first start after upgrading can take longer, and the database grows because it now stores the prepared data. Later starts reuse the prepared views and rebuild only views whose catalog prices changed. Usage speed percentiles batch repeated histogram updates while preserving exact results.
+ The TUI and web Usage screens and task-cost details show only known values. Missing cells render empty instead of `unreported`, `Unknown`, `N/A`, `Waiting` or `Measuring`; a partially priced cost shows its priced subtotal; lines with nothing known are omitted; untitled Sessions read `Session <id>`. The `>=` lower-bound marker, priced and unpriced request counts, `so far` and `incomplete` labels stay. A subagent with accounting but no priced request shows `$0.00` with `so far` or `incomplete`.
+ Retryable pre-output provider failures use at most three physical attempts (the first plus two retries) instead of ten, with two- and four-second delays. A configured model fallback starts after those three attempts.
+ Computer-use input no longer shifts keyboard focus away from you, and pixel input to a Chromium window on another Space fails immediately instead of being dropped silently.
+ Chrome extension: the extension and backend use bridge protocol version 5. After `ycoding update`, select Reload for the unpacked YCoding extension in `chrome://extensions`, or the extension stays disconnected. If the popup shows unpaired, create a new pairing code and connect again. History search and download waiting need optional `history` and `downloads` permissions, which the popup requests when you pair or reconnect.
+ The installed `ycoding` executable includes `ycoding api`, `ycoding decision` and `ycoding dots`. `ycoding api` keeps a non-2xx response body on stdout, prints `ycoding: API request failed: HTTP <status>` on stderr, and exits 1.
+ Sessions that the Dots executor creates for its tasks no longer appear in TUI or web Session pickers, searches, pins, quick switches, recent and workspace lists, Project Session choices, the TUI Chrome directory chooser, or the web Session carousel. `session.list` with `background: "exclude"` omits them before ordering, cursors and limits; without it every Session is listed, and opening one by ID, its history and native Dots root listings are unchanged. Roots started through Dots stay listed. A one-time startup migration adds the Session origin and marks existing Dots executor Sessions that a current executor mapping still names; an executor Session whose mapping was already replaced stays listed.
+ The remote workspace uses flat sections separated by single rules instead of nested frames. Text fields, menus and sheets, the focus ring, and the hard-review outline keep their boundaries. The desktop sidebar is a sunken spine: the current destination shows with stronger text and an accent icon, without a green fill or halo, and the phone bottom bar keeps three labelled destinations with the label under the icon. Connection, notice, and consent strips are flat bars with an inset status edge. Sign-in and invitation pages are one narrow column under a full-width top bar, with an `or` divider between Google and the access key, and errors appear as an inset bar.
+ The Sessions list shows rows separated by rules, with plain status text and underline filters. Rows grow with their content. Appearance and Office choices in Settings use the same underline style, and Settings records, devices and notification choices are ruled rows. Question options and guardrail decision grades in request forms are ruled rows, with a coloured start edge and heavier text on the selected option; the hard-review outline is unchanged. The Office roster, inspection card, and attention bar use the same flat rows, and the Office floor is unchanged. The reading position stays steady when the sidebar collapses or the transcript re-wraps at a new width, including rows that gain a folio head.
+ Phone layouts: the composer keeps its draft, attachment controls and send actions usable in a compact layout. Usage filters reflow into a phone-friendly view while retaining provider, profile, model, effort and range selection; the status bar and settings controls adapt to the available width, and Usage incident details and cost/accounting views preserve their selected context on mobile. Short phone layouts move Session status, full-word autonomy-mode labels, sleep and review labels, and the active-goal preview into the conversation scroll area while keeping primary controls in the composer. Usage, composer, Settings, Status and device-alias layouts retain their controls without horizontal clipping.
+ TUI views: confirmation dialogs let Up/Down move through choices, keep Cancel and Confirm visible while details scroll, and settle a selection once. Compact and short permission, guardrail and Form details size to their content, keep the keyboard-selected option visible in long lists, and stay bounded, scrollable and answerable on short or narrow terminals. BTW headers reflect that Session's own pending and execution states, omit the redundant agent name, and shorten long paths. Compact parent and child layouts keep the composer and pending-review controls visible with the autonomy footer. Footer chips gain compact horizontal padding, Session headers omit duplicate titles, and member rosters use available width for titles and directories. Project notification cards keep long titles, status and Open actions in a compact header with full-width bounded previews, Project chats retain their Session panels and standard footer, and Project status words and glyphs use consistent semantic colors across the list, preview and legend.

## Fixed

+ Interleaved transcript notices stay between their surrounding text through settlement, reconnect and forks, using recorded text offsets even when notice clocks or message IDs disagree. Historical text keeps unknown timing and deterministic ordering; hidden state updates do not split visible text. Generic working activity stays in the header without a duplicate transcript row; open text streams retain their Typing indicator.
+ The Context rail distinguishes missing cache telemetry from a reported zero hit ratio and keeps its cache status visible when diagnostics are absent.
+ Settled automatic guardrail approvals and match dismissals no longer fill the conversation, including while a Session loads. Model rejections appear in order within the loaded chat, pending reviews stay at the end, and guardrail status keeps the full record. Failed autonomy refreshes show unknown modes instead of stale permissions, inheritance or sleep state, without emitting a wake notice; a successful refresh restores the current state.
+ Chrome connection dialogs keep the pairing code and actions visible in short terminals, and Page Up, Page Down and the mouse wheel reach the full installation path, service address and permission note. The TUI Connect Chrome dialog sizes to its content instead of leaving blank rows above the scroll hint, and shows the one-time-code instruction only while a pairing code is displayed.
+ Scoped keymaps share one destruction listener per renderable, and process warnings go to the TUI log instead of overwriting the terminal. Automatic titles preserve explicit names and exclude structured provider commentary from title text.
+ Multiline free-text and custom answers show their last line in short terminals and submit the complete value.
+ Restarting the service no longer fails running managed child Sessions with `Agent not found`. Shutdown now stops running drains before releasing Locations, so children end interrupted and suspended and are recovered after restart. Recovery after a restart ends its request on a user or tool turn, so providers that reject assistant prefill, such as Claude Opus 5.5, no longer fail with "The conversation must end with a user message".
+ Touching a directory no longer builds its whole Location graph. Services load on demand, idle Locations are released, model discovery is shared across Locations, and Location builds, configuration reads and first loads no longer publish catalog, agent, command, skill or config update events when nothing changed. Connected clients stop reloading Locations after each such event, which lowers the memory a long-running service holds.
+ The "Will run out" and "Cutting it close" quota alerts fire once per warning level and re-arm only after the pace stays ahead for 15 minutes or the window resets. A restart no longer repeats warnings already delivered.
+ Pasted and dropped local files in the TUI are read by the TUI and sent as content, so a file the service cannot read (for example in another macOS account's home) no longer fails with "Attachment rejected". The 20 MiB limit, text line ranges and directory listings are kept, and the receipt shows the rejection reason.
+ The web prompt receipt no longer keeps showing Processing under a finished Session after a reconnect. The status read retries up to five times with doubling delays, and a missed execution outcome is recovered from the Session log.
+ Direct OpenAI Responses requests for GPT-5.6 and later keep eligible earlier message boundaries as cache lookup markers, so growing conversations can reuse previously cached prefixes. For supported OpenAI and Anthropic models, changing effort keeps the earlier effort and applies later choices as chronological updates; a profile-label change keeps that history only when the account identity is known and unchanged. ChatGPT Codex requests remain key-only, and no cache hit is guaranteed.
+ A short-lived command that loads global configuration and stored credentials exits once its work finishes, even when it finishes before the configuration watcher has started.
+ Opening a subagent from Team selects it directly. Main is no longer offered for the previous parent while the subagent opens, the parent Session is not read again, and Main returns to the same reading position and draft.

## Upgrade

## Limits

+ YCoding still cannot wake an idle Dots conversation: notifications reach only native streams the Dots client has opened.
+ Delivery of pending decisions to a live native Dots client, and answering them there, has not yet been confirmed end to end with a real client; the behaviour is covered by tests against the native protocol.
+ The protocol status has no completed or failed value, so a run another client started appears only as active, then idle.
+ The goal decision loop is not the only decider: an answer from you, a native Dots client or the review box that arrives first is the one that counts, and the loop then leaves that request alone.
+ A computer whose executor an earlier version already left offline is not repaired automatically. Its service log shows ChatGPT's refusal with its HTTP status; bringing it back requires registering that computer's executor again, which gives it a new executor.
+ Each request is sent once per connection. A client that reconnects receives every decision that is still pending, not notifications it missed while disconnected. After the fifth failed retry, pending requests for that Session arrive with its next event.
+ `ycoding decision watch` prints its result when it exits. The executor forwards command output as it is produced, but when Dots reads that output is not specified, so the watch does not rely on Dots reading output before exit. Pending decisions are a point-in-time read: a listed item can settle by its Session's own mode or appear twice while it moves to the review box. Each decide command rechecks it.
+ Commands run by the Dots executor still run with your user account's access: YCoding cannot confine a running program's file or network access. Any local process with access to the service, including the Dots agent, can record a review decision; the decision API does not establish that a person supplied it. Deny rules and the review-box cap still apply. Stop in Dots does not stop a command on this computer: the command runs until it exits, reaches the 600-second default limit, is terminated explicitly, or its executor closes. Messages and results of other YCoding Sessions are not pushed to Dots; use `ycoding decision watch` to learn them.
+ Native approval, reviewer and sandbox labels are adapter-specific, not strict Codex policy equivalence. They describe surfaced typed reviews and no Codex-enforced OS sandbox, not unrestricted YCoding authority or every automatic decision. Non-null model, provider, approval, reviewer, sandbox or configuration overrides reject before effects, including matching values; null or omitted fields preserve defaults. Resume and turn requests cannot change the recorded directory. Exact external ChatGPT decoder compatibility is unverified.
+ Historical text is a transcript-summary projection of actual user and assistant messages, excluding internal system, synthetic and compaction records without relabeling them. A completed summary means its stored projection is complete, not original execution success; pruning can remove those old outcome associations. Live execution statuses use canonical events. Unrecorded metadata remains unknown or null. Stored history and retention policy are unchanged, and no lost execution outcome is reconstructed.
+ External ChatGPT picker discovery and end-to-end selection remain unverified. Live Antigravity acceptance of Claude tool schemas and quota-summary responses remains unverified, and live inference against an Antigravity subscription has not been verified.
+ Live Library delivery through ChatGPT from a Dots task is unverified. Display labels never let several computers stay attached: attaching this computer still detaches your other computers from the Dot.
+ The web Session lists send `background: "exclude"`, which a YCoding service older than this release rejects. Update the service on each connected computer so its Session lists load.
+ Automatic-lock prevention under Keep machine awake depends on the Mac's idle screensaver and lock settings and was not established by assertion success.
+ Large Usage dashboards can still exceed the two-second warm-read target. Models defined only by external plugin packages read as unpriced in Usage, because pricing does not load external plugin packages. Code Mode value-size caps are soft limits, not hard heap isolation.
+ Connector availability depends on hosted-service access and completed upstream authorization. Claude profiles require the `user:mcp_servers` grant. Set up connectors and consent in ChatGPT or Claude. Account connectors launch no native client, copy no external client's credentials, and use no desktop cookies. ChatGPT connectors use the hosted endpoint's `initialize` handshake because its `server/discover` advertises a revision its list results do not satisfy. Claude connector requests use the Claude Code client identity, including the `X-Mcp-Client-Session-Id` header the proxy requires. When a hosted catalog fails or returns a listing invalid for its negotiated MCP revision, that provider's tools are unavailable for the request, the backend log names the connector server, and prompts still run. Each catalog contains only the connectors installed and authorized in that account.
