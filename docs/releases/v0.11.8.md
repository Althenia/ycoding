# YCoding v0.11.8

## Added

+ `dots.detach` (`POST /api/dots/computer/detach`) and `ycoding dots detach` detach this computer from your Dot, and the TUI and web Dots dialogs show Detach while it is attached. The request is sent once, only when ChatGPT allows disconnecting this computer, and is never retried; the computer is then read again, and a refusal reports `rejected` and an unknown outcome `unconfirmed`.
+ `dots.remove` (`POST /api/dots/computer/remove`) and `ycoding dots remove` remove this computer's executor from your ChatGPT account, only when ChatGPT allows deleting it. A confirmed removal marks the local enrollment removed and turns Dots access Off, so nothing reconnects; turning access On again enrolls a new executor. Other computers and executors on the account are never removed.
+ The Dots computer status reports ChatGPT's view of the executor connection (`readiness`: `connected`, `offline` or `unknown`), whether ChatGPT can use this computer for tasks (`usableForTasks`), and the Dot's environment status (`dotEnvironment`). A field ChatGPT does not return in the expected shape is omitted.
+ While Dots access is On, YCoding connects to ChatGPT's cloud task host with the selected Dots sign-in and reports this computer ready (`thread/environmentReady`) for the Dot task threads bound to its executor, as ChatGPT.app does. Reports are retried with backoff and sent again after a reconnect.
+ Dot conversation operations, through the API and `ycoding dots`: `dots.threads` lists the Dot's threads and tasks, `dots.task.updates` reads a task's updates, `dots.thread.read` reads a thread transcript, `dots.thread.send` sends or queues a message, `dots.thread.interrupt` interrupts a turn, `dots.resume` resumes the Dot runtime, and `dots.thread.requests` and `dots.thread.respond` list and answer the approval and input requests ChatGPT raises for a thread. Each change is sent once; when the outcome is unknown it is reported as `unknown` and not sent again. YCoding never answers a ChatGPT request on its own.

## Changed

+ The Master and supervisors now settle every member request themselves through `project answer` in every autonomy mode, including Manual: routine, decline-only and explicit-decision requests, hard, custom-rule and outside-repository guardrail reviews, permissions, and questions and forms. Approve allows a request once, decline rejects it with the rationale as the member's feedback, and an answer settles a question or form. Deny rules and permission ceilings still hold, so an approval of something they cover stays denied. A guardrail review raised by an invalid guardrail configuration cannot be approved because its deny rules are unreadable: `answer` returns `escalated` with reason `configuration-invalid`, and a decline settles it. Supervisors resolve their members' issues and take to the Master only blockers they cannot resolve or coordination needs across members, and the Master resolves supervisor escalations itself.
+ A member request reaches you only by escalation: a coordinator's explicit `escalate` (member → owning subagent → Master → you), or an `answer` that refuses, errors or is uncertain and returns `escalated` with a reason the coordinator then escalates. Project inspect reports each request's delegation class (routine, decline-only or explicit-decision) as risk information for the decision. The Master and supervisor prompts and the Project tool description state this rule.

## Fixed

+ `project create` accepts an optional `repository`, an absolute directory path inside a Git repository. The member's worktree and Session are created in that repository, so a Master whose Location is not a Git repository can create members. A `repository` outside any Git repository fails naming the path, and omitting it keeps using the Master's current repository.
+ Commands that call `ycoding api` or `gh api` inside shell loops no longer trigger an outside-repository review, and the advisory scan no longer warns about API paths, `/dev/null` or temporary directories.
+ Project coordinator Sessions can run read-only commands such as `ycoding api GET`, `gh run view` and `gh run list`; commands that change anything stay blocked.
+ Deletion deny rules (deleting the filesystem root or home directory) now also apply inside shell loop and conditional bodies.
+ `ycoding` no longer cuts off output written to a pipe when it exits. Large responses from `ycoding api`, such as `GET /openapi.json`, previously stopped at a 64 KiB boundary when piped into another command, so a Dot reading them through this computer got truncated JSON.

## Limits

+ The cloud task host connection, readiness reports and Dot conversation operations follow the shapes ChatGPT.app 26.1106.51428 uses and have not been exercised against ChatGPT. YCoding presents the same desktop client identity as ChatGPT.app; whether ChatGPT accepts it from YCoding is not yet confirmed.
+ Dot conversation is available through the API and CLI only. Live task updates and the cloud thread queue are not supported.
