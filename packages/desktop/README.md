# YCoding Desktop

Build the macOS Tauri 2 application with `/bin/sh <absolute path to packages/desktop>/script/build.sh --outdir=<fresh-output-directory> [--smoke]`, run from a neutral working directory. `package.json` `build` points at the same wrapper, but `bun run build` and `bun run build:desktop` start an outer Bun in the current directory first, and that Bun loads the directory's dotenv files before any wrapper runs. Task pipelines must therefore call the operating-system shell wrapper directly. It refuses, by name only and without reading values, any `.env*` entry in the repository root, `packages/desktop` and `packages/cli`, `MODELS_DEV_API_JSON`, and the signing, Apple, Tauri-config and client-secret variables, then starts Bun. The build is unsigned (`--no-sign`), offline and locked, and refuses to overwrite: it first reads `cargo metadata --offline --locked`, preserves the existing runtime, `dist`, generated schemas and permissions, built app bundle and `Cargo.lock` under `<output>/preserved` with a verified manifest, and fails if `Cargo.lock` changes. `--smoke` is the only opt-in and adds `--features isolated-smoke`. It also builds an incognito main window and a per-build bundle identifier `app.ycoding.desktop.smoke.t<hex>` from a Tauri config overlay written to `<output>/smoke-config.json`, so the smoke app uses a nonpersistent WebKit website-data store and a separate per-build app-domain identifier; normal macOS bookkeeping may still occur. The build checks that the copied app's `Info.plist` holds exactly that `CFBundleIdentifier` and records the identifier, `incognito: true` and the overlay's path and SHA-256 as `isolation` in the receipt. While it runs it holds an exclusive lock file in Cargo's target directory; it refuses an existing lock and removes only its own. That lock coordinates builds that use this script, not arbitrary Cargo or manual builds sharing the target. The output directory must not exist. The build runs the owning CLI build, prepares its executable and native helpers as Tauri resources, runs the owning Vite/Tauri build and copies `YCoding Desktop.app` from Cargo's configured target directory (reported by `cargo metadata`) to the selected output. Rust is limited to the native shell and restricted IPC/resource ownership.

At startup, choose **Start my own backend** or **Connect to a shared backend**, then activate Start/Connect. Own mode uses the bundled native runtime and stops its private backend when the window closes. Shared mode accepts a credential-free HTTP(S) origin; an empty endpoint discovers an already-running compatible managed local service without starting or replacing it. Shared disconnect leaves that backend running. The mode and shared endpoint are local preferences, not credentials or authorization to connect at launch. An explicit shared URL authenticates like `ycoding --server`, with `YCODING_PASSWORD` or `YCODING_SERVER_PASSWORD` from the app process environment; managed discovery uses the service registration. The window accepts no password and stores no credential.

The Solid/Vite window verifies native health and the initial `server.connected` event and reports connection/reconnection state. Once connected it shows a rail of native Sessions, read 40 at a time with search, paging and pinning, each Session's transcript with a composer, and New chat. New chat places a bound Session in a repository this backend has opened before and is still available. The window keeps a client Session ID and message ID with each draft until the backend confirms them, so an explicit Retry cannot create a second chat or message. The bundled Bun client worker uses the same generated native client as the TUI, not relay enrollment or the hosted browser workspace. Rust owns that worker, its stdin lease, bounded request queue and joined reader/writer tasks. Backend credentials stay inside the Bun native client/control processes. The WebView receives sixteen restricted Tauri invokes and native event, resync and status notifications, never a generic shell/HTTP bridge. Besides connection and Session reads and sends, the invokes search and page Sessions, read one Session by ID, pin and unpin a Session, stop a chat, list and answer pending permission and form requests for a given Session ID, and list models and switch a Session's model. Session lists carry only the fields the rail and conversation header show, and a next-page cursor is accepted only under the connection revision that returned it and only while it is among the 64 cursors that revision returned most recently, whatever reads or searches came between. Model lists carry only display fields; provider headers, body and settings never reach the window. A model switch is refused while the Session is running, because the backend would interrupt the turn. Answers are fenced by the connection revision they were read under, which is never reused across backend connections.

`backend.json` lists every file under the bundled `backend/` directory with its SHA-256 digest. Rust verifies that tree before starting the worker and the worker verifies it before each backend start; any extra, missing or changed file refuses the launch.

Run only selected cases, for example `bun test test/preferences.test.ts test/resources.test.ts test/native-client.test.ts test/models.test.ts test/requests.test.ts test/model-switch.test.ts test/sessions.test.ts` from this package and `cargo test --locked` in `src-tauri` for the Rust host. The requests, model-switch and sessions cases start `/bin/echo` in place of the bundled backend and serve synthetic backends on loopback inside the test process. The actual backend cases in `test/native-backend.test.ts` require `YCODING_DESKTOP_TEST_RESOURCES` set to the prepared `src-tauri/runtime` directory (`bun run prepare:backend -- --outdir=<fresh-directory>`) or a built app's `Contents/Resources`. `test/isolation.ts` starts every backend-side process inside a generated deny-by-default `sandbox-exec` profile with owned synthetic state and the loopback fake provider. It probes that boundary step by step, stopping at the first unexpected result, before the fake provider starts or the bundled backend first runs. While the tests run, the harness's own HTTP requests may reach only granted endpoints or verified bundled-backend loopback listeners, and never follow redirects. Run them only after the review gate in `specs/desktop.md`, from this package with `env -i HOME="$HOME" PATH=<bun directory>:/usr/bin:/bin YCODING_DESKTOP_TEST_RESOURCES=<Resources directory> bun test test/native-backend.test.ts`. The harness refuses to run if it inherits a credential-named variable. Run the window smoke only on the executable of an app copied by a `--smoke` build, together with the `build-receipt.json` that build wrote beside it; never write or edit a receipt by hand. Before isolation the smoke refuses the app unless that receipt is a regular, canonical file naming this bundle and executable, recording the executable's actual SHA-256 and listing only the `isolated-smoke` feature, so a default build's receipt or one for another app is refused. It also refuses a receipt unless its `isolation` carries a valid `app.ycoding.desktop.smoke.t<hex>` identifier and `incognito: true`, and the app's `Info.plist` holds that identifier as its single `CFBundleIdentifier`. The receipt is not signed, so a hand-made receipt with matching contents would pass; its origin rests on the build that produced it. Build and run native-window smoke locally; installing in Applications, signing and publishing are separate operations.
