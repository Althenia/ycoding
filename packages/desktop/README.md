# YCoding Desktop

YCoding Desktop uses an Electrobun Bun host and a Solid/Vite window. The host exposes twenty typed operations and state, event and resync messages; backend credentials remain in the host and backend control process. Events larger than 16,384 UTF-8 bytes cause a resync. The window installs navigation rules before loading its local view. Native enforcement of those rules has not been verified by a packaged window run.

The navigation rule syntax is based on Electrobun `v1.18.1` [`nativeWrapper.mm`](https://raw.githubusercontent.com/blackboardsh/electrobun/v1.18.1/package/src/native/macos/nativeWrapper.mm), SHA-256 `2f9b1b804f92f903012eb525d74e9dc77dffad06334a1353640c47b1b6706aca`: lines 1408–1451 define rule evaluation, 2132–2147 handle WKWebView navigation, 4993–5016 handle CEF navigation, and 7127–7131 expose `setWebviewNavigationRules`. The installed `package/dist/api/bun/proc/native.ts` does not pass `navigationRules` to `initWebview`; the host therefore creates a blank view, explicitly installs the rules, and then loads the local URL. Native enforcement is unverified. The window document also declares `Content-Security-Policy: frame-src 'none'` as its first `<head>` element, so the renderer loads no subframes; it does not govern top-level navigation, downloads or `about:blank` frames, and WKWebView enforcement of this policy is unverified.

On launch the host reads backend preferences and connects to the saved choice, or to the shared managed service if none is saved. Invalid preferences stop automatic connection without rewriting the saved data. Own mode starts a private bundled backend and stops it on disconnect. Shared mode accepts a credential-free HTTP(S) origin; with no origin it discovers a compatible local managed service or starts one using the bundled executable. An incompatible managed service is left running and connection is refused. Shared disconnect leaves the service running. An explicit origin uses `YCODING_PASSWORD` or `YCODING_SERVER_PASSWORD` from the process environment. No credentials are stored in desktop preferences.

The window checks native health and the initial `server.connected` event. It offers Session browsing, search, paging, pinning, transcripts, prompts, interruption, permission and form replies, and model selection. Session cursors and replies are fenced by the connection revision. New chat accepts an available previously opened repository or lets the server resolve the location when the directory is omitted. Draft Session and message IDs remain stable until confirmed.

The private server uses explicit non-detached child mode and retains the control process's group. Its stdin pipe is the ownership lease. Core terminates this direct child through its retained Node handle, waits for exit, and escalates from TERM to KILL after the configured grace without executing a process-list command. This direct-child mechanism does not supervise an entire descendant tree.

An own-mode retirement record, invalid lease or control closure invalidates native bootstrap immediately. Ignore readiness, events and status callbacks after that attempt loses its lease or its lifetime is cancelled. Join unfinished native acquisition, close any late handle exactly once and wait for successful control close before confirming retirement or admitting explicit replacement. A retirement record does not prove that the control transport or native client has closed. A shared endpoint remains independent of its control process.

Private readiness binds the server PID to native health. The internal control channel emits one `desktop.retired` observation only after successful finalization of its private connection scope. Before readiness this confirms retirement even if startup never acquired a child; after readiness it must name the original server PID, whose exit is also observed. Cancellation can retire an unfinished startup before another connection begins. Concurrent retirement joins one outcome. A nonzero or signalled control close, invalid or missing terminal evidence, or failed native close remains an error; repeated disconnect cannot convert it to idle success. Unconfirmed ownership prevents another launch. Once scoped retirement, control closure and native closure are confirmed, an explicit connect can proceed, including after an unexpected backend stop. The controller never retries automatically.

The bridge also exposes `fileChanges` for captured Session changes; `activity` for Session-scoped subagents and attributed repository shells, with a count of unattributed shells; `projects` for coordination groups and repository inventory with cursor metadata; and `usage` for the retained summary and bounded model report. These reads reject results from an earlier connection generation or revision.

`backend.json` records every regular file under `backend/` with its SHA-256 digest. The controller verifies the complete tree and bundled executable version before backend startup, refusing extra, missing, changed or non-regular files. A replacement between verification and spawn remains a risk.

## Build

From a neutral working directory, use `/bin/sh <absolute path to packages/desktop>/script/build.sh --outdir=<fresh-output-directory>`. The shell checks for `.env*` entries in the repository root, desktop and CLI directories, and for configured signing, Apple, model snapshot and client-secret environment variable names before starting Bun. The build refuses signing and notarization configuration, an existing output directory, or existing `runtime`, `dist`, `build` or `artifacts` directories. Preserve existing outputs before running; the build does not delete them. An exclusive lock coordinates this wrapper's builds.

The Electrobun CLI and platform core assets must already be provisioned. The wrapper checks the package metadata, CLI entry points, shared runtime entry points and architecture-specific Bun, patch tools, compressor, launcher, native wrapper, `libasar.dylib` and extractor before starting the build; missing or non-file assets are refused without provisioning them. These presence checks do not verify asset identity or ABI compatibility. Backend preparation builds the CLI at its default `packages/cli/dist` location, refuses to run if that path already exists, and copies the backend into `runtime`. Vite and Electrobun then produce the application. The stable Electrobun bundle replaces `Contents/Resources/app` with `metadata.json` and a `<hash>.tar.zst` payload. The wrapper reads the metadata, checks that every payload path stays inside `YCoding Desktop.app/`, extracts the payload with `/usr/bin/tar` into `validation/` in the output directory without running it, and requires its `backend.json` to match the prepared manifest. Any missing or invalid metadata, unreadable payload, unsafe path or manifest mismatch fails the build without a receipt. The wrapper copies the unmodified outer app to the output directory and writes `build-receipt.json` with SHA-256 digests of the launcher, the validated backend manifest and the outer application tree, plus the validation path. The output directory is for validation and delivery, not backend production. The receipt is not signed.

A user-facing desktop release MUST bundle a backend built with a release installation channel (`YCODING_CHANNEL=prod`, `latest`, or `beta`). Core namespaces its database file by installation channel, so a development-channel backend (for example a worktree branch name) opens an isolated `ycoding-<channel>.db` instead of the user's `ycoding.db`; that isolation is intentional for development builds and MUST NOT be bypassed in product code.

`--smoke` remains refused by the build harness. Source and contract tests do not establish native acceptance.

## Release

The release workflow's `build-desktop` job runs on a `macos-26` (Apple silicon) runner. It installs dependencies with `bun install --frozen-lockfile`, which pins Electrobun 1.18.1 through `bun.lock`, then downloads the official Electrobun v1.18.1 CLI and core darwin-arm64 assets from the upstream GitHub release, verifies their SHA-256 and extracts them into the installed package. Local builds need those assets provisioned the same way. The job builds with `/bin/sh packages/desktop/script/build.sh --outdir=<fresh-output-directory>` using the release version and the `latest` channel, checks that the receipt's backend version equals the release version, and archives the app.

The release asset is `YCoding-Desktop-v<version>-darwin-arm64.zip`, created by `bun script/release-archive.ts create-desktop <version> <app> <output>` with `ditto` without resource forks, extended attributes, quarantine or ACLs. The archive contains exactly the self-extracting outer bundle: `Info.plist` (identifier `app.ycoding.desktop`, executable `launcher`, icon `AppIcon`), the executable `MacOS/launcher`, an empty `Frameworks`, `Resources/AppIcon.icns`, `Resources/metadata.json` (identifier, name, channel `stable`, hash) and `Resources/<hash>.tar.zst`. Release finalization requires the four CLI archives plus this zip and writes seven checksum lines (five archives, `LICENSE`, `NOTICE`) to `ycoding-<version>-checksums.txt`.

The app supports Apple silicon only. It is unsigned and not notarized: the configuration keeps `codesign`, `notarize` and `createDmg` false and `build.sh` refuses signing input. A downloaded copy carries the macOS quarantine attribute, so Gatekeeper blocks the first open until the user allows it, as macOS does for any unsigned download: right-click Open, or allow it in Privacy & Security. Building from source is also supported.

## Verification

Run selected tests only, for example `bun test test/preferences.test.ts test/resources.test.ts test/native-client.test.ts test/models.test.ts test/requests.test.ts test/model-switch.test.ts test/sessions.test.ts test/backend-controller.test.ts test/host-contract.test.ts` from this package. The controller tests use synthetic loopback backends and `/bin/echo` in place of the bundled backend.

Confined native-backend tests require a separately reviewed build and `YCODING_DESKTOP_TEST_RESOURCES` pointing to `<output>/validation/YCoding Desktop.app/Contents/Resources/app/runtime`, the unpacked payload the build validated. Before execution an independent reviewer must approve the generated deny-by-default profile, canonical resources/backend/run/HOME paths, synthetic configuration, credential-free environment, probe ordering and exact command. Remove inherited credential-named variables with individual `env -u` options without reading their values; preserve HOME, PATH and configured toolchain locations. The harness refuses inherited credential-named variables and limits backend-side processes to its generated sandbox and synthetic loopback endpoints. Stop and report any sandbox `EPERM`; do not widen the boundary or retry outside it.
