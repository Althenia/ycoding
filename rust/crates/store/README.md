# Operational storage engine

## Derived Session cleanup transactions

`session::cleanup_sessions(snapshot, cutoff, cursor)` returns at most 200 expired
Sessions in ascending `(time_updated, id)` order with an exclusive cursor and
strict `time_updated < cutoff`. IDs use UTF-8 binary order, not the tuple codec's
UTF-16 order. Without an updated-time index, the helper scans primary rows in
bounded 200-row reads and retains at most 200 candidates per page. No catalog,
codec or table change is required.
Lossless IDs with colliding replacement-character renderings use their original
code units as a final tiebreak so an exclusive cursor cannot skip distinct rows.

`session::cleanup_projections(tx, sweep_snapshot, sessions, cutoff, active, kind)`
deletes only selected exclusions, file changes or usage/request projections.
It rechecks Session age/update identity, excludes active IDs, and compares current
projection encodings with the snapshot. New or changed rows remain intact. Child
reads are bounded at 128 records; counts accumulate without returning deleted
records. The transaction owns rollback; committed pages can be retried or resumed
after reopen without double-counting. Events, sequences, messages, Session rows,
revisions and manifest blobs are not mutated.

Usage/request deletion uses the existing domain operations, recording analytics
source intents and a pending physical-purge fence in the same transaction. After
the canonical receipt, Core maintenance calls the attached `Handle::purge()`
before acknowledging success. An absent engine retains the fence and reports
failure; start reports, purge and rebuild before admitting reads. Restart retains
the fence, and sweeps with no remaining deletions still retry purge. Keep the
Engine alive until maintenance closes, and close the Engine before the Store.

`tests/session_tables.rs` covers the strict cutoff, 200-Session pages, non-BMP
UTF-8 ties, page rollback, restart after a committed page, activity/freshness
rechecks, concurrent new rows and durable-history preservation.

`ycoding-store` owns the redb engine and transaction/index boundary. `Catalog::EMPTY` declares no domain tables. Domain owners supply compiled `TableSpec` declarations and schema-owned record codecs; the engine creates only `storage_metadata` plus the declared primary/index tables. All operational tables use `TableDefinition<&[u8], &[u8]>`.

## Lifecycle and resources

- Initialize a new explicit file path with `Store::initialize(path, options, catalog, Metadata::new(identity, generation))`. Supply a nonzero 16-byte database identity and positive generation. Initialization uses exclusive file creation and never opens or replaces an existing file.
- Reopen an existing file with `Store::open(path, options, catalog)`. Missing, empty, corrupt, incompatible, unregistered-table and catalog/codec mismatch errors fail closed. Do not reset data or select memory after an open error.
- Request disposable operation explicitly with `Store::disposable(options, catalog, metadata)`. Each call creates a distinct real `InMemoryBackend`; it has transaction semantics, not reopen durability.
- Construct, retain and shut down the `Store` lifecycle owner outside an async executor's ready-task loop. The owner is neither `Send` nor `Sync`; this prevents moving its destructor onto its writer thread. Share `store.client()` (`Client: Clone + Send + Sync`) with consumers. The owner dereferences to `Client` for local calls.
- Use `Options::core()` for a 128 MiB cache or `Options::meeting()` for a 64 MiB cache. Both select 256 queued requests and 64 concurrent snapshots. Explicit overrides permit cache sizes from 1 byte through 128 MiB and queue/snapshot counts from 1 through 256. These are engine budgets, not process-RSS guarantees.
- Call `Store::shutdown()` to close admission, drain accepted requests and join the one blocking writer. Owner drop also drains and joins. Surviving clients reject new work after shutdown. Drop snapshots to release their permits and database handles; a resident snapshot deliberately keeps its file locked and remains readable after owner shutdown.

## Transaction and cancellation contract

`Client::submit` accepts only `FnOnce(&mut Write<'_>) -> Result<R, Error> + Send + 'static`, with `R: Send + 'static`. The transaction context exposes typed `get`, `put` and `delete`, not redb commit/abort handles. An async closure cannot satisfy this signature, and a transaction borrow cannot escape in the result. Keep provider/network/filesystem operations, human review, notifications and waits outside the closure.

Submission is nonblocking. `Error::QueueFull` means the operation was not admitted; no mutation occurred. A successful submission returns a `Receipt<R>`, usable as a `Future<Output = Result<R, Error>>` or with blocking `wait()` outside executor threads. The writer releases the transaction and table guards, completes an Immediate durable commit, then resolves/wakes the receipt. Publish notifications only from its successful result.

Dropping a receipt cancels a still-queued operation. Once the writer claims an operation, receipt cancellation cannot abort its commit. The writer always settles that transaction even if its caller disappears. A cancelled caller must reconcile its stable domain identities before resubmitting; cancellation does not promise rollback. Queued cancellation occupies its bounded queue slot until the writer dequeues it.

Every failed typed operation latches transaction failure. Even a closure that catches a uniqueness/codec/storage error and returns success cannot commit earlier mutations. Explicit closure rejection rolls back the complete batch. For cross-record owner, digest, revision and RESTRICT checks, call `Write::reject(error) -> Error` and propagate its result or discard it; either action latches rollback, including mutations made later in the closure. Use `Error::Domain { kind: &'static str, message: &'static str }` for stable domain classification and safe public text. Supply constants without secrets, credentials or record contents. The method returns the supplied error unchanged. If the closure returns `Ok`, its receipt returns the first retained `Domain` or `Rejected` error; other rejected errors and caught typed-operation errors settle as `TransactionAborted`. If the closure returns `Err`, that error is preserved. A transaction panic rolls back and fences the writer. Nested submission and blocking receipt waits on the same writer return `Error::Reentrant`.

`Client::submit_with_snapshot` accepts the same closure and returns `Receipt<(R, Snapshot)>`. It reserves one snapshot permit before admission, commits the operation on the writer, and opens the returned read transaction before another queued mutation can run. A rejected or failed commit returns no snapshot. A read-transaction opening error after a successful commit can still leave the mutation committed; reconcile stable identities rather than replaying the closure. Queue rejection and queued cancellation release the reserved permit. Use this boundary to reset derived generations and capture their exact committed source state without an external wait in the write transaction.

`Write::scan`, `Write::index` and `Write::index_range` use the same bounds, ordering, cursor and explicit result-limit contracts as their Snapshot counterparts. They read the transaction's own uncommitted puts, deletes and index membership changes, return owned decoded records and latch errors like the other typed operations. References and cascades remain domain-owned checks and mutations in that closure; the engine supplies no foreign-key or cascade framework.

`Error::CommitUncertain` represents a redb commit error other than `TransactionPoisoned`: all mutations are atomic but may already be durable. The writer is fenced, later queued operations fail without executing, and new mutations are rejected. Close the owner, release snapshots, reopen compatible storage and reconcile stable identities before admitting new writes. Never replay the uncertain closure automatically. Rollback failure also fences the writer.

## Read snapshots

`Client::snapshot()` captures one real redb MVCC read transaction. Its typed `get`, primary `scan(lower, upper, limit)` and named `index(name, logical_key, after_primary, limit)` return owned records; no table guard or iterator escapes. Primary ranges use encoded-key byte order. An index cursor is an exclusive encoded primary identity within the selected logical index key. Explicit limits bound scan/index result counts.

### Ordered index windows

Both `Snapshot::index_range<T: TableSpec>(&self, name: &str, query: IndexQuery<'_>)` and `Write::index_range<T: TableSpec>(&mut self, name: &str, query: IndexQuery<'_>)` return `Result<Vec<IndexEntry<T::Record>>, Error>`:

```rust
pub struct IndexQuery<'a> {
    pub lower: Bound<&'a [u8]>,
    pub upper: Bound<&'a [u8]>,
    pub prefix: Option<&'a [u8]>,
    pub order: IndexOrder,
    pub after: Option<&'a IndexCursor>,
    pub limit: usize,
}
pub enum IndexOrder { Ascending, Descending }
pub struct IndexCursor {
    pub logical_key: Vec<u8>,
    pub primary_key: Vec<u8>,
}
pub struct IndexEntry<R> {
    pub record: R,
    pub cursor: IndexCursor,
}
```

Bounds compare full encoded logical keys, not physical index keys or primary identities. Included/excluded logical bounds include/exclude the entire equal-key group. `prefix` intersects those bounds with a logical byte prefix. Express a tuple-component prefix with `tuple_key` containing complete leading components, retaining their terminators: a prefix for `String("s")` matches `(String("s"), I64(seq))`, not `(String("st"), I64(seq))` or `(String("s\0"), I64(seq))`. An empty prefix matches all logical keys. Reversed or disjoint bounds and zero limits return no records; catalog and index names are still validated.

Ascending order compares logical key then primary identity; descending reverses both. Unique indexes have one identity per logical key; nonunique ties use encoded primary identity. Partial-index `None` records are excluded. Copy the last returned entry's cursor into `after` for the next page, using the same index, bounds and order. The cursor is exclusive in the selected direction and remains effective if its record is deleted. Use one Snapshot for gap-free, duplicate-free pages; changing the write view or taking new snapshots between pages does not freeze index membership. No table guard or iterator escapes either API, and only the requested number of records is decoded.

For a Session sequence window, build `prefix = tuple_key(&[KeyPart::String(&session_id)])`, lower/upper bounds from `(session_id, seq)`, choose `Descending` for newest-first or `Ascending` for forward history, and supply an explicit limit. The tuple and index physical encodings remain version 1; range/prefix translation does not add stored data or change catalog manifests.

Hold one snapshot when reading coupled records and domain watermarks. Commits do not alter resident snapshots. Snapshot drop, including drop during future cancellation, releases only its own permit and guards. Excess concurrent snapshots return `Error::SnapshotLimit`, never queue unbounded readers. Release snapshots before external waits unless a consumer contract explicitly requires a retained coherent view.

## Metadata and catalog

`storage_metadata` stores `physical_format = ycoding-redb`, `catalog_version = 1`, `record_codec_version = 1`, `key_codec_version = 1`, `database_identity`, `generation`, and the exact compiled catalog manifest. Versions and generation use eight-byte big-endian unsigned integers. The manifest identifies primary table names, index names, parent tables and uniqueness; declaration ordering does not affect it. Open verifies physical types, the complete table set, manifest, versions, identity and generation before serving operations. Physical-format and codec versions are independent of application wire/event versions.

Implement `TableSpec` with a record type, primary key, record encode/decode, named index definitions and `index_key` for each index. Return `None` from `index_key` for records excluded by a partial predicate or domain null rules. Register each spec through `TableDeclaration::of::<T>()` in a static `Catalog::new(1, declarations)`. Reject empty, reserved or duplicate names; do not register placeholder domain tables.

`put` replaces the primary record and its old/new index memberships in the same transaction. Unique indexes map the logical key to one primary identity and reject a different owner with `Error::UniqueViolation { index }`. Nonunique index keys are the tuple `(Bytes(logical_key), Bytes(primary_identity))`, with the primary identity as value and ordering tiebreak. `delete` removes primary and index entries atomically. Index reads reject dangling, stale or inconsistent memberships instead of returning false matches. Domain owners implement their foreign-reference/cascade/refcount rules through these operations within the same closure.

## Ordered key codec version 1

`tuple_key(&[KeyPart, ...])` uses lexicographic tuple ordering. Type ranks are `Null < U64 < I64 < Bytes < String`; compare integers numerically within their type and strings lexicographically by unsigned UTF-16 code units. Null sorts first. A shorter equal-prefix tuple sorts first.

| Component      | Encoding                                                                       |
| -------------- | ------------------------------------------------------------------------------ |
| Null           | tag `00`                                                                       |
| u64            | tag `01`, eight big-endian bytes                                               |
| i64            | tag `02`, reinterpret as u64, flip the sign bit, eight big-endian bytes        |
| Bytes          | tag `03`, escaped bytes, terminator `00 00`                                    |
| LosslessString | tag `04`, big-endian UTF-16 code-unit bytes, escaped bytes, terminator `00 00` |

Escape each zero byte as `00 FF`; retain nonzero bytes. The terminator sorts before every escaped content byte, preserves prefix ordering, and separates tuple components without collisions. UTF-16 includes lone surrogates without replacement or normalization. Use a consistent component type per domain key position; do not infer numeric coercion across u64/i64 tags.

## Session-core tables

`session::TABLES` declares the 18 event, Session, context/compaction, and instruction tables below. The declarations contain all 25 baseline secondary/unique indexes, including SQLite's implicit task-input uniqueness name `sqlite_autoindex_session_task_2`; SQLite's primary autoindexes are represented by the named primary KV tables, not duplicated secondary tables. The catalog does not implement projector, instruction folding, compaction selection, task transitions, or runner logic.

### Records and codec

Record codec version 1 begins with byte `01`, followed by each record's declared fields in order. Signed integers use eight-byte big-endian two's-complement values; reals preserve all eight IEEE-754 bytes, including negative zero. Optional values have `00`/`01` presence tags, so SQL NULL is distinct from JSON null, zero, false, and an empty string. Stored integer booleans remain integers; unchecked SQL columns are not narrowed to `bool` or nonnegative counters.

Strings have an eight-byte nonnegative code-unit count and big-endian UTF-16 units. Arrays have a count followed by elements. JSON uses tags `00` null, `01` false, `02` true, `03` real, `04` string, `05` array, and `06` object; objects contain a count and lossless key/value pairs. Decoders reject unknown tags/versions, negative or impossible lengths, duplicate object keys, truncation, and trailing bytes. JSON is represented by `ycoding_schema::JsonValue`, not `serde_json::Value`.

`Document<T>` validates a schema-valued column with `ycoding_schema::DomainDecode`, retains its complete stored JSON value, and exposes a separately decoded typed view. It preserves values rather than replacing stored columns with schema-filtered projections. The Session model, revert, permission ceiling, profile binding, task model/question data, instruction values, manifest content, and exclusion selector reuse their schema domains. Autonomy is Core-owned in the TS baseline and remains JSON. Message data omits `id`/`type` in storage; `Message::info()` restores those columns and invokes the schema codec. `Pending::info()` invokes the schema pending codec, including the current persisted compaction input kind. These views do not alter the stored record. Instruction entry/blob values are nullable JSON, not nullable text.

### Transaction operations and cascade ownership

- `append`, `reserve_sequence`, `claim_sequence`, and `delete_aggregate` preserve `event.ts:26–51`, `:256–365`, `:588–599`: allocation starts at 0 from an absent watermark of −1, reservations take max without clearing owner, replay requires the next sequence or an exactly matching existing event, strict owner divergence fails, and non-strict future replay from a different claimed owner is ignored. Owner checks preserve TS truthiness: an empty stored owner does not fence replay, but remains distinct from NULL; an empty replay owner does not claim an existing NULL owner. `event_empty_owner_preserves_ts_truthiness_without_coercing_null_identity` asserts these cases. JSON replay equality ignores object-key order and distinguishes signed zero. Allocation overflow rejects rather than wrapping. Call append and the caller-owned projection/pending mutations in one `Write` closure; publish only after receipt success.
- `admit` preserves first pending admission on same-Session/same-kind retry and returns `Admission::Promoted` for an already resident message identity. Cross-Session/kind reuse rejects. The caller owns durable-admitted-event reconciliation and projected message content (`session/pending.ts:95–230`); the storage layer does not synthesize them. `promote` returns the consumed row while inserting the supplied projected message and removing pending membership atomically, enforcing the existing compaction/lifecycle fences (`session/pending.ts:48–71`, `:325–343`). `promotion_rejects_unsupported_pending_kind_without_consuming_it` and `promotion_rejects_empty_delivery_without_consuming_pending` assert rejected promotion leaves both tables unchanged.
- `messages` provides bounded signed-sequence windows with both directions and exclusive index cursors (`session/history.ts:108–133`). `pending` selects one exact delivery group, including NULL for stored compaction inputs, in admitted-sequence order (`session/pending.ts:441–463`). Keep the same Snapshot for Session rows, windows and `latest_sequence`; `append_admission_promotion_and_watermark_commit_or_rollback_together` proves coherent committed and resident views.
- `TaskTable::insert`, `NotificationTable::insert`, `task_by_launch`, and `notification_by_transition` preserve launch, input and notification ownership without folding task transitions (`session/projector.ts:585–657`).
- `session::delete` and `project::delete` are the single Session/project cascade entry points. `delete_revision` deletes only the selected revision's linked descendants and dependent jobs/state/exclusions; legal NULL-parent revision roots remain independent. `delete_task` removes task-owned notifications, not the independently stored child Session. All operate in the caller's Write and update index membership atomically. Provider continuation/request/usage and artifact owners must extend these entry points with their child tables; they must not install parallel cascade functions. The present compiled groups contain only the tables listed here.
- `manifest_references` derives the current reference count from all four incoming FK tables in the same write view. `delete_manifest` latches RESTRICT failure when that count is nonzero; zero permits explicit removal. There is no stored numeric blob refcount or automatic manifest GC in the baseline. Session/revision deletion removes references but retains shared blob content. Instruction blobs have no SQL FK/refcount/GC at all; preserve them because durable instruction events refer to their hashes (`session/instruction-state.ts:282–297`). Cascades retain both blob kinds. Tests cover four-way RESTRICT, rollback after a caught rejection, reference release, and shared-content retention.

`cascade_pages_remove_more_than_one_batch_without_skipping_signed_prefixes` proves cleanup across 128-record page boundaries and an integer prefix ending in `FF`. `file_initialize_reopen_keeps_catalog_indexes_and_lossless_records` couples durable event/promotion state with odd JSON strings and negative-zero reals. These storage tests do not certify WP-007 projector/runner behavior, imported SQLite roots, provider-owned tables, artifacts, or analytics invalidation.

## Project-artifact and import-provenance tables

## Offline SQLite import

`import::stage(Request { source, candidate, kind, metadata }, progress)` imports an offline synthetic or explicitly selected SQLite source into a new staged redb candidate. It does not activate a database, fence launchers, select recovery roots, or modify SQLite. `DatabaseKind::Core` requires the exact 47 main tables from `packages/core/src/database/schema.gen.ts` and the two bootstrap tables created in that same SQLite file by `database/migration.ts`. `DatabaseKind::Bootstrap` accepts only `migration` and `database_format`. `DatabaseKind::Meeting` uses the separately owned Meeting catalog described below. Every source table has an existing compiled redb owner; `resource_sequence`, analytics bookkeeping and importer provenance are redb-owned additions, not source tables.

The source opens with an immutable `mode=ro` URI and read-only flags. A single SQLite read transaction spans inventory, all row reads, final-reference validation and reopened-candidate comparison. A nonempty WAL or rollback journal is refused; supply an already consistent offline source, because the importer never checkpoints, vacuums, migrates or writes it. The exact table/column inventories and the Core/bootstrap `database_format` identity or Meeting user_version must match. SQLite file encoding must be UTF-8; UTF-16 files are refused before SQLite can transcode and replace invalid text units. SHA-256 of the source file before and after import must be identical. Paths, source contents and credential values are absent from importer provenance and row diagnostics.

Text values use SQLite's UTF-8 decoding semantics: malformed sequences become U+FFFD before schema string decoding or lossless JSON parsing. Valid text preserves embedded NULs and its exact Unicode code units; JSON retains escaped lone surrogates, dynamic keys, negative zero and JSON null. SQL NULL remains distinct from present JSON null. Numeric columns retain their declared INTEGER or REAL representation without conversion. A REAL stored in an INTEGER column remains unrepresentable where the compiled record field is `i64`; the importer fails closed with table, one-based source row ordinal, column and type/codec reason rather than truncating or changing the stored field type. Row ordinals refer to ascending source `rowid` order, not sensitive primary identities.

The importer creates a private sibling staging directory, calls `Store::initialize` with exclusive creation there, and links the newly created inode to `candidate` without replacing an existing path. Initial writes enforce record CHECKs, primary identity and indexes. A second pass invokes every owner's typed `put` against the complete candidate write view, enforcing foreign references including artifact/version cycles without depending on insertion order. Source `sqlite_sequence.web_latency` seeds the redb allocator; deleted SQLite IDs are not reused. No source row is dropped or coerced on validation failure.

After closing the writer, verification reopens the candidate with the exact compiled catalog. It independently rereads the same SQLite snapshot, compares per-table source/candidate SHA-256 digests of length-framed encoded primary keys and complete records in source `rowid` order, counts all reopened primary rows, and traverses every index in bounded windows to verify membership validity and expected cardinality. Rows and indexes use 128-record batches. The singleton `import_provenance` table records importer version 1, source fingerprint/size, per-table row counts/digests and the imported latency high-water value; `migration` and `database_format` retain only original source rows. Use `import::catalog(kind)` to reopen this staged format.

The synchronous progress callback runs outside write transactions and may return `ControlFlow::Break(())` to cancel. Cancellation, validation/storage/verification failures and caught callback panics close all owned workers and remove the candidate created by that invocation; an existing candidate is never removed. Cleanup failure returns an explicit combined error. A hard process kill cannot execute cleanup: an unvalidated private file can remain, and this API provides neither resume nor activation. Later root/activation owners must keep such candidates unselected; no crash-cleanup or launcher behavior is supplied here.

`tests/import_sqlite.rs` builds isolated real SQLite files using the current baseline DDL and tests reopened documents/values/indexes, bootstrap rows, cyclic references, multi-page index groups, sequence nonreuse, source byte equality, malformed UTF-8 replacement decoding, invalid CHECK/FK/type/document rows, existing-path refusal, unsupported inventories/formats/WAL, cancellation and reopened-candidate corruption. The WP-001 producer requires installed TypeScript workspace dependencies; hand-built fixtures do not prove every populated WP-001 cohort.

The APIs take lossless `JsonValue` documents, validate the strict schemas from `extensions/meeting/src/store.ts:17–128` and return schema-ordered views. Reads validate identity columns against the document. Imported per-meeting JSON rows retain their actual SQLite rowid; replacement preserves that insertion position, while insertion allocates the next current table position. Meeting list search uses SQLite's ASCII-only lowercase behavior and sorts by updatedAt descending then SQLite BINARY ID order. Final sequence admission is Meeting-global and monotonic; temporary segments do not advance it. Record IDs cannot move between Meetings and approval history cannot change on replay. Parent checks, all child cascades and compound consumer writes share the Meeting transaction; failures latch rollback even when a caller catches them. Recovery interrupts only recording/stopping Meetings and running jobs, preserves failed-job details, and marks applying proposals uncertain without issuing external writes or changing either database's generation.

### File-level erasure owner

Use `meeting::MeetingStore::initialize(file, metadata)` or `MeetingStore::open(file)` for the Meeting lifecycle. The owner retains an OS advisory lock in `<file>.erasure.lock`, shares its current `client()`, and dereferences to Client for ordinary reads and compound write closures. It is non-Send/non-Sync like Store. The low-level `meeting::initialize/open` functions remain engine entry points for importer and transaction tests, not file-replacement ownership boundaries. Keep runtime access under one MeetingStore owner; do not bypass its lock or replace its files externally.

`MeetingStore::delete_meeting(id)` and `MeetingStore::retain(days, now_ms)` perform logical mutation and file-level erasure before returning success. They close old Client admission, drain previously accepted operations, require release of all resident snapshots, and execute the deletion transaction against the exclusively detached database. A resident snapshot rejects this operation before its own deletion commits; old Clients remain closed, and callers must release the snapshot, recover through `erase()`, and obtain the current `client()`. Transaction primitives `meeting::delete_meeting(tx, id)` and `meeting::retain(tx, ...)` remain usable inside an enclosing transaction; call the lifecycle owner's `erase()` after that enclosing commit to establish the file-level guarantee.

Erasure creates and fsyncs a private `<file>.erasure` pending directory before mutation, copies only retained typed primary rows into a new exclusive redb candidate, rebuilds indexes, checks source index memberships and cardinalities, and compares every reopened candidate record and index against the committed source. Database identity, generation, codecs, original JSON text, rowid order and import provenance are preserved. The candidate and its directory are fsynced before an old-inode hardlink is made durable. Publication uses one same-filesystem atomic rename, followed by fsync of both directories. The selected database is never overwritten or truncated in place.

After publication, every superseded database file in the owned pending directory is overwritten across its full length with zero bytes and fsynced before unlink; the empty directory and its deletion are also fsynced. Successful erasure leaves the selected database plus its payload-free lock file, with deleted record-exclusive payloads absent from both the selected image and any still-open old inode. Retained rows remain readable after reopen. Shared values still present in retained rows are retained, not erased. Models, audio, other filesystem resources, independently managed backups and the imported SQLite source are outside this file set and remain untouched. This is a file-level guarantee: SSD wear levelling, filesystem copy-on-write remnants, filesystem snapshots, external backups and physical media remanence are outside it, as they are outside SQLite secure_delete's file-level guarantee.

MeetingStore reopen completes any pending erasure before admitting work. Recovery always creates, verifies and publishes a new inode before touching any pre-existing staging file, including candidates left by earlier interrupted recovery, so a staging alias cannot corrupt the selected root. A process crash at any step leaves the selected path with either the pre-delete or post-delete canonical state, never a partially copied or scrubbed selected file. The pending directory is retained until cleanup is durably complete. Unknown entries, symlinks, unaccounted hardlinks, locking conflicts, source/candidate verification failures and filesystem errors fail closed. All inode links must be accounted for by the selected path and owned staging entries; a forged staging hardlink cannot erase a filesystem-owned target. An error can occur after the logical deletion or publication committed; reconcile by reopening the owner rather than assuming rollback or replaying mutation. File-level erasure currently requires Unix inode ownership checks and filesystems supporting advisory file locking, hard links, atomic same-filesystem replacement and directory fsync. Other platforms reject deletion before its transaction; unsupported filesystem operations fail explicitly and can fail after logical commit. The process-crash tests do not simulate hardware power loss or certify a filesystem's fsync implementation.

`delete_meeting_with_progress` reports the synchronous `ErasurePhase` checkpoints outside database write transactions. A rejected callback before Finished leaves the pending directory for recovery; an error from the Finished callback cannot roll back the completed mutation or erasure. `tests/meeting_erasure.rs` writes unique random synthetic markers into Meeting, segment and finding records, checks both UTF-8 and stored UTF-16 byte sequences across owned files, retains an old file descriptor to prove overwriting rather than unlink-only cleanup, verifies retention and released-snapshot requirements, and kills a subprocess at every durable/copy/scrub checkpoint before reopening and verifying the selected state and cleanup.

### Domain source inventory and startup

`sqlite_sum(DOUBLE)` uses a fixed-size SQLite Kahan–Babushka–Neumaier accumulator for recorded cost and token sums, preserving decimal and cancellation vectors without collecting request values. Catalog-priced corrections and local-spend totals retain their ordinary sequential-addition rule. Native registration uses the already linked DuckDB C API; no extension, dependency or external code is loaded.

The native database guard owns the C database handle and closes it after the Rust connection disconnects. The registering C connection is disconnected and temporary configuration/function/type handles are destroyed on every settlement path. Only the blocking analytics worker owns this guard. DuckDB allocates and initializes aligned aggregate state, supplies flat DOUBLE input vectors and state-pointer arrays for each callback's advertised count, and owns output-vector capacity including the finalize offset. Callbacks borrow these buffers only for their invocation; no pointer or reference escapes. Update mutates one state at a time; combine copies a source state before borrowing its target, including when pointers alias. Finalize makes the validity mask writable before setting NULL entries. Arithmetic callbacks contain no fallible indexing, allocation, panic or shared Rust mutable state. Native cancellation and watchdog joining precede connection/database release through the existing worker settlement boundary.

`analytics::reports::start(client, private_directory)` registers `reports::SOURCES`, starts the process-wide engine and attaches a non-owning engine link to the Client. Retain the returned non-Send Engine owner outside executor ready-task loops. `client.analytics()` supplies the handle; missing or stopped owners fail explicitly, without canonical report fallback. Close and join the Engine before shutting down its Store. The link retains neither the Engine owner nor a reference cycle.

Open the selected canonical Store after any approved offline import has completed and its candidate has been activated. Complete startup canonical retention before starting reports; then call `reports::start`, complete any pending `handle.purge()` and run `handle.rebuild()` before admitting report reads. Run blocking startup, report, rebuild, purge and shutdown calls outside executor threads. Subsequent canonical mutations already record source intents; call `handle.notify()` after successful receipts as an advisory wake. Reports reconcile even without notification. Canonical provider-request/usage deletion sets the pending physical-purge fence; retention/deletion owners must call `handle.purge()` after their successful receipt before acknowledging cleanup. Web-latency consent, retention and capacity cleanup use the same fence and purge boundary.

### Canonical mutation and asynchronous delivery

Call `analytics::record(tx, Change { source, identity, delete })` inside the same canonical transaction as each source mutation, metadata change, deletion, retention action or committed revert effect. It reads canonical identity/generation from `tx.metadata()`. Its return value is monotonic committed source order, independent of aggregate sequences. Stable `(source, identity)` entries coalesce to the latest action/order; they contain no source payload. A caught record/privacy error still rejects the complete transaction. After the successful receipt, call `handle.notify()` outside the transaction. Wakes are advisory and coalesce when the bounded queue is full; reports and explicit rebuilds also reconcile durable work. Dropped notifications do not lose intents.

Delivery captures a coherent source snapshot/watermark and applies every captured identity in bounded batches. Rows use stable primary identities, not additive usage updates. One DuckDB transaction commits all rows and its internal database identity, canonical generation, delivery generation, source order and schema checkpoint together. Only then does the worker acknowledge in redb. Acknowledgement compares captured versions before removing intents, preserving newer coalesced changes. A lost acknowledgement reconciles the native checkpoint; an uncertain native settlement closes the connection and inspects its checkpoint before another attempt. No cross-engine transaction exists, and DuckDB never runs in a canonical write closure.

Delivery metadata holds current identity/generation, source/applied orders, bounded intent accounting, validity/reconstruction state and the current privacy epoch. At intent overflow the source mutation still commits, advances order and invalidates the generation atomically. Per-identity capture stops until reconstruction; existing intents remain bounded and are reclaimed in 128-entry writer operations outside admission. Invalid and reconstructing generations are not queryable.

### Reconstruction and report reads

Reconstruction closes the old connection, reclaims superseded intents/private candidates, then uses `submit_with_snapshot` to commit a new delivery generation and re-enable bounded capture before opening its exact source snapshot. It writes retained, permitted records into a private candidate, checkpoints the captured watermark, and catches up subsequent changes. Activation commits the canonical generation selector only when identity/generation and checkpoint match a fully applied source boundary. Concurrent overflow, invalidation, cancellation or deadline failure prevents activation. Ahead checkpoints, identity/generation/schema mismatch, missing derived files and pruned delivery gaps require reconstruction, not trust in cursors or expired events. Interrupted-candidate recovery advances delivery generation before reopening readers. The canonical restore owner advances `Metadata::generation` in its selected root before reopening the Store; analytics compares that identity/generation and reconstructs from the selected state.

`handle.report(Vec<Query>)` and `report_cancellable(queries, Cancellation)` capture source watermark/privacy state, release the canonical read transaction, then reconcile DuckDB outside canonical transactions. All queries for a request share one stable native read transaction, including rows, totals and pagination. `Query` contains compiled static SQL, bound scalar parameters and an explicit maximum row count. SQL executes only as a SELECT subquery; external file/network access and extension auto-install/load are disabled, and native configuration is locked. Domain responses acquire no analytics metadata or cross-request snapshot guarantee.

Before releasing rows, the worker rechecks canonical privacy epoch, pending purge and generation validity. Freshness, storage, cancellation, resource and fence failures are explicit `analytics::Error` values, never stale success or synthetic zero. `Cancellation` is single-operation and cloneable; cancelling queued/running work targets only its owned native handle. `wait_querying()` supplies a native-query start signal. Cancellation/deadline settlement joins native work and its watchdog before returning or starting another request.

### Consent and physical purge

Commit the domain-owned consent/retention/deletion change plus `analytics::privacy_changed(tx, scope, purge)` in one redb transaction before acknowledging its operational effect. It reads canonical identity/generation from `tx.metadata()`. The call advances privacy epoch and invalidates analytics immediately. With `purge = true`, it stores a temporary affected-scope marker in `analytics_delivery`; repeated scopes coalesce. Marker overflow becomes one all-scopes pending marker, not an unbounded privacy ledger. While any marker is pending, reports fail with `Error::Privacy`, including during DuckDB outage.

After the canonical receipt, notify delivery or call `handle.purge()`. Reconstruction uses only the selected canonical retained/allowed state, replaces the derived file and removes obsolete owned generation/WAL/spill copies before clearing markers in redb. Deletion failure or a concurrent privacy/source change leaves markers pending and reads fenced. A crash resumes from the durable marker; completed markers retain no history. Logical deletion and owned-copy removal do not promise secure erasure or immutable deletion across backups. Selecting an explicitly approved older canonical backup may restore earlier records and consent; a derived backup never supplies canonical facts.
